How it fits together

The shape of Product OS

TLDR: Product OS is memory plus skills plus commands, packed into five modules you install as a plugin. You need only two verbs each day: /brief-me to open the day and /start to begin any piece of work.

The full idea

Before you go skill by skill, here is the whole thing in one picture. Product OS is not a chatbot. It is an installable system that lives inside Claude Code as a plugin marketplace. It has four kinds of parts: skills, commands, agents, and bridges. Underneath all of them is memory.

A skill is a unit of know-how grounded in a named framework. Jobs to be done from Moesta and Christensen, strategy kernel from Rumelt, heuristics from Nielsen. A skill is a markdown file that says what good work looks like, what it needs before it can run, and what artifact it produces. Skills do not run on their own. A command is the verb you type, like /write-prd or /ship. Commands read memory, call the right skills, and produce the artifact. An agent is a worker a command hands a job to when that job is big and separate: deep research, a hostile code review, writing tests before code exists. A bridge is a special command that reads across two functions and reports where they disagree. /handoff-audit reads the PRD and the design files and catches "the PRD requires an empty state, the design has no empty state screen." Neither side could find that alone.

Memory is what makes any of this personal. It lives in your project at .product-os/memory/ as flat markdown files: your profile, your product context, your stakeholders, your roadmap, your bets, your metrics, your design system, your lessons, your calibration ledger. Every command reads memory before it opines, and the ones that change reality write one dated line back. The skills never get smarter. The memory does.

Now the modules. Core is always installed: the memory schema, onboarding, the daily brief, the router, and three shared skills, which are memory protocol, stakeholder comms, and calibration. PM holds twenty skills for discovery, strategy, PRDs, and go-to-market. Design holds twelve for critique, systems, accessibility, and handoff. Eng is the build module: it turns stories with acceptance criteria into tested software, and it needs PM installed. Leader holds the bridges and needs both PM and Design. You buy bundles, not checkboxes: PM, Design, Leader, or Builder, which is everything.

With the Builder bundle, the system runs a full pipeline from idea to working software. Take the case this guide runs on. Uber Eats grows overall, but weekday orders between 11:30am and 1:30pm sit 30% below dinner. Call it the lunch gap. A problem brief asks whether the lunch gap deserves discovery time. An opportunity assessment asks whether a 12:00 pre-order slot deserves build time. /write-prd writes the spec. Story mapping picks the first slice. Story writing turns the slice into stories with Gherkin acceptance criteria. /build-setup picks the stack once. /build-story turns each criterion into a test first, then code, and the tests gate done. /build-slice builds the walking skeleton. /ac-audit and /ui-conformance check the seams on the build. /ship deploys. The one joint you never shortcut is acceptance criteria as tests.

Day to day you use two verbs. In the morning, /brief-me: one screen with the single thing that deserves your attention, what moved, what is at risk, who needs a touch, and which predictions are due for scoring. If nothing moved, it says so in two sentences. For any piece of work, /start and the outcome you want in plain words: "/start tighten the empty state copy on the lunch cart screen." The router picks a lane. Express for a small clear ask: it names one skill and runs it. Guided for net-new or high-stakes work: it shows the whole chain, skips what memory already covers, and after every step asks go, skip, swap, or stop. Explore when you state no outcome: you get a menu grouped by what you are trying to do.

One more thing about the shape of this guide itself. It runs one case from discovery to go to market, in six phases. Phase one, Discover: you start with nothing but the lunch gap observation and build research questions, interviews, the job, personas, an opportunity tree, and a journey map. Phase two, Shape the value: the value proposition, product-market fit, the business model on one page, and the four risks. Phase three, Decide and scope: Kano, prioritization, the innovation games, the MVP cut, and the story map. Phase four, Specify: the strategy kernel, the metric tree, OKRs, the PRD, the stories, and the states matrix. Phase five, Validate: experiments, usability tests, and heuristic evaluation. Phase six, Go to market: positioning, pricing, launch, and the roadmap. Everything else sits on a Reference shelf: the skills you pull down when a specific job calls for them, not because the sequence reached them. Each phase eats the phase before it by name, so nothing in this guide starts from a blank page except the very first step.

One rule sits above all of it. You keep the judgment gates. The system drafts, structures, audits, and remembers. Appetite calls, ship decisions, and kill decisions stay with the human. The rest of this guide is about making those decisions with better evidence.

The commands

  • /onboarding asks about ten questions about your product, org, and working style and writes the first version of every memory file. Core.
  • /brief-me produces the one-screen start-of-day briefing across roadmap, bets, risks, stakeholders, open questions, and due scorings. Core.
  • /start is the router: say the outcome you want and it picks the express, guided, or explore lane through the right skills. Core.
  • /calibrate scores the predictions that are due and, with report, rebuilds the org's bias profile. Core.
  • /write-prd turns a feature idea into a full PRD with JTBD framing, opportunity mapping, spec, risks, and GTM notes. PM.
  • /roadmap reviews, pressure-tests, or updates the Now/Next/Later roadmap with kill criteria, reconciling against any live tool. PM.
  • /design-critique runs a structured critique of a design against your own principles first and generic heuristics second. Design.
  • /design-system defines, builds, or connects a design system so tokens and components have one source of truth every other workflow reads. Design.
  • /build-setup scaffolds the build once per product: stack choice, repo structure, test harness, deploy target. Eng.
  • /build-story implements one story and verifies it against its acceptance criteria, tests first, the pipeline's workhorse. Eng.
  • /build-slice builds a whole release slice story by story in story-map order, walking skeleton first. Eng.
  • /ac-audit is a PM-to-eng bridge that cross-references the built software against the PRD and acceptance criteria. Eng.
  • /ui-conformance is a design-to-eng bridge that checks the rendered app against the design system and states matrix, not the mock. Eng.
  • /ship deploys what is built, writes the demo notes, and closes the loop in memory, only when the suite is green and the audit is clean. Eng.
  • /handoff-audit is a bridge that cross-references a PRD against the design artifacts and reports every seam defect before it ships. Leader.
  • /pm-design-sync is a bridge that preps a PM and Design sync by finding where the two functions' stated realities disagree. Leader.
  • /team-health-check is the widest bridge: it reads the whole memory system for signs that the product org itself, not the product, is drifting. Leader.

The agents

  • discovery-researcher runs market scans, competitor teardowns, and evidence gathering for or against a bet, starting from what memory already believes. PM.
  • design-critic does the deep design review: heuristic evaluation, states audit, and design-system conformance on one flow, judged by the org's own principles first. Design.
  • test-writer converts acceptance criteria into tests before any code exists, adversarially, and is kept separate from the implementer so nobody grades their own homework. Eng.
  • implementer writes the smallest clean production code that turns the already-written failing tests green, and never edits the tests. Eng.
  • code-reviewer reads one story's diff as a hostile senior engineer, checking correctness, test honesty, convention drift, and scope smuggling before ship. Eng.

PM

Research Hypothesis

TLDR: Turn a raw observation into hypotheses sharp enough to be proven wrong, then rank them by which wrong guess hurts most. Reach for this at the very start of any discovery work, before you talk to a single user.

The full idea

Here is everything you know: Uber Eats is growing, but weekday lunch orders between 11:30am and 1:30pm run 30 percent below dinner orders. That is it. No backlog, no personas, no research. Just the lunch gap. The worst move now is to jump to a fix. The best move is to write down what you think is causing it, in a form that can be killed by evidence.

That form is a hypothesis. The discipline comes from the lean startup tradition and from Rob Fitzpatrick's The Mom Test, and the format is simple: We believe [X] because [Y]; we will know we are wrong when [Z]. The X is a specific claim about a specific group of people. The Y is your causal reasoning, why you think it is true. The Z is the kill condition, the observable signal that would prove you wrong. Most hypotheses PMs write are really wishes, because they skip the Z. A hypothesis without a kill condition is a belief, and beliefs do not get tested. They get defended.

A second phrasing of the same discipline is worth knowing because it names the evidence out loud: I believe [this statement is true]. I will know I am right or wrong when I see the following feedback from the market: [qualitative feedback] and or [quantitative feedback] and or [key performance indicator change]. The two formats do the same job. The first is tighter about your reasoning, since it forces the "because". The second is tighter about your evidence, since it forces you to say which of the three kinds of feedback would settle it: something people say, something people do at scale, or a number that moves. Write your hypothesis in whichever form you will actually use, then check it against the other one. If you cannot fill in all three evidence slots, you are not yet clear on how you would find out you were wrong.

This is what falsifiability means. A good hypothesis sticks its neck out. "People are busy at lunch" cannot fail, so it teaches you nothing. "Office workers skip delivery at lunch because a 40 minute wait does not fit a 60 minute break; we are wrong if most lunch abandoners quote price, not time" can fail, so it can teach you something.

You never write just one. Write several competing explanations for the same gap. Maybe delivery is too slow for a lunch break. Maybe lunch spend comes out of a different mental budget than dinner spend, and fees sting more at $12 than at $40. Maybe offices sit in delivery dead zones where few restaurants list. Each one points to a different product, so picking the wrong one quietly wastes months. Then find the riskiest assumption inside each: the belief that, if false, kills the whole idea. That is what you test first, and your bias should run toward invalidation. Design every question so a negative answer is possible and useful. You are trying to kill your hypotheses fast, not collect reassurance.

The most common mistake is validating with hypothetical questions. "Would you order lunch if it arrived faster?" invites polite lies. Ask about past behavior instead: "Walk me through what you ate for lunch yesterday and how you got it." People are honest about what they did and optimistic about what they would do.

Why does this matter to you as a PM? Because everything downstream, the interviews, the personas, the value proposition, inherits its honesty from this step. Start with a wish and you will build a research program that confirms it. Start with three falsifiable hypotheses and the lunch gap starts answering back.

Capture

STEP 5

State the evidence that would settle it

20 min
Search
Rewrite this hypothesis in the form "I believe [statement]. I will know I am right or wrong when I see: [qualitative feedback] and or [quantitative feedback] and or [key performance indicator change]." Explain the difference between the three kinds of feedback and when each one is the right thing to go looking for.
Get
Qualitative feedback is what people say and do in front of you, a small number of people in depth. Quantitative feedback is a pattern across many people, a survey or a behavioral cut. A key performance indicator change is the number in the business moving. They sit in that order for a reason: the first is fastest and weakest, the last is slowest and strongest, and a claim that only one of them could settle is a claim you will be slow to test.
Build
Take your three lunch gap hypotheses and rewrite each one in the evidence-first form. For every one, fill all three slots. What would you have to hear in an interview, what would you have to see across a cohort, and which number would have to move. Where a slot is genuinely empty, write "none available" and say why, because an empty slot is a real finding about how testable the claim is.
Capture
Write your three hypotheses in the evidence-first form into your doc. Then add one sentence that starts "The cheapest of my three evidence slots to check is ..." and name what you would do first.

Smells to watch for

  • A hypothesis with no "we will know we are wrong when" line. That is a belief wearing a lab coat.
  • "Users" as the who. If you could not name ten real people in the segment, it is not a segment.
  • Three hypotheses that are really one idea reworded. Competing means they point to different products.
  • Questions about the future ("would you ...") instead of the past ("walk me through the last time ...").
  • Kill criteria written after the evidence is in. That is moving the goalposts with extra steps.

Customer Interviews

TLDR: Customer interviews done right produce evidence instead of politeness: questions about the past, a commitment test at the end, and synthesis within a day. Reach for it when writing an interview script, debriefing a call, or checking whether "validation" was real.

The full idea

Two sources here. Rob Fitzpatrick wrote The Mom Test, and Bob Moesta gave us the switch interview. Fitzpatrick's rule is the one to remember: even your mom cannot lie to you if you never mention your idea. People are polite about the future and honest about the past. So you ask about the past.

The Mom Test has three rules. One, talk about their life, not your idea. The moment the idea enters the room, the data leaves. Two, ask about specifics in the past, not opinions about the future. "Would you use X?" is worthless. "When did this last happen? Walk me through it" is gold. Three, talk less, listen more. You are mining for facts, workarounds, and money already spent. You are not pitching.

Some questions that work. "Tell me about the last time you had this problem." "What did you do about it?" The workaround is the real competitor and the real budget. "What have you already tried or paid for?" Spend is evidence, adjectives are not. "Who else struggles with this?" And the sharp one: "What happens if you just do not solve it?" If the answer is "nothing really," the pain does not clear the bar.

Let us run it on our case. Uber Eats is growing, but weekday lunch orders from 11:30am to 1:30pm sit 30% below dinner. Call it the lunch gap. Bad version: "Would you order lunch delivery more often if it were faster?" Everyone says yes. Good version: "Tell me about the last time you got lunch on a work day." Now you hear: "Tuesday, I had 35 minutes between meetings, I looked at the app, delivery said 40 to 55 minutes, so I grabbed a granola bar and kept working." That is a struggling moment, a workaround, and the cost of the workaround, all in one answer. Then: "What did you try?" "I pre-ordered once the night before. It showed up at 11:10, before I was hungry." Now you know timing, not appetite, is the fight.

Then comes the commitment test. Compliments are fool's gold. End every promising conversation with an ask that costs them something: their time (a follow-up session with their real order history), their reputation (an intro to a colleague who has the same problem), or their money (a deposit or a pilot fee). If they advance, that is real signal. "Sounds great, keep me posted" is a polite no. Log it as a no.

Moesta's switch interview is for real purchases. Find people who recently switched to or from a product and walk the timeline backwards: first thought, passive looking, active looking, the event that forced the decision.

Synthesis discipline: within 24 hours, write exact quotes, facts, and commitments, tagged to opportunities. Three interviews with the same unprompted complaint is a pattern worth a bet. One enthusiastic interview is an anecdote. The most common mistake is the word "would" anywhere in the script. This matters to a PM because you will be asked "did you validate it?" and the only honest answer is a list of things people did, not things they said they might do.

JTBD Framing

TLDR: Jobs-to-be-done turns a feature request or a vague idea into the real job a customer is trying to get done, the moment they struggle, and what they compare you against. Reach for it when you evaluate a feature idea, write a problem statement, or need to challenge someone's pet feature.

The full idea

This idea comes from Bob Moesta and Clayton Christensen. Their claim is simple: people do not buy products, they hire them. They hire a product to make progress in a specific situation. So the thing we study is not the persona and not the feature. It is the struggling moment: the exact situation where someone is stuck and wants to move forward.

The method has four steps. First, find the struggling moment. Write it as "When [specific situation], I struggle to [the progress I want]." If you cannot picture the situation clearly, you do not have a job yet. You have a category. Second, write the job statement: "When [situation], I want to [motivation], so I can [expected outcome]." Here is the test: delete your product name. Does the sentence still make sense? If the statement mentions your feature, it is circular and you need to start over.

Third, map the four forces. There is the push of the current situation, meaning what hurts right now. There is the pull of the new solution, meaning what looks attractive. Then there is anxiety about the new thing, and habit, which is everything that keeps people where they are. Most teams only work on pull. But a feature that adds pull and ignores anxiety and habit loses to "do nothing," and "do nothing" is the most hired competitor in every market.

Fourth, name the real competition. What do people hire today for this job? Often it is a spreadsheet, a phone call, or simply ignoring the problem. That is the bar you have to beat, not the big company in your category.

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. A stakeholder looks at that number and says "we need a lunch promo." That is a feature wearing a trench coat. Ask for the struggling moment instead: "When I get 40 minutes for lunch on a work day, I struggle to get real food without losing half my break to waiting." Now the job is clear. The push is a short break and a boring desk drawer. The pull is hot food showing up on time. The anxiety is "what if it arrives at 1:20 and I eat cold noodles in a meeting." The habit is the sandwich shop downstairs and the lunch packed at home, which are fast, cheap, and never late. The real competitor is the sandwich shop, not the other delivery app.

The most common mistake is letting personas do the work that circumstances should do. "Millennials want convenience" tells you nothing. The same person hires a different product at noon on a work day and at 9pm on a Sunday. Circumstance, not demographics. This matters to a PM because every roadmap decision is a bet on a job. If nobody is struggling, nothing gets hired, no matter how good the demo looks.

STEP 1

What is a job to be done?

Personas and Archetypes

TLDR: Compress your interview evidence into a small cast of goal-directed characters you can design for, plus behavioral archetypes that cut by what people do. Reach for this once you have real interview evidence and before anyone starts sketching solutions.

The full idea

By now you have interview evidence on the lunch gap and a job statement from JTBD Framing. The problem is that raw evidence does not fit in anyone's head during a design argument. Personas are the compression format. The idea comes from Alan Cooper, in The Inmates Are Running the Asylum: design for a specific fictional person with specific goals, built from patterns in real research, and you will serve the real people that person stands for. Design for "the user" and you serve no one, because "the user" stretches to fit whatever the loudest person in the room wants to build.

Cooper's personas are goal-directed. What makes a persona is not age, city, or hobbies. It is what the person is trying to accomplish and what stands in their way. That is why the famous failure mode, "Jessica, 29, lives downtown, likes yoga and podcasts", is not a persona at all. It is demographic fiction. Nothing about Jessica's yoga habit tells you whether she can receive a delivery at her desk. The details that earn a place in a persona are the ones that change a design decision.

For the lunch gap, your interviews likely split along one line that matters more than any demographic: whether the person controls where they are at noon. A desk-bound office worker can order at 11:40 and eat at the keyboard when food lands. A shift worker, a nurse, a retail associate, gets 30 unpredictable minutes and no desk to deliver to. Same city, same age range, completely different lunch problem. Two personas, both built from quotes and observed behavior in your interview notes, cover most of your evidence.

Archetypes go one step further and drop the character entirely. An archetype is a cut by behavior: "orders ahead and schedules" versus "decides at the moment of hunger". One person can move between archetypes across a week. That is also where JTBD fits, and the contrast is worth keeping crisp: personas describe who is struggling, jobs describe when and why they struggle. The same office worker hires a completely different lunch on a deadline day than on a quiet Friday. Personas and jobs answer different questions, so you keep both, and neither replaces the other.

The most common mistake, beyond demographic fiction, is inventing personas from imagination and then treating them as evidence. A persona is only as honest as the interviews behind it, so every claim in it should trace back to something someone actually said or did.

Why does a PM care? Because personas are how research survives contact with a roadmap discussion. When someone proposes a feature, "which of our two people does this serve, and toward which goal" is a question with a checkable answer. That question kills more bad features than any prioritization framework.

Continuous Discovery

TLDR: Continuous discovery is a weekly habit of talking to customers and organizing what you learn into an opportunity solution tree, so every solution is compared against other solutions and tied to an outcome. Reach for it when planning discovery, deciding what to build next, or when someone jumps from problem to solution in one step.

The full idea

This comes from Teresa Torres and her book Continuous Discovery Habits. Her big point is in the title: discovery is a habit, not a phase. A "discovery phase" with an end date means you stop learning on a Friday and build for six months on what you knew then. The core sin she names is comparing a solution against nothing. A team falls in love with one idea, and the only question left is "how do we build it." Good teams compare solutions against other solutions, map them to opportunities, and map those to an outcome.

The tool for this is the opportunity solution tree. You build it top-down and prune it bottom-up. At the root is one outcome: the single metric the team is chartered to move. If the root is a feature or a theme, stop and go get the outcome first. Under the outcome sit opportunities: needs, pains, and desires you have heard from customers, in their words. The test is simple. An opportunity is something a customer could confirm: "yes, that is annoying." A solution is something only you could confirm. Under each opportunity you target, list at least three solutions. Always three. One solution under an opportunity means you are already committed, not deciding. Under each solution go assumption tests: the riskiest things that must be true, and the cheapest test for each.

Assumption mapping: for a candidate solution, list assumptions across five types: desirability, viability, feasibility, usability, and ethical. Plot each on importance against evidence. Test the top-right corner first, important and no evidence. Testing the comfortable ones is theater. Tests should be the smallest thing that produces evidence: a fake door, a one-question survey, a prototype walkthrough, a concierge run. Days, not sprints.

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. The outcome at the root is "weekday lunch orders per active customer, 11:30am to 1:30pm." Opportunities we heard in the lunch interviews: "I cannot tell if it will land before my break ends," "by the time I remember to order, the wait is 45 minutes," "I order the same thing every week and still rebuild the cart." Pick the first one. Three solutions: a guaranteed arrival window shown before you pay, a plain "arrives by 12:40" line instead of a range, and a nudge at 11:15 that pre-builds the order. Under the guaranteed window, a big assumption is "people will accept a smaller restaurant list in exchange for a promise they can trust." Cheap test: show the promise on a fake door for a week and count who taps through.

The weekly habit is the part people skip. One customer conversation a week, recruited from people who ordered lunch on a weekday, keeps the tree current. Interview for stories, not opinions.

The most common mistake is opportunities that are secretly solutions wearing need language: "users need a lunch tab." No customer ever said that. Why does this matter to a PM? Because your job is to make good decisions under uncertainty, and a tree with one branch is not a decision, it is a wish with a deadline.

Journey Mapping

TLDR: Mapping one person's end-to-end experience to find where it hurts, then using a service blueprint to find why it hurts backstage. Reach for it when problems span screens, channels, or teams, when onboarding or retention sags for unclear reasons, or before redesigning any multi-step flow.

The full idea

Three sources ground this skill. G. Lynn Shostack invented service blueprinting in the 1980s. Kerry Bodine and the Forrester lineage shaped modern journey mapping practice. And Daniel Kahneman's peak-end rule tells us how to read the emotional line. Hold onto this sentence: a journey map is a diagnostic instrument, not a poster. If it does not change a decision, it is wall art.

Scope it like a diagnostician. One persona, one goal, end to end, including the stages outside your product. The journey starts at the struggling moment, not at your login screen. "Priya, from the 11:40 stomach growl to having eaten at her desk" beats "the user experience of our app." The seams between channels, app to SMS to phone call to app again, are where journeys die, and no single team owns a seam by default. That is why the map has to.

Build the layers from evidence. Rows against a timeline of stages: doing, the observed actions; thinking and feeling, verbatims from research, not invented emotions; touchpoints per channel; and the emotional line. A map without research inputs is persona fan fiction. Read the line with peak-end in mind: the worst moment and the final moment dominate how people remember the whole thing. A mediocre middle matters less than one terrible peak or a limp ending. That reorders your fix list against intuition. Then mark the moments of truth: the two or three points where the relationship is decided. First value delivered, first failure handled, the loyalty ask.

When the cause is backstage, blueprint. The journey map shows where it hurts. The service blueprint shows why. Below the customer's actions you add frontstage, what they see; backstage, the staff and system actions they do not see; support processes; and the line of visibility. Most journey pain traces to something below that line.

Now our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Map one weekday lunch person. Priya opens the app at 11:47 with a meeting at 12:30. The estimate says 25 to 50 minutes, which is the whole question and no answer. She orders anyway at 11:52. The status sits on "Preparing" while the restaurant works a queue of twelve office orders at once. Food lands at 12:41, after the meeting started. Her verbatim: "I gambled my whole break on a range." The peak is the 12:30 mark passing with the status unchanged. The ending is eating cold noodles at 1:10. Above the line, the estimate screen looks fine. Below the line, lunch restaurants batch orders and the platform hands out the same wide estimate at noon that it uses at 8pm. Redesigning the estimate screen would be repainting a door that is nailed shut. The fix lives backstage: a lunch-hour capacity model and a narrower promise the kitchen has actually agreed to.

Output discipline: each mapped pain gets evidence, a stage, a severity, a suspected backstage cause, and an owner. Feed the top items into the roadmap. A map dated last year describes a product that no longer exists.

The most common mistake is building the map in a workshop from what the team assumes users feel. Why a PM cares: a gap like this rarely lives on one screen. The map is how you find the seam nobody owns, and then own it.

Value Proposition Canvas and Statements

TLDR: Map one customer's jobs, pains, and gains against what you offer, check the fit, then compress the match into one sharp sentence. Reach for this once you have a job statement and personas, and before you touch business models or features.

The full idea

You now know who struggles with weekday lunch and what job they are hiring for. This guide answers the next question: what exactly would you offer them, and why would it beat what they do today? The tool is Alexander Osterwalder's Value Proposition Canvas, from the Strategyzer books. Think of it as a zoom lens on one customer segment: not the whole business, just the exchange of value between one type of person and one offer.

The canvas has two sides. The right side is the customer profile: their jobs (what they are trying to get done), their pains (what hurts or blocks them today), and their gains (what a great outcome looks like). The left side is your value map: products and services, pain relievers, and gain creators. The whole game is fit: does each thing on your side connect to something real on their side? Anything on the left with no partner on the right is a feature nobody asked for. Any severe pain on the right with nothing pointing at it is a hole in your offer.

The order matters, and it is the same rule every canvas shares: customer side first, always. Fill the left side first and you get a brochure, a list of things you would enjoy building, decorated with imagined customers. You already did the honest work: the job statement from JTBD Framing and the pains and gains sitting in your interview evidence. This canvas is where they land. And run one canvas per segment: Desk-bound Dana and On-shift Sam do not share pains, so they do not share a canvas.

For the lunch gap, Dana's canvas might read: job, get a real lunch without breaking the flow of the workday. Pains, unpredictable arrival times, fees that feel heavy on a $12 meal, decision fatigue at 11:45. Gains, food landing inside a known 15 minute window, one tap reorder. A pain reliever has to answer one of those pains by name: a guaranteed delivery window answers unpredictability; nothing on that list is answered by "AI powered recommendations".

Product-Market Fit Canvas

TLDR: Stack the five layers of product-market fit, from target customer at the bottom to user experience at the top, and check that every layer is held up by the one below it. Reach for it after you have a value proposition and before anyone writes a feature list.

The full idea

You have a job statement, two personas, and a value proposition for the lunch gap. Each of those answers one question well. This guide stacks them into one picture so you can see whether they hold each other up. The tool is Dan Olsen's Product-Market Fit Pyramid, from The Lean Product Playbook. Olsen's point is that product-market fit is not a feeling you get later. It is five specific layers, and fit means each layer actually rests on the one under it.

Bottom to top the layers are: target customer, underserved needs, value proposition, feature set, and user experience. A line runs across the middle. The bottom two layers are the market, and you do not control them. You can only understand them, choose them, or choose wrong. The top three are the product, and those you build. That line is the whole reason the model is useful: most teams argue about the top three while the answer is sitting in the bottom two.

The connecting move is value mapping. You take each underserved need and ask which part of your offer serves it. Then you take each feature and ask which need it answers. No feature is allowed to exist without a need above it in the pyramid, because a feature with no need behind it is a guess that costs money. This is the same fit check you did on the Value Proposition Canvas, now applied to the whole stack instead of one exchange.

Olsen wraps the pyramid in a six step Lean Product Process: determine your target customer, identify their underserved needs, define your value proposition, specify your minimum viable product feature set, create the MVP prototype, then test it with customers. The rhythm to remember is that you build the pyramid bottom up and you test it top down. You reason from customer to needs to value to features. But a customer can only ever touch the user experience, so feedback arrives at the top and travels down. When someone hates the prototype, the fault may be the screen, or the feature set, or the value proposition, or you may have picked the wrong customer entirely. Test top down means asking those questions in order instead of redesigning the button.

For the lunch gap, the honest version might be: target customer is the desk-bound office worker on a fixed break, not everyone who eats lunch. The underserved need is arrival time you can trust inside a 60 minute window, which nobody serves well today. The value proposition answers that need. The feature set is only what delivers that promise. The most common mistake is skipping straight to the feature set and calling the rest obvious. As a product manager, this one page is what lets you say no to a good idea, out loud, because it has no need above it.

Business Canvases

TLDR: A canvas puts a whole business model on one page so contradictions cannot hide, and every box is a guess with a confidence level. Reach for it when shaping a new product, stress-testing an existing model, or turning a 30-page business case into one honest page.

The full idea

Alexander Osterwalder gave us the Business Model Canvas and the Value Proposition Canvas in Business Model Generation. Ash Maurya gave us the Lean Canvas in Running Lean. The idea is the same: a canvas is a shared argument on one page, so contradictions cannot hide in separate chapters. And a canvas is a set of guesses. Treat every box as a hypothesis with a confidence level, not a fact.

Choosing the canvas. The Lean Canvas is Maurya's startup remix of Osterwalder's original, and it is the one this case needs. It swaps partners, relationships, and resources for Problem, Solution, Key Metrics, and Unfair Advantage. Use it when the question is "is there a business here at all?" for a specific segment you have not served properly yet. The swapped-in boxes are the ones a team is most likely to lie to itself about. The Business Model Canvas is for an operating business or a corporate setting: how the whole machine makes money, including partners, channels, and cost structure. The Value Proposition Canvas is a zoom lens on one segment: customer jobs, pains, and gains against your pain relievers and gain creators. Use it when the value box is hand-waving.

The Lean Canvas does not start from a blank page here. It eats what discovery already produced. The Segment box takes the personas you built in Personas and Archetypes. The Problem box takes the job statement from JTBD Framing and the top opportunities from your opportunity solution tree. The Value box takes the value statements from Value Proposition. If those boxes disagree with each other on one page, that disagreement is the finding.

Fill it honestly, and the order matters. Start on the customer side, never the product side: segment, then problem and jobs, then alternatives, then value, then channel, then revenue. Only then the delivery machinery. A canvas filled from "our solution" outward produces a brochure. Rules per box. Problem: top three, with existing alternatives named, and "nothing" is a valid and deadly alternative. Segment: narrow enough to find ten this week. Unfair advantage: something that cannot be easily copied or bought, and most first drafts here are blank. Key metrics: one or two. Revenue and costs: coarse math is fine, no math is not. One multiplication, price times plausible buyers, exposes most fantasy models.

Four Risks

TLDR: Every product idea carries four risks: value, usability, feasibility, and viability. Reach for this when evaluating an idea, planning discovery, reviewing a PRD's risk section, or when a team is about to build something untested.

The full idea

This comes from Marty Cagan, in Inspired and Empowered. His observation is that most product failure is not building the thing wrong. It is building the wrong thing, confidently. Every idea carries four risks, and discovery's job is to knock down the biggest one before engineering scales it.

The four. Value risk: will they buy it, or choose to use it? This is the riskiest and the most skipped. Proxy signals of real interest, like clicks on a fake door, deposits, or signed letters of intent, beat stated intent every time. Usability risk: can they figure out how to use it? You can test this with a prototype and five users before anyone writes production code. Feasibility risk: can we build it with the time, skills, and tech we have? Engineers answer this, but only if you ask them during discovery, not after you hand them a spec. Viability risk: does it work for the business? Legal, compliance, sales channel, support load, brand, unit economics. This is the risk the PM is uniquely accountable for, and the one that kills products after they launch.

The method. For the idea in front of you, write each risk as a sentence that could be proven false. Rate it high, medium, or low, with one line of evidence, or admit "no evidence." Then design the cheapest test for the highest risk only. Do not test all four at once. Knock down the biggest, re-rank, repeat. A week of discovery on the right risk saves a quarter of building.

Prototypes are the currency: a feasibility spike, a user prototype in Figma, a live-data prototype, a concierge test. Match the prototype to the risk. A beautiful Figma flow tells you nothing about value.

Take our case. Uber Eats grows overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. The idea on the table is a guaranteed lunch arrival window: a short list of restaurants that promise food inside a 15 minute band you can plan a meeting around. Value risk: "Office workers with a break under 45 minutes will accept a shorter restaurant list in exchange for a window they can trust." Evidence: interview quotes only, so high. Usability: "People understand a window promise at checkout and know what happens if it is missed." Probably medium, easy to test with a prototype. Feasibility: ask engineering whether the noon kitchen queue can even be predicted, likely medium. Viability: "The restaurants and couriers we would need at noon can hit that band without us paying away the margin." That is the scary one, and it is math and partner agreements, not opinion. So the cheapest first test is a fake door: show the window promise on a handful of lunch listings for a week and count who taps through. Not a single kitchen agreement signed yet.

One more check from Cagan. If the idea arrived as a solution to build rather than a problem to solve, say so. You can still assess the four risks, but the team is operating as a feature factory and the value risk is probably unexamined. The most common mistake is a risk section that says "risks: timeline." That is a plan risk, not a product risk. This matters to a PM because your credibility comes from being the person who asked "what kills this?" before it was expensive to find out.

The Kano Model

TLDR: A way to sort candidate features by the kind of satisfaction they create: must-be, performance, delighter, indifferent, or reverse. Reach for it when you have a list of ideas and no idea which ones are table stakes and which ones are wow.

The full idea

By this point in the lunch gap work you have a job, two personas, a value proposition, and a Lean Canvas. What you do not have yet is a way to compare the feature ideas that came out of all that. The Kano model, from the Japanese quality researcher Noriaki Kano, gives you one. His insight was that not all features create satisfaction the same way. Some only create anger when they are missing. Some create satisfaction in proportion to how good they are. And some create love out of all proportion to their cost.

Kano named five categories. Must-be features, also called basics, infuriate people when absent and go unnoticed when present. Food arriving warm is a must-be. Nobody praises it, everybody rages without it. Performance features are "more is better": faster delivery, lower fees. You compete here on purpose or not at all. Delighters, also called attractive, are unexpected and earn disproportionate love. Cheap delighters are the best return in product. Indifferent features move nobody either way, and they still cost money to build. Reverse features actively annoy some people when present. A popup upsell at checkout can be reverse: adding it makes the product worse for part of your users.

Two rules make the model dangerous to skip. First, delighters decay into basics over time. Live order tracking was magic once. Now its absence is a bug. Yesterday's wow is today's table stakes, so a Kano map has a shelf life. Second, teams over-invest in performance features, because "20 percent faster" fits on a slide and a delighter sounds like a toy.

The method is a questionnaire, not a debate. For each candidate feature you ask a pair of questions. The functional form: "If you could pre-order at 10am for a 12:00 delivery, how would you feel?" The dysfunctional form: "If you could not do that, how would you feel?" The answers come from a fixed scale: I like it, I expect it, I am neutral, I can tolerate it, I dislike it. The pair of answers, looked up in Kano's table, gives you the category. Like it when present plus dislike it when absent is performance. Like it when present plus neutral when absent is a delighter. Neutral both ways is indifferent, and that answer just saved you a quarter of building.

The common mistake is classifying by team vote instead of asking anyone who resembles a user. Your team knows the roadmap too well to feel surprise, so everything looks like performance to them. Ask the personas, even simulated ones, and let the answer pairs do the sorting. For the lunch gap, this is where your candidate list stops being a list of opinions.

Prioritization

TLDR: Four ways to rank a list of candidates (RICE, MoSCoW, Kano, cost of delay) plus a final check on your own motivation. Reach for it when everything is marked P0, when you need to defend a call, or when you need to decide what not to do.

The full idea

Every list of candidates tells lies. Not on purpose. The lies come from gut feel, from the loudest voice in the room, and from the fact that nobody ever deletes anything. Prioritization is the set of tools that catches those lies. This skill uses four of them: RICE from Intercom, MoSCoW from the DSDM method, the Kano model from Noriaki Kano, and cost of delay from Don Reinertsen. The key point is this: no framework decides for you. Each one catches a different lie. You pick the one that targets the lie you suspect.

RICE is for when gut feel is running the roadmap and you have many candidates to compare. You score each item. Reach is how many people it affects per quarter, and it must be a real number. Impact is a scale per person: 0.25, 0.5, 1, 2, or 3. Confidence is 100, 80, or 50 percent, and if you are below 50 percent, stop scoring and go do discovery. Then divide by Effort in person-months. The score is not the decision. It is the start of the argument. The useful moment is when the score contradicts the favorite idea in the room, and the room has to explain why.

MoSCoW is for a different situation: a fixed deadline and a room full of stakeholders who each think their thing is essential. It comes from DSDM, the agile delivery method, and it sorts everything into four buckets. Must means the release is not worth shipping without it, and the honest test is legal, safety, or "the thing does not work at all." Should means it hurts to leave out but there is a workaround for now. Could means it is nice, and it is the first thing to go when the date gets close. Won't means not this time, said out loud and written down, with the reason. The main failure mode is obvious and near universal: everything becomes a Must. DSDM's own guidance is that Musts should be well under half the effort in the release, because a release that is all Must has no give in it, and a plan with no give breaks on the first surprise. The test that keeps people honest is asking, item by item, "if we shipped on the date without this, what actually happens?" If the answer is "people would be annoyed," that is a Should. Prefer MoSCoW over RICE when the date is fixed and the job is agreeing with other people on scope. Prefer RICE when the date is open and the job is comparing many candidates against each other. And know this: the Won't list is the most valuable one on the page. It is the only part anybody will thank you for later, because it is the only part that ends an argument permanently.

Kano is for when the team cannot tell table stakes from wow. You put each candidate in one of three buckets. Basic features make people angry when missing but nobody notices when present. Performance features are "more is better," and you compete here on purpose. Delighters are unexpected and earn love far beyond their cost. Two traps: delighters decay into basics over time, and teams over-invest in performance features because they are easiest to justify on a slide. You already ran this classification in the Kano Model guide, so here you carry it forward rather than build it again.

Cost of delay is for when everything is "high priority." For each item, ask: what does one month of not having this cost us, in revenue, risk, or learning? Divide by duration to sequence. This is the only framework that handles urgency and importance together, and it exposes fake P0s instantly. A P0 with zero cost of delay is somebody's pet.

Picture our case. Uber Eats grows overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. The candidates that came out of discovery are a guaranteed arrival window on a short lunch list, a one-tap repeat of last week's lunch order, and an 11:15 nudge that pre-builds the cart. Under RICE, the repeat order wins on reach and effort. Under Kano, the arrival window is a delighter and the repeat order is closer to basic. Under cost of delay, every week the arrival window is missing is another week of lunch orders lost to the sandwich shop. Under MoSCoW against a fixed launch date, the arrival window is a Must because the release means nothing without a promise, the repeat order is a Should, the nudge is a Could, and a full lunch subscription is a Won't with the reason written next to it. Four tools, one defensible answer.

The last pass is the hyper-focus trap check. Label which top item is interesting but unimportant and which is boring but load-bearing. Your brain will pick the interesting one on its own, so the ranking has to name the trade. And ship the list with a kill list: what you are explicitly not doing and why. A priority list without a kill list is a mood board. The most common mistake is setting confidence to 100 percent on items with no discovery behind them. That is not confidence, that is hope with a number.

Innovation Games

TLDR: Structured games from Luke Hohmann that make customers reveal priorities through choices instead of opinions: 20/20 Vision, Buy a Feature, Prune the Product Tree, and Speed Boat. Reach for them when a survey would get polite answers and you need honest tradeoffs.

The full idea

Ask someone which features they want and they say "all of them." Surveys collect wishes. Luke Hohmann's book Innovation Games fixes this with a simple move: turn the question into a game with rules, because rules force choices, and choices tell the truth that opinions hide. You already have Kano categories for your lunch gap candidates. The games add a second, independent read: what people pick when picking costs them something.

The lead game here is 20/20 Vision, named after an eye exam. At the eye doctor you never judge a lens on its own. You compare two: better like this, or like this? The game works the same way. Feature cards go up one at a time, and the player places each new card above or below the ones already ranked, one comparison at a time. Nobody has to score anything. They only ever answer "is this more important than that?" By the last card you have a full ranking, and the arguments that happened along the way are worth more than the ranking itself.

Buy a Feature adds money. Each feature gets a price, roughly its build cost. Players get a fixed budget that is deliberately too small to buy everything. Now they must trade. The best version prices one feature higher than any single budget, so players have to pool money and negotiate, and you get to hear what a buyer says to convince another buyer. That speech is the value proposition in the customer's own words.

Two more games fit different moments. Prune the Product Tree draws the product as a tree: trunk, branches, leaves as features. Players place new leaves where they think growth should go, and the point is shape, not addition. A tree with every leaf on one branch is telling you the rest of the product is dying. Use it for roadmap balance. Speed Boat draws the product as a boat and asks players to attach anchors: the things holding it back. Use it when you suspect the biggest wins are removals and fixes, not new features. Anchors on the boat are complaints made safe to say.

When does each fit? 20/20 Vision when you need a ranked list without scores. Buy a Feature when you need tradeoffs and the words behind them. Prune the Tree when the question is where to grow. Speed Boat when the question is what to stop or fix. The common mistake is running a game with one player. The information lives in the disagreement between players, so you need at least a few, and for the lunch gap you can have Claude play them.

Scoping and the MVP

TLDR: An MVP is the smallest product that tests your bet end to end, cut with a fixed time budget and a written not-doing list. Reach for it when a winning idea needs to become a buildable first slice instead of a wish for "phase 1".

The full idea

You now have a winning lunch gap bet from your prioritized cut. The next danger is the word "just": we will just build it. Scoping is the discipline that stands between the winner and a six-month build. Four ideas do the work.

First, Eric Ries and the minimum viable product. The words matter. Minimum: the smallest thing. Viable: it must actually work for a real user. Product: not a mockup, the thing itself. And the purpose is learning. An MVP is not version one with fewer features. It is the cheapest product that tests whether your bet is true. If your bet is "pre-order at 10am gets desk workers to order lunch," the MVP is whatever proves or kills that sentence fastest.

Second, the walking skeleton, which you will meet again in Story Mapping. The first slice must run the whole journey thinly: a user hears about pre-order, places one at 10am, gets food at 12:00, and comes back or does not. Every step exists, badly. Duct tape everywhere invisible. A beautiful ordering screen with no delivery behind it is not a skeleton, it is a severed arm.

Third, cupcake, not dry cake. If the vision is a wedding cake, the wrong MVP is a layer of plain sponge: a fragment of the final thing, complete in nothing. The right MVP is a cupcake: tiny, but it has cake, frosting, and delight in one bite. Small and whole beats large and partial. The pre-order MVP might serve one office district, three restaurants, and a single 12:00 delivery window. Tiny, complete, tastes like the real product.

Fourth, appetite, from Ryan Singer's Shape Up. Instead of asking "how long will this take?", you declare how much time it is worth: "this bet gets six weeks, no more." Time is fixed, scope is the variable. When the work bulges past the appetite, you scope hammer: swing at every piece and ask "does the bet still get tested without this?" Account creation? Order as a guest. Payment integration? Charge the saved card, or take payment on delivery. Ratings? Later. The hammer produces the most underrated artifact in product: the not-doing list. Written, explicit, with reasons. Scope you cut silently crawls back in the dark. Scope you cut in writing stays cut.

The common mistake is scoping by feature completeness instead of by learning. "It needs accounts, payments, and notifications to be real" is the dry cake talking. The only question is what the bet needs to be tested end to end, once, by real lunch orders. Everything else goes on the list you are proud to not be doing.

Story Mapping

TLDR: Lay the work out along the user's real journey, then slice releases as thin end-to-end cuts, starting with the walking skeleton. Reach for it when breaking a big initiative into releases, when a flat backlog has lost the plot, or when planning what an MVP actually includes.

The full idea

This comes from Jeff Patton's book User Story Mapping. His picture: a flat list of work is a bag of parts with the picture on the box thrown away. Prioritized, but story-less. The map puts the picture back. It arranges work along the user's journey, so scope decisions become visible cuts through a story instead of fights over a ranked list.

Building the map has three moves. First, the backbone. Across the top, the user's activities in narrative order, told out loud: she notices she is hungry at 11:40, decides whether to risk delivery, picks something, orders, waits with one eye on the clock, eats, gets back to her desk. Activity level, user language, left to right in time. If you cannot narrate the backbone as a person's day, it is a feature list lying down. Second, steps. Under each activity, the tasks that accomplish it, then variations descending by necessity. Depth shows how well that activity is supported. Third, walk it with real people; the map builds shared understanding before it plans anything. Walking an engineer along the backbone reveals missing steps, like "wait, what happens when the kitchen falls behind at noon?" Those gaps are the cheapest bugs you ever fix.

Now the point of it all: slicing releases. Draw horizontal lines through the map. Each slice must span the entire backbone: a thin end-to-end journey, not a thick fragment. The user completes the whole story badly rather than half of it well. The first slice is the walking skeleton: the minimum path where a real user gets the real outcome once, with duct tape everywhere you cannot see. Later slices deepen activities by priority.

Take our case. Uber Eats grows overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. The walking skeleton is one office district, a hand-picked list of six restaurants that agreed to a noon prep window, a single "arrives by 12:35" line instead of a range, and a text when the courier is two minutes out. No lunch search, no ratings filter, no subscription. But one office worker with a 45 minute break eats on time and gets back to her desk. Slice two widens the restaurant list and adds the one-tap repeat of last week's lunch. Name every slice by what the user can newly do, not by what the team builds.

Here is the anti-slice check. If a release covers three of seven activities completely and four not at all, you built a beautiful third of a product, which is a whole product to nobody. A "phase 1" of restaurant prep-time agreements and a courier zone tool, with no way for a person to see or trust a lunch promise, is exactly this. Patton's rule: you are slicing outcomes, not features.

Keep the map alive. When scope pressure comes, and it comes, cuts happen on the map where everyone sees which part of the journey got thinner, not silently in a ranked list. In this skill the wall is required, not an appendix. Every run produces the written map and an HTML sticky wall you can drag, edit, and walk. A map that exists only as prose has already lost, because you cannot point at a paragraph in a room. The wall is a starting position, never a finding, so the notes must move. For a PM, this is the skill that turns "what is the MVP?" from an opinion fight into a line you draw together.

Strategy Kernel

TLDR: A strategy has three parts: a diagnosis, a guiding policy, and coherent actions. Anything missing one of them is a wish, a slogan, or a budget. Reach for it when drafting or reviewing a strategy, or when a "strategy" is really a list of goals.

The full idea

This is Richard Rumelt, from Good Strategy Bad Strategy. His claim is that a strategy is a kernel with three parts, and if one is missing you do not have a strategy. You have a wish, a slogan, or a budget.

Part one is the diagnosis: what is actually going on, named plainly. A good diagnosis simplifies the overwhelming mess down to the critical aspects. "We lose enterprise deals at security review" beats "the market is competitive." The diagnosis is falsifiable and often uncomfortable. If everyone nods instantly, it is probably not a diagnosis.

Part two is the guiding policy: the overall approach you chose to deal with the diagnosis. The key word is chose, because a real policy excludes other approaches. A policy that forbids nothing guides nothing. That exclusion is the strategy.

Part three is coherent actions: resource commitments that reinforce each other and follow from the policy. The coherence test: if a stranger read only the list of actions, could they guess the policy? If the actions could belong to any strategy, they belong to none.

Let us do our case. Uber Eats grows overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Bad strategy: "Become the platform people love at lunch by delighting customers and closing the gap 30%." No diagnosis, no exclusion, a goal dressed as a plan. Good kernel. Diagnosis: "Weekday lunch buyers have a fixed break under 45 minutes, and our noon estimate is a wide range built for evening demand, so ordering lunch is a gamble against a meeting, and they take the certain sandwich instead." Guiding policy: "Win the weekday lunch hour by being the only option with a promise you can plan a meeting around, on a short list of restaurants that agreed to it, not by having the most lunch choices." That excludes the "run lunch discounts across the whole catalog" play. Coherent actions: sign noon prep-time agreements with a handful of restaurants per office district, stage couriers in those districts before 11:15, show a single arrival time instead of a range for that list only, and stop spending lunch marketing on breadth of selection. A stranger reading those four actions could guess the policy. That is coherence.

Rumelt also names four hallmarks of bad strategy, and you should call them out by name in any review. Fluff: inflated language that restates the obvious, like "customer-centric lunchtime excellence." Failure to face the challenge: a lunch strategy that never mentions the 45 minute break or the kitchen at noon. Mistaking goals for strategy: "close the lunch gap by 30%" is an ambition, not a how. Bad objectives: a long list of everything everyone wants, or objectives as impossible as the challenge they avoid.

The last idea is leverage. Strategy works by concentrating force where it matters: finding the pivot point where focused effort produces a disproportionate result. A strategy that spreads resources evenly across ten priorities has chosen not to have a pivot point. The most common mistake is the word "and" doing heavy lifting in the guiding policy, trying to keep every option open. This matters to a PM because your roadmap is only defensible if someone can trace every line of it back to a diagnosis and a policy that said no to something.

Metrics Trees

TLDR: Pick one north star metric, break it into input metrics teams can actually move, and pair every metric with a counter-metric. Reach for it when defining success for a product, auditing a dashboard, choosing key results, or when a team is staring at a number it cannot move.

The full idea

Here is the idea in one sentence: a metric you cannot break down is a metric you cannot move. You can only watch it. Three sources. Amplitude's North Star framework gives us the top of the tree. John Doerr's Measure What Matters gives us the link to goals. And Andy Grove gives us the habit of pairing indicators so nobody games a number.

Start with the north star. It is the single metric that best captures the value customers receive, and revenue follows it with a lag. There are four tests. It measures customer value delivered, not what the company extracts. So, meals eaten on time, not fees collected. Second, moving it is a leading indicator of the business result. Third, every team can see how their work touches it. Fourth, it is a rate or ratio over a stated period, never a cumulative total. Registered users only ever goes up, so it tells you nothing.

Then build the tree. Break the north star into three to five input metrics. These are the levers teams actually pull: breadth, more users doing the core action; depth, doing more of it; frequency, doing it more often; efficiency, doing it faster or with less friction. Each input breaks down again until you reach a metric one team owns end to end. The tree is the org chart of accountability. The north star belongs to product leadership, inputs belong to teams, sub-inputs belong to squads. A team given a metric three levels above its control is chartered on hope.

Take our case. Uber Eats grows overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. The guiding policy you wrote in Strategy Kernel says you win lunch on a promise people can plan around, so the north star follows from that: weekday lunch orders per active customer in the 11:30 to 1:30 window. Breadth: customers who placed at least one weekday lunch order this week. Depth: items per lunch order. Frequency: lunch orders per customer per week. Efficiency: minutes from opening the app at 11:40 to the order being placed. Now the lunch checkout squad owns "minutes to order placed at noon," and they can actually move it. Give that squad "revenue" instead and they can only stare at it.

Now the Grove part. Every metric optimized alone will be gamed, by users, by teams, or by dashboards. So pair each target with the counter-metric that catches the failure mode. Lunch delivery speed paired with promise-kept rate, because a team can hit a speed average by quietly widening the promise. Activation paired with week-four retention. Engagement paired with whether it is the good kind, because session length is a cost to the user, not a value. No key result ships without its counter-metric named.

One more discipline: leading versus lagging. Lagging metrics like revenue, churn, and NPS tell you the score after the game. Leading metrics like activation rate and time to value are playable during the game. Dashboards should be mostly leading. Reviews can be mostly lagging. A team reviewing lagging metrics every week is performing accountability, not exercising it. The most common mistake is a north star that is a revenue number. That is the board's metric, not the product's. It matters to you as a PM because the tree is how you turn "close the lunch gap" into work a team can start on Monday.

OKRs

TLDR: Objectives and Key Results are a focusing device: one inspiring direction, two to four numbers that prove you arrived. Reach for it when drafting quarterly goals, converting output goals to outcome goals, or when OKRs have become a task list with percentages.

The full idea

OKRs come from Andy Grove at Intel, written up in High Output Management. John Doerr carried them to Google and wrote Measure What Matters. Christina Wodtke added the weekly rhythm in Radical Focus. Here is the core idea. An OKR is a focusing device. The objective is the inspiring direction. The key results are how you will know you arrived. And its real power is what it makes you not do.

Writing the objective: it is qualitative, memorable, time-bound, and slightly uncomfortable. One line a team member could recite cold. If it could be any team's objective, like "delight our customers," it is fluff. Go back to your strategy first. Writing the key results: two to four per objective, and each one is an outcome with a number, never an activity. "Ship the lunch arrival window" is an output. You can ship it while making everything worse. "Weekday lunch orders per active customer from 0.7 to 1.0" is an outcome. It is the reason the window exists.

The conversion test is simple. For any activity-shaped key result, ask "so that what?" until you hit a number in the world. Then write that number. Also attach the counter-metric from your metrics tree, or the key result is gameable by definition.

Let us try it on our case. Uber Eats grows overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Objective: "Make lunch a decision nobody has to gamble on." Key results: weekday lunch orders per active customer between 11:30 and 1:30 goes from 0.7 to 1.0. Time from opening the app at noon to placing the order drops under 60 seconds. Counter-metric: the share of lunch orders that arrive inside the promised window stays at or above today's level, so nobody buys speed by widening the promise. Notice there is no feature in there. The team can build the arrival window, or fix the noon capacity model, or do something nobody has thought of yet.

Now the cascade. Company OKRs set what matters. Teams draft their own OKRs answering "how does our lever move that," and roughly half should be proposed bottom-up. This is Grove's point: people commit to goals they authored. Leadership's review job is coherence checking. Do these team key results plausibly add up to the company one? It is not assignment. OKRs handed down whole become compliance theater by week three.

Grading and cadence. Aspirational key results target around 70 percent attainment, so a straight-A quarter means the targets were sandbagged, and you should say so, gently. Committed key results, like contracts, compliance, or dates promised outside the company, target 100 percent and get labeled differently. Mixing the two silently is how "stretch goal" becomes an excuse. Set quarterly. Check confidence weekly: Wodtke's Monday ritual, per key result, is confidence up or down from last week and why. Grade at quarter end in one honest hour. A key result rolled over twice without examination is a strategy question wearing a metrics costume. The most common mistake is the roadmap with percent signs. If your key results list features, you have a plan, not a goal. As a PM, OKRs are how you say no to a hundred good ideas and mean it.

Writing the PRD

TLDR: The document where everything you discovered converges into something a designer and an engineer can both start from. Reach for it after the thinking is done, never as the place to do the thinking.

The full idea

A product requirements document has a bad reputation, and most of the time it earns it. The bad version is a wish list written on a Monday by someone who has not talked to a customer, handed to a team as if it were a decision. Marty Cagan's framing in Inspired fixes the order. The PRD is where discovery output converges. It is not where product thinking starts. Before it sits the opportunity assessment: what problem, for whom, how big, what alternatives exist, why you, why now, how you will measure it, and a go or no go call. If you cannot answer those, you do not need a better document. You need more discovery.

The lean shape has nine parts. Problem and evidence. Goals and non-goals. Target user. User flows. Requirements with priority. KPIs and guardrails. The four risks. Open questions. Launch criteria. That is the whole thing. Every section is short, and every section is answerable, because by now you have already answered it somewhere else.

Two of those nine get skipped more than the other seven put together. The first is non-goals. Writing what you are not doing, and why, is the only section that prevents scope from growing quietly for three months. It is also the only section that reads as a decision instead of a hope. The second is launch criteria: the conditions that must be true before this goes live, written before you build, when you are still honest. Written after, they become whatever is already true on launch day.

The risk section deserves its own care. Cagan names four risks: value, will they choose to use it; usability, can they figure it out; feasibility, can you build it with the time and tech you have; and viability, does it work for the business, meaning legal, support load, unit economics, brand. State each as a sentence that could be proven wrong, rate it high, medium or low, and give one line of evidence or admit you have none. Then design the cheapest test for the highest risk only. A risk section that says "risk: timeline" is a plan risk, not a product risk.

For the lunch gap, every section has an upstream owner. The problem is the 30 percent gap plus your interview evidence. The target user is a persona. The flows come from your journey map and story map. The requirements are the prioritized cut. The KPIs come off the metric tree. Which brings the real point of this guide. The PRD is a convergence point. If a section has nothing upstream behind it, that is not a writing problem you can solve with better sentences. It is a gap in the discovery, and the fix is to go back and do that work.

Story Writing

TLDR: Epics, user stories, and acceptance criteria that hold up: the three C's, INVEST, SPIDR splitting, and real Gherkin. Reach for it when breaking a PRD or story-map slice into buildable work, reviewing backlog quality, or when stories have become task tickets with "As a user" stapled on.

The full idea

The sources: Mike Cohn's User Stories Applied, Bill Wake's INVEST, Ron Jeffries' three C's (Card, Conversation, Confirmation), and job stories from Klement and Intercom. The story is not the ticket text. It is a placeholder for a conversation plus a confirmation of done. Forget the three C's and you get a pile of tiny contracts nobody discussed.

Keep the hierarchy honest. An epic is a story too big for a sprint or two, tied to one outcome. It answers four things: the problem, the outcome metric, what is out, and "done when," a metric threshold held for a period or an explicit kill decision. A story is a thin vertical slice of user-visible value: as a specific role, I want a capability, so that an outcome. The "so that" carries the weight. A task is an implementation step inside a story, no user framing needed. The cardinal sin is dressing a task as a story. "As a user, I want the lunch capacity model deployed" is a lie with a persona.

Take our case. Uber Eats grows overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Epic: "Weekday lunch customers can order without gambling their break," done when weekday lunch orders per active customer reach 1.0 for four straight weeks, or killed at quarter end. Story: "As an office worker with a 45 minute break, I want to see one arrival time instead of a range before I pay, so that I know whether I can eat before my meeting." Task: build the noon capacity estimate endpoint. When personas mislead, use a job story: when it is 11:45 and I have a meeting at 12:30, I want to know if food will land in time, so I can decide between the app and the sandwich shop downstairs.

INVEST is the review checklist. Independent, schedulable in any order. Negotiable, details left for the conversation. Valuable to the user, vertical not horizontal. Estimable, or it needs a spike, not more words. Small, days not weeks. Testable; a story you cannot demo is a philosophy.

When a story is too big, split with SPIDR: Spike, Path, Interface, Data, Rules. Never split by layer. A front-end story and a back-end story demo nothing. Watch the Rules trap: a story bundling a capacity rule, a restaurant eligibility rule, and a fallback rule is three stories wearing one badge. Ship the simplest promise alone first.

Acceptance criteria are the confirmation. Three to seven, each observable and binary. Use Gherkin when precision pays, as separate lines: Given, And, When, Then. Never folded into one sentence, which hides a second condition inside one bloated Given. Cover the unhappy paths: empty, error, and permission states. And a criterion that hedges is not a criterion. "(decided later)" is a placeholder pretending to be a check. Decide now or cut it into a spike.

The most common mistake is "As a user" on every story. Nobody is "a user." Name the role. And audit your own rewrite: after fixing a story, run the whole INVEST and smells checklist again on the new text. Author mode grades kindly. For a PM, stories are where the strategy finally touches a sprint, so this is where it either survives or quietly dies.

States and Edges

TLDR: Every screen is really five screens: empty, loading, partial, error, and ideal, plus the transitions between them. Reach for it when specing or reviewing any screen, preparing handoff, or whenever only the ideal state has been designed, which is always until you check.

The full idea

This skill comes from Scott Hurff's book Designing Products People Love, where he describes what he calls the UI Stack. The idea changes how you read every mockup: every screen is five screens. The pretty one in the deck is the ideal state. Users spend most of their early relationship with your product in the other four, and those four are where trust is won or lost.

Let me name them. One, the empty state, which is first contact. It has three flavors: first use, where the empty state is the onboarding and should invite the first action; user-cleared, where an empty inbox is a win and should feel like one; and no results, where the screen should repeat what was searched and offer a correction. An empty state that only says "No items" is a dead end dressed up as minimalism. Two, loading. Perceived speed is design's job. Skeletons that match the real layout beat spinners. Optimistic UI beats both when the action is safe to assume. Decide what is interactive during the load, because a frozen screen is an error state with better PR. Three, partial: some data, not enough to be useful. This is the state that makes new accounts look broken. Design the bridge from one item to the fifty-item mockup. Four, error, per class: user-fixable errors say what to do and keep the input. System-down errors apologize and say what is safe to retry. Permission-denied errors say who can help. Five, ideal. Already in the deck. It was never the risk.

Then the transitions. How does empty become partial? How does loading become error? Unhandled transitions are where the flashes, the jumps, and the lost form input live.

Our case makes this concrete. Uber Eats grows overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap, and the fix on the table is a lunch list that shows one guaranteed arrival time instead of a range. Now look at that screen honestly. An office worker opens it at 12:05 and no restaurant nearby can promise delivery by 12:40. That is the no-results empty state, and it decides whether she ever trusts the promise again. Does the screen say "No results," or does it say "Nothing can reach you before 12:40 right now, here is what can get there by 12:55" and show it? While the noon capacity check runs, is the list frozen or can she keep browsing? Her first week, she has one past lunch order, so the reorder shelf built for a regular looks broken. And when her card is declined at 12:10 with a meeting at 12:30, does the app wipe the cart and the desk address? Wiping a form is a hostile act. At noon it is also a lost order.

The method for catching all this is the matrix habit. Screens down the rows, five states across the columns. Every cell either has a design, is marked N/A with a reason, or is a finding. This matrix is exactly what the PRD's spec section checks against at handoff. The matrix closes the seam between the PRD and the mocks.

The most common mistake is reviewing the happy path only and saying "we'll design errors during build." Build designs them as browser defaults. As a PM, you own the requirement. If your spec says "handle errors" and the design has one generic error screen, you did not spec it. Ask for the matrix before the handoff, not after the bug reports.

Experiment Design

TLDR: An experiment is a decision procedure, not a ritual: write the hypothesis first, check you have enough traffic to detect the effect, set guardrails, and fix the window before you start. Reach for it when planning an A/B test, reading results, or when someone says "let's just test it" on something that cannot be tested.

The full idea

The grounding for this skill is Ronny Kohavi's book Trustworthy Online Controlled Experiments. The one idea to keep: an experiment is a decision procedure. If no decision changes based on the result, the experiment is theater. Skip it and ship.

So the hypothesis comes first, written before anything else. The template is: we believe this change will cause this effect for this population because of this mechanism. We will know if this metric moves by this minimum size within this window. If it does not, we will do this specific thing: kill, iterate, or ship anyway and why. The "because" clause carries the weight. A hypothesis without a mechanism is a slot machine pull, and a win without a mechanism cannot be built on.

Here is one for our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. We believe showing a guaranteed arrival time on the restaurant list, not only at checkout, will raise order completion in the lunch window because uncertainty about whether food lands before the break ends is why people back out. We will know if lunch-window order completion rises by at least 3 points within two weeks. If it does not, we kill the change and go back to the people we interviewed instead.

Next, power, honestly. Before running, ask: what is the minimum detectable effect at our traffic? Small products routinely run tests that can only detect a 20 percent lift, then read a flat result as "no effect." Compute it first. If the effect worth acting on is smaller than what you can detect, do not run the test. Use a different instrument: interviews, before-and-after with a holdout, or a painted door.

Then guardrails and the ratio check. Every test carries guardrail metrics that must not degrade: latency, error rate, support contacts, and the counter-metric from your metrics tree. And always run the sample ratio mismatch check. A 50/50 split that arrives as 52/48 means assignment is broken and every number downstream is fiction.

Reading results has four rules. Do not peek early and stop on significance; fix the window in advance. Segment only after the topline result, and only to generate new hypotheses, because twenty segments guarantee one fake "significant" one. A significant result you cannot explain by mechanism gets replicated before it gets celebrated. And losses teach more than wins. A killed idea is discovery working, so log it.

Finally, know when not to A/B test. Too little traffic for the effect you care about. Changes with network effects or long feedback loops. Strategic bets where the option value is bigger than the local metric; no A/B test approves a platform migration. And anything you would ship regardless. In each case, say which instrument replaces the test. "We cannot test this" never means "we cannot know anything." The most common mistake is the success metric switched after the fact to whichever one moved. As a PM, this skill is what keeps you from shipping noise with a confidence interval around it.

Usability Testing

TLDR: Watching a handful of real people try to complete real tasks on your design, then fixing the top three problems and testing again. Reach for it before build, to settle a design argument with evidence, or when the team is debating what users will do instead of watching five of them.

The full idea

Two names anchor this skill. Steve Krug, whose book Rocket Surgery Made Easy argues for small, frequent tests with fixes made the same morning. And Jakob Nielsen, whose research found that five users find about 85 percent of the problems in a given design. The lesson from Nielsen is not "five is enough forever." It is: test five, fix, test five again. That beats twenty users on one version every time.

One boundary before we start. A usability test answers can they use it. It does not answer do they want it. For want, you run customer interviews. Mixing the two questions ruins both answers.

Tests are won or lost in task design. Tasks are scenarios with a goal, not instructions. "You have 40 minutes for lunch and you want hot food at your desk before 12:45. Do that." Not "Tap the guaranteed arrival filter." The moment your task names a UI element, you are testing reading comprehension. Use their reality where you can: their address, their real hunger, their real break time. Four to six tasks, riskiest flow first because attention fades. Include one task that tests whether they can find the feature before you test whether they can use it. Define success per task in advance: unaided, with struggle, failed. Otherwise grading becomes vibes.

Moderating is a discipline of silence. Ask them to think aloud. Answer questions with questions: "what would you expect that to do?" Never rescue before the failure has taught you something: "what would you do if I weren't here?" Never explain the design, because you will not ship yourself alongside it. Watch the hands and hesitations over the words. Behavior is the finding. The polite person who says "this is nice" while failing the task three times gave you a blocker, not a compliment.

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Five participants, all people who work a fixed weekday break. Task one: find food that will arrive before your break ends. Task two: change the delivery address after adding items, because you moved to a different floor. Task three: reorder the same thing you had on Monday. Three of five could not tell whether the arrival estimate was a promise or a guess, so they abandoned the order and walked downstairs. Two said "oh, that's fine" while scrolling past the estimate twice. That is your first fix. Not the small font on the receipt that one person mentioned.

Synthesis follows Krug's rule. Same day, each observer lists the three worst problems they saw. Dedupe. Fix the top three only before the next round. A forty-item findings report is where usability data goes to die. Small test, top-three fix, retest beats the big quarterly study by an order of magnitude. Log findings and fixes so the same problem found twice shows up as a pattern.

Unmoderated tools are for benchmarking known flows with completion rate and time on task. They cannot probe, so do not use them to explore a design you are still shaping. Why a PM cares: you will sit in arguments about what users will do. The cheapest way to end the argument is to watch five of them.

Heuristic Evaluation

TLDR: A structured walk through a flow using Nielsen's ten heuristics and Norman's two gulfs to find where users will stumble. Reach for it in critique, design QA, before handoff, or when you want to judge a competitor's UX without running a study.

The full idea

A heuristic evaluation is the cheapest usability method there is. You do not need users in the room. You need a flow, a checklist, and the discipline to look at the flow the way a distracted first-timer would, not the way the designer who built it does. The method comes from Jakob Nielsen, who published ten usability heuristics in the 1990s, and from Don Norman, who described the seven stages of action in The Design of Everyday Things. The posture underneath both is the same: an error is a design failure, not a user failure. Every place a user could stumble is the artifact's fault until proven otherwise.

Here is how you run it. Walk the real flow step by step. Not the happy-path demo, the actual flow. At each step ask Norman's two questions. First, the gulf of execution: can the user figure out what to do here? Are the options visible and labeled in the user's own words? Second, the gulf of evaluation: after they act, can they tell what happened? Is feedback immediate? Did the state visibly change?

Then sweep the ten heuristics and report only the ones that fire. Visibility of system status. Match with the real world. User control. Consistency. Error prevention. Recognition over recall. Flexibility for experts. Minimalism. Error recovery in plain language. And help, findable when needed. You look for violations, not essays.

Take Uber Eats at lunch. Weekday lunch orders between 11:30am and 1:30pm run 30% below dinner, and the pre-order flow you scoped is supposed to close that lunch gap. An office worker taps "Place order" at 11:55 and the button goes grey for four seconds with no spinner and no message. That is a gulf of evaluation failure and a visibility of system status violation. The failure scenario in one sentence: a hungry office worker taps Place order, sees nothing happen, taps again, and gets charged twice five minutes before a meeting. That is a blocker. Compare that to the lunch spot list using the word "merchant" on one screen and "restaurant" on another. That is a consistency issue, and it is minor. Both are findings. They are not the same weight.

That brings us to the most common mistake: the inventory. Teams produce forty undifferentiated findings and hand it over as a list. Nobody can act on that. The skill says rate every finding as blocker, major, minor, or polish. Blocker means users will fail the task. Major means many will struggle. Minor is friction. Polish is nice to have. A report that names three blockers is worth more than one that lists forty items with no ranking.

Why does this matter to a PM? Because you will review designs every week, and you need a vocabulary that is not "I don't love it." Per finding you state the heuristic violated, the specific element, the failure scenario in one concrete sentence, the severity, and one suggested fix. Then you close with the three you would fix first and why. That is a review an engineer can act on and a designer can argue with. It turns taste into evidence.

Positioning

TLDR: Positioning is choosing the market frame so buyers compare you to the right thing, expect the right thing, and pay the right price. Reach for it when writing positioning, messaging, a launch narrative, or when a product is being described by its features instead of its value.

The full idea

This is April Dunford, from Obviously Awesome. Positioning is context-setting. The market frame you choose decides what buyers compare you to, what they expect, and what they will pay. And here is her sharpest point: weak positioning is almost never a product problem. It is a default frame nobody chose.

There are five components, and the order matters because each one feeds the next. First, competitive alternatives: what would customers do if you did not exist? Include "spreadsheet," "intern," and "nothing." The alternative sets the bar. Positioning against a rival nobody uses only flatters the rival. Second, unique attributes: capabilities you have that the alternatives do not. Features, yes, but also your delivery model, your expertise, your integrations, your business model. Third, value: what those attributes enable for the customer, stated as outcomes. Take each attribute and ask "so what?" and keep asking until you hit something a buyer would pay for. Fourth, best-fit segment: who cares a lot about that value? Specific enough to target. Positioning for everyone is positioning for no one. Fifth, market category: the frame that makes your value obvious to that segment. Category is a lever, not a fact. Slack calling itself "email for teams" instead of "chat" changed what it was compared against.

Now our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. The default frame is "food delivery," and inside that frame the lunch customer compares us to dinner delivery and decides we are slow and expensive for a 40 minute break. Change the frame. Alternatives at lunch: the sandwich shop downstairs, the lunch packed at home, the office cafeteria, and skipping lunch entirely. Unique attributes: we can commit to an arrival window, we can hold an order placed at 9am for 12:15, and we know which kitchens can cook in under twelve minutes at noon. So what? A person with a fixed short break gets hot food at their desk without gambling the whole break on it. Who cares a lot? Desk-bound weekday workers whose break is short and fixed. Category: not "food delivery," which stands us next to dinner. Try "lunch that arrives before your break ends." Now the comparison is the sandwich line, and the sandwich line takes 18 minutes of standing.

Dunford gives three plays for choosing the frame. Head-to-head: own the existing category, only if you can actually win it. Big fish, small pond: subsegment the category where you win, like "CRM for investment banks." Create the game: a new category, expensive, needs missionary selling, usually the wrong answer for a small player. Framing the weekday lunch occasion as its own thing is a big fish, small pond play inside a category we already sit in.

The output is a positioning statement per audience, not a tagline: For [segment] who [struggle or context], [product] is a [category frame] that [value]. Unlike [top alternative], it [key differentiator]. Messaging comes from this, never the other way around.

The most common mistake is "our differentiator is quality, simplicity, or AI." Every competitor claims those too. This matters to a PM because the product you ship is only half the job. The frame it lands in decides whether anyone understands why it exists.

Pricing

TLDR: Price is the exchange rate on the value you create: pick the value metric first, research willingness to pay properly, anchor on the outcome, then design three tiers. Reach for it when setting or changing a price, designing plans, deciding if a feature should be paid, or when the price was copied from a competitor.

The full idea

Three people stand behind this. Patrick Campbell from ProfitWell, for value metrics and willingness-to-pay research. Madhavan Ramanujam, author of Monetizing Innovation, whose rule is price before you build. And Alex Hormozi, whose value equation is the anchor. The big idea: price is the exchange rate on the value you create. It is a product decision, not a finance afterthought, and the lever most products never test.

Start with the value metric. That is what you charge along: per seat, per thousand events, per project, or flat. A good value metric scales with the value received, so a heavy user pays more and is happy to. It is predictable by the buyer, because surprise bills churn accounts. And it aligns your growth with theirs, so your invoice reads like a receipt for their success. Per-seat is the default, not the answer. It taxes collaboration in products where value comes from more people seeing it.

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Look at it from the restaurant side. A flat monthly fee to be listed in the lunch window punishes the small cafe that gets nine orders and undercharges the busy chain that gets four hundred. Charging a percent per completed lunch order scales with what the restaurant actually gets, is predictable, and means we only grow when their noon hour fills. That is the value metric doing its job.

Next, willingness to pay, asked properly. Never ask "would you pay X?" People are polite about the future, so the answer is worthless. Use Van Westendorp's four questions: at what price is this too expensive, at what price is it expensive but worth considering, at what price is it a bargain, and at what price is it so cheap you would doubt it? Run it on fifteen or more real prospects and the band falls out. For features, "how disappointed would you be if this went away" is a better must-have detector than "how much do you like it."

Now the anchor. Hormozi's value equation: perceived value equals dream outcome times likelihood it works, divided by time to result times effort required. Price against the outcome, not your costs and not your hours. For a restaurant, the thing we are really priced against is an empty kitchen from 11:30 to 1:30 with paid staff standing in it. Raising likelihood, with proof and guarantees, and cutting time to value moves willingness to pay more than discounts ever will.

Then packaging. Three tiers, each an identity, not a random pile of features. The entry tier answers "can I start cheaply." The middle tier is where you want most buyers, so design it first. The top tier anchors the price and catches the whales. Fence tiers along the value metric plus one or two capability gates, not twenty checkmarks nobody reads. And leave money on the table at the top: a plan ten times the middle price with human service costs one paragraph to offer.

The most common mistake is copying the nearest competitor's price. That outsources your strategy to someone with different costs and different customers. As a PM, pricing is the one decision that changes who your customer is.

Three sources. April Dunford: positioning feeds messaging, never the reverse. Brian Balfour: channels are not chosen, they are earned by the shape of the product. And the working-backwards press release, which, if you have one, is the launch narrative's source of truth.

Step one: tier the launch. Not every ship is a launch. Deciding the tier up front stops you under-marketing the big thing and exhausting your audience on small ones. Tier 1 is a new product or market claim: full apparatus, narrative, customers as proof, channel plan, sales enablement, support ready. Tier 2 is a meaningful capability: announcement, docs, an in-product moment, and one channel push. Tier 3 is an improvement: changelog, an in-product note if it is discoverable, and no external push. The tier is set by customer impact and story value, not by engineering effort. A two-week feature that unlocks a new buyer is Tier 1. A two-quarter migration is Tier 3.

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Say we ship a lunch guarantee: order between 11 and 1, see a committed arrival window before you pay, and get it free if it lands late. Three weeks of work, but it opens an occasion we do not own and a buyer we have never spoken to, the person with a fixed 40 minute break. Tier 1. The four-month courier routing rewrite that made the guarantee possible, and that customers never see? Tier 3.

Step two: messaging comes from positioning. If positioning is stale, run that skill first; messaging without it is adjectives. Then, per audience (buyer, user, press if Tier 1): lead with the pain of the alternative, name the change in their words, prove it with one thing, a number, a customer, or a demo, and give one call to action. If a press release from working backwards exists, it is the master narrative. Every asset is a resize of it.

Step three: channel-product fit. Channels reward product shapes. Virality needs the product to be seen in use. Content and SEO need searchable pain. Sales needs deal sizes that pay for humans. Paid needs lifetime value that pays for acquisition cost, with proof. Pick the one or two channels the product actually supports, and write down what you are not doing. A launch plan listing seven channels is a hope plan. The lunch guarantee happens in a room full of coworkers watching food land on time at 12:20, so word of mouth inside a workplace is earned, and so is an in-product moment at 11am when the decision is actually being made. Broad paid ads are not earned.

Step four: launch day and the week after. Before: support briefed with the FAQ, rollback path named, launch metrics instrumented and checked in staging. Most launches ship with broken analytics. During: one owner watching guardrails, one thread for triage. After, and this is the part that is actually go-to-market: a day-seven review against the launch hypothesis. Adoption, activation quality, support themes. A launch without a day-seven review is a party, not a strategy.

The most common mistake is drafting messaging before positioning exists, the "we will figure out the story in the blog post" move. For a PM, this skill matters because shipping is not the same as arriving. The launch is where the product meets the people it was built for.

The idea that holds them together: a roadmap is a strategic communication device, not a delivery schedule. The moment it becomes features with dates, it stops steering and starts promising. Each framework answers a different question.

Now/Next/Later is the working default. It answers: what are we doing, in what order of certainty? The time buckets are fuzzy on purpose. Now is committed and detailed, at most about three items, because more means nothing is now. Next is shaped but can be reordered. Later is directional and cheap to change. The fuzziness is the feature: it matches how certainty really decays. Each item is a problem or an outcome, with a metric and an owner. The weakness: it says nothing about why. Pair it with your strategy kernel or it turns into a prettier backlog.

The GO roadmap answers: why does each chunk of work exist? Five rows per slice: date or timeframe, name, goal, features, metrics. The rule that gives it its name: the goal row leads and the features row serves it. Features are trimmable examples of how the goal might be met; the goal is the commitment. One goal per slice, three to five per horizon, every goal traceable to strategy, metrics chosen before features. If a negotiation is about a feature, redirect it to the goal.

Three Horizons answers: are we investing in futures at all? H1 extends and defends the core, most of the effort. H2 is emerging opportunities being scaled. H3 is cheap probes on possible futures. It is a portfolio lens, not a delivery plan. Horizons are about business maturity, not time: an H3 probe can ship next month.

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Upstream sits Pichler's Product Vision Board: one page with vision, target group, needs, product, and business goals. Every roadmap goal should trace back to it. The formats stack: Three Horizons balances the portfolio, strategy kernel picks the fights, GO states the goals, Now/Next/Later is the living view, metrics trees wire each item to a number. Moats

TLDR: A moat is a condition that gives you lasting better returns: a benefit plus a barrier that stops competitors from copying it. Reach for it when asking "what stops a competitor from copying this," or when a strategy doc claims differentiation.

The full idea

This is Hamilton Helmer, from 7 Powers. He calls a moat a "power": a condition that creates persistent differential returns. The key is that a power needs two things at once, a benefit and a barrier. A benefit without a barrier is a feature head start: temporary, and copied by anyone it hurts.

The seven powers. Scale economies: unit cost falls with volume, and the barrier is the loss a challenger must eat to match your scale. Network economies: value rises with users, and the barrier is that a small copy of a network is worthless. Counter-positioning: a new model the incumbent will not copy because it would cannibalize their core. The most available power for a small player. Switching costs: leaving hurts because of data, integrations, workflow, retraining. Earned over usage, invisible at purchase. Branding: habitual trust that commands a premium. Cornered resource: exclusive access to a patent, a dataset, a team, a supply deal. Process power: an embedded way of working that rivals can see but not copy on any useful timeline.

Apply two tests to any claimed moat. Benefit: does it materially improve cash flow or customer value? Barrier: what specifically prevents a competent, funded competitor from copying it within the payback window? "We move faster" and "our UX is better" fail the second test. That is operating excellence, which Helmer rules out as power: necessary, insufficient, and imitable.

Stage matters too. Counter-positioning and cornered resource are available at the start. Network and switching costs compound during takeoff. Scale, brand, and process power arrive at maturity. The right question is "which power is this bet positioned to earn, and does the roadmap feed it?"

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Someone says "our moat is the best app experience." Test two fails immediately. Now look for a real power. Lunch is not dinner: it is one narrow rush, in a few dense office districts, where the only thing that matters is whether food lands before the break ends. A bet: buy exclusive reserved noon prep slots from the two fastest kitchens in each office district, paying for the slot whether it fills or not. That is a cornered resource. Benefit: we can promise an arrival time nobody else can promise, because the kitchen is not queueing our order behind forty others. Barrier: there is only one noon, and the slot is already sold. The barrier becomes real the day the fastest kitchens in a district are all booked. What does a rational competitor do in the meantime? Pay those kitchens more to break the deal. So the roadmap has to feed the power: make the noon-hour tools good enough that a kitchen would not leave even for money.

For any bet, name one intended power, not a menu, with the benefit and barrier in one sentence each. If no power is nameable, the bet may still be right, but it is a race, and you should price and pace it like one. The most common mistake is "our moat is AI." A supplier's product is nobody's cornered resource. This matters to a PM because "defensible" is the word that separates a feature from a business.

Pre-mortem

TLDR: A pre-mortem assumes the project already failed, asks everyone to write why, then sorts the causes and assigns owners to the real threats. Reach for it before a launch, a big bet, a hire, a migration, or any decision that is expensive to reverse.

The full idea

This comes from Gary Klein's research on prospective hindsight, and it is practiced today by Shreyas Doshi. Klein found that imagining an outcome as already certain improves how well people identify its causes, by about 30%. The trick is grammatical. Not "what could go wrong?" That question invites optimism and politeness. Instead: "It is six months later and this failed. What happened?" That question invites the truth everyone was sitting on.

The method has five steps. One, set the scene. "It is [a date after launch]. [Project] failed, clearly and publicly. Write the story of what happened." Everyone writes silently and independently first. The whole value is harvesting private doubts before the room converges on one opinion.

Two, collect the causes and sort them into three buckets, which is Doshi's taxonomy. Tigers: real threats that will hurt you if you do not address them. Paper tigers: things that look scary but are actually fine, and you consciously set them aside. Elephants: the thing in the room nobody is saying. The pre-mortem exists to give elephants a speaking slot.

Three, score the tigers by likelihood times damage, and take the top three to five. Four, assign de-risking actions. Each tiger gets an owner and a dated action that either prevents it or detects it early: a canary metric, a checkpoint, a kill criterion. An unowned tiger is a decision to accept the damage. Five, log it. Causes and mitigations go into memory, so that if a post-mortem ever happens it can be compared against the pre-mortem. That comparison is how a team's risk instincts get better over time.

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. We are about to launch a lunch guarantee in three office districts: order between 11 and 1, see a committed arrival window before you pay, and get it free if it lands late. Set the scene: "It is February. The lunch guarantee launched in November and is being quietly switched off. What happened?" Silent writing produces: "Kitchens could not hold the noon slot on a busy day, so a third of the guarantees paid out." "Couriers got stuck in tower lobbies and the clock kept running." "Nobody believed a desk worker would trust a promise after one late lunch, but the sponsor had already announced the number." Sort them. The first two are tigers. A rival announcing a similar promise is a paper tiger. The last one is an elephant, and it only appeared because people wrote privately. Owners: the ops lead tests noon slots with ten kitchens by a date; the delivery lead times ten tower deliveries door to desk by a date; the PM runs five interviews with people who were once burned by a late lunch, before launch, as a kill criterion.

Why does this work when "any risks?" does not? Asking for risks at a kickoff turns doubters into traitors. The pre-mortem makes doubting the assignment, and the most junior person's elephant carries the same weight as the sponsor's tiger. It is psychological safety by procedure.

The most common mistake is running it after the commitment is irreversible. That is a post-mortem with extra steps. This matters to a PM because you are the person who will be asked "did we see this coming?" and the pre-mortem is your written proof that you did, and what you did about it.

Working Backwards

TLDR: Write the press release and the FAQ before you build anything, so you find out whether the product is compelling while it still costs only a rewrite. Reach for it when kicking off a significant initiative, forcing clarity on a fuzzy vision, or replacing a 40-slide kickoff deck.

The full idea

This is Amazon's PR/FAQ process, described by Colin Bryar and Bill Carr in Working Backwards. Start from the customer's moment of launch and reason backwards. If the press release is not compelling, the product will not be either, and you just saved two quarters finding out.

The press release is one page, in customer language only. Six parts. A heading: the product name and the customer it serves. A subheading: one sentence with the benefit, not the mechanism. A problem paragraph: the customer's pain, written so the customer would say "yes, that is me." Write this one first and hardest. A solution paragraph: what they can now do, in plain words. If it needs jargon to sound good, it is not good yet. A customer quote: invented but plausible. If every quote sounds like marketing, the value is not concrete enough. And how to start: the first run in two sentences. Rules: no superlatives, no internal language, no feature lists.

The FAQ is where the honesty lives, in two halves. Customer FAQs are the skeptical buyer's questions: price, migration, what happens to my data, why not the alternative. Internal FAQs are the hard questions leadership will ask: unit economics, why now, why us, biggest technical risk, what we are not doing, what kills this. An internal FAQ with no uncomfortable question in it means the team is hiding the body. Every one of the four risks should appear as a question with a real answer or an honest "we do not know yet, here is the test."

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Heading: "Noon: lunch that beats your break." Subheading: "See one arrival time you can trust before you pay, or the lunch is on us." Problem paragraph: "At 11:40 every weekday, Priya has 40 minutes and no plan. The app says her food lands somewhere between 12:35 and 1:05. Her break ends at 12:50. She closes the app and stands in the sandwich line for 18 minutes instead, holding her phone." Solution: "Priya opens the app at 11:40 and sees one time, 12:18, from a kitchen that can hold that slot. She pays. It arrives at 12:16." Quote: "I stopped ordering lunch because I could not risk it. Now I know when it lands," said Priya, who works in a tower downtown. Internal FAQ: "What does a missed window cost us per order, and how many can we afford?" "What share of kitchens can actually hold a noon slot on a busy day?" If you cannot answer those, you learned something before writing code.

How it is used: written by the owner, read silently in the room, not presented, because reading cannot be carried by charisma. Then attacked. Each round of "would a customer care about this sentence?" is discovery at the cost of a rewrite. The version that survives becomes the north-star document, and every scope cut is tested against "does the press release still hold?"

The most common mistake is a press release written after the roadmap commitment. That is backwards working backwards. This matters to a PM because it is the cheapest way to find out your idea is boring, and it forces every stakeholder to agree on what "done" looks like before anyone argues about how.

Briefs and Cases

TLDR: There is a ladder of documents below the PRD, from a half-page problem brief up to a business case, and each one is priced by the decision it serves. Reach for it when work needs a document but a PRD is too heavy, or when someone asks for "a quick business case" for something nobody has examined.

The full idea

This skill draws on Marty Cagan's opportunity assessment, Ryan Singer's Shape Up pitch with its idea of appetite, and the Amazon working-backwards discipline, whose PR/FAQ sits at the top of this ladder. The principle: documents are decision instruments, priced by the decision they serve. A two-week experiment documented like a capital request is theater. A quarter-long bet approved on a Slack message is gambling.

The ladder, bottom to top. Rung one, the problem brief, half a page. Decision: is this worth anyone's discovery time? Four parts: the struggling moment with quoted evidence, who has it and how often, what they do today, and why now. No solution content at all. Output: pursue or park.

Rung two, Cagan's opportunity assessment, one page. Decision: should a team spend discovery on this? Answer plainly: what problem, for whom, how big (one honest multiplication), what alternatives exist, why are we suited to win, why now, how will we measure success, what factors are critical, and a go or no-go. If three of eight answers are "we do not know," the output is a discovery plan, not a verdict. Say so instead of decorating the unknowns.

Rung three, the product brief or one-pager. Decision: alignment before detail. The PRD's trailer: problem, target user, the bet in one sentence, success as a number, what is out, open questions with owners. Its job is to get people disagreeing now, at one page, not at page nine of the PRD.

Rung four, the Shape Up pitch. Decision: should a team get a fixed appetite of time? Five parts: the problem with its raw story, the appetite ("worth six weeks, no more" instead of "how long will it take?"), a fat-marker solution, rabbit holes, and no-gos. Appetite is the strongest scope-control device on this ladder.

Rung five, the business case, two to three pages, only when real money moves. It needs a do-nothing baseline with its cost made explicit, build and run costs, benefits traced to an owned metric, risks, sensitivity, and kill criteria with a review date.

Take our case. Uber Eats is growing overall, but weekday lunch orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. Someone says "write me a business case for fixing lunch." Ask what decision it serves. If it is "should one squad spend two weeks on discovery," that is a problem brief: "When my break starts I cannot tell if the food will beat the clock, so I go downstairs instead," quoted from three interviews, the lunch window is 30% below dinner and holds most weekday demand, people use the sandwich shop and the packed lunch today, and the noon rush is the only slot where our kitchens sit idle. Half a page. If it is "should we pay kitchens to hold reserved noon capacity across three districts," then yes, a business case, with the do-nothing cost spelled out.

The most common mistake is every initiative getting the same document regardless of size. That is ceremony, not judgment. This matters to a PM because matching the document to the decision's blast radius is how you earn the right to skip the paperwork when it does not matter and insist on it when it does.

UX Writing

TLDR: Writing the words a user reads in the product: labels, buttons, errors, empty states, confirmations, onboarding. Reach for it when drafting or reviewing any in-product copy, or the moment the interface says "An error occurred."

The full idea

This skill is grounded in Torrey Podmajersky's book Strategic Writing for UX. Her starting point is worth writing down: words are the interface's cheapest, most-shipped, least-reviewed component. Every string does a job. It helps the user, and it carries the brand's voice, in that order.

Six rules do most of the work. One, buttons say what happens. "Order for 12:00," "Remove 2 items," "Send to the group." Never "OK / Cancel" on a destructive confirm. "Delete / Keep" makes the choice clear without reading the paragraph above, which nobody read. Two, write from the user's side of the screen. They manage notifications, not webhook config. Three, front-load. The first two words carry the meaning because users scan the left edge. "Payment failed: card expired," not "There was a problem processing your payment because the card on file appears to have expired." Four, errors say what happened, why, and what to do. No apologizing paragraphs, no blame, no error code as the only content, and preserve the user's work. Five, one idea per string. If a tooltip needs three sentences, the design needs a change. Six, consistency is comprehension. One name per concept everywhere. If it is "cart" in the nav, "basket" on the button, and "order" in the email, the user has three things to reconcile. Keep a terms list and enforce it in critique.

Then voice. Onboarding can be warm. Errors are calm and plain. A cute 404 page is fine. A cute "your lunch will be late" is contempt. Destructive confirmations are sober. Success states can celebrate briefly. A voice that does not change with the stakes is not a voice, it is a font.

Here is the case. Uber Eats grows overall, but weekday orders from 11:30am to 1:30pm run 30% below dinner. Call it the lunch gap. Now read the words in that window. The pre-order button says "Continue." Continue to what? Change it to "Order for 12:00, $18.40." The 12:00 promise is written as "ETA 12:00 (est.)" which is three ways of hedging in six characters, and hedging is exactly what a person with a 12:30 meeting cannot use. The group order screen says "Participants: 3/5 submitted," which is a database report, not a sentence a coworker says. "Waiting on Sam and Priya" is the same fact and does the job. When the driver is running late the app says "Delivery exception 4102." What happened, why, what to do: "Running late. Now arriving 12:15. Cancel for a full refund." And the empty lunch cart says "Your cart is empty." That describes the emptiness. "Pick something that arrives by 12:00" describes the way out and names the thing the user actually wants.

The method for checking all of this is the read-aloud test. Read the flow's strings out loud in sequence as a conversation. Screen says X, user does Y, screen says Z. Anywhere you wince, cut. Anywhere a normal person would answer "but what does that mean?", rewrite. The interface is a dialogue where you scripted both sides in advance. Make your side coherent.

The most common mistake is "An error occurred," which is the string equivalent of a shrug. Why does a PM care? Because copy ships without review more than any other part of the product, and the error state is where you earn or lose trust at the highest exchange rate. On a lunch order, that exchange rate is brutal: a person who gets a vague message at 12:10 does not come back at 11:45 tomorrow. You will write half these strings yourself in tickets. Write them well.

Information Architecture

TLDR: Structuring navigation, labels, and content so users can find things: card sorting to learn their mental model, tree testing to check the structure. Reach for it when designing or reorganizing navigation, naming sections, deciding where a feature lives, or when users keep "not finding" things that exist.

The full idea

Information architecture, or IA, comes from Rosenfeld and Morville's book Information Architecture, known as the polar bear book because of its cover, and from Donna Spencer's practical work on card sorting. Here is the definition I want you to keep: IA is the argument the product makes about how the user's world is organized. When users cannot find things, the taxonomy is wrong. Not the users, and usually not the visual design either.

The core diagnosis is one question: whose model is it? Most broken IA is the org chart or the database schema leaking into the navigation. Sections named for the teams that built them. Splits where the backend splits. The user's mental model groups by their task and their vocabulary. So every IA job starts here: is this structure organized by how we build it or by how they use it?

Now the methods, matched to the question. Open card sort: users group your content their way and name the groups. Use it to discover the mental model before you design a structure. The group names users invent are label gold. Closed card sort: your categories, their sorting. Use it to validate a proposed structure or place new items into it. Tree test: users find X in a text-only hierarchy with no visual design to help. A failure is unambiguous: the label or the location is wrong. Run it before UI exists and again after big changes. Under about 70 percent first-click success, the argument is not landing. And first-click testing on mocks, from Bob Bailey's research: get the first click right and task success roughly doubles.

Labels are the IA's interface. User vocabulary over internal. What users type into search is their label. One concept, one name. Scent over cleverness: a label must predict what is behind it. "Workspace Hub" predicts nothing.

Here is the case. Uber Eats grows overall, but weekday orders from 11:30am to 1:30pm run 30% below dinner. Call it the lunch gap. Look at what the app offers someone opening it at 11:45 with four minutes to decide. The bottom nav says Home, Marketplace, Activity, Wallet, More. There is no lunch anywhere in it. The one thing that would close the gap fastest, ordering ahead for a 12:00 arrival, is buried three taps down inside a restaurant page as "Schedule." An office worker looking for it does not think "schedule." They think "get it here by noon." An open card sort with ten office workers produces groups they call Order for Noon, Lunch Near Work, Split With The Team, and My Usual. Nobody says Marketplace, and nobody says Schedule. A tree test on a structure built from those names gets 79 percent first-click on "order lunch so it arrives at 12:00." The old structure gets 34. That is a finding you can ship.

Structure heuristics. Breadth beats depth at equal scent, because each extra level sheds users. But forty items at one level is a search problem pretending to be navigation. Things can live in two places when tasks arrive from two directions, and lunch is exactly that case: a person may arrive from the clock or from a craving. And search is IA too: the no-results page, synonyms, and top-query tuning are part of the architecture. If someone searches "lunch" and gets nothing, the taxonomy just told them the product has no opinion about the middle of their day.

Visual Hierarchy

TLDR: Directing attention with layout, type, spacing, and contrast so the user knows what to look at first and what to ignore. Reach for it when a screen feels cluttered or flat, when everything looks equally important, or when reviewing visual quality in critique.

The full idea

Visual hierarchy is the design answering a question before the user asks it: "what should I look at first, and what can I ignore?" The grounding here is the Gestalt principles from Max Wertheimer, typographic scale practice from Robert Bringhurst as passed down through every good design system, and the working heuristics made popular by Refactoring UI by Adam Wathan and Steve Schoger. The one-line summary: a screen where everything is emphasized has no emphasis.

Four Gestalt principles carry most of the load. Proximity: things close together read as related. This is the most violated principle in practice. A label equidistant from two fields belongs to neither. Padding inside a card larger than the gap between cards dissolves the cards. Space is meaning, so spend it on purpose. Similarity: same style implies same behavior. If blue text is sometimes a link and sometimes just emphasis, both uses are broken. Common region: enclosure groups things. Which is why the fix for clutter is rarely more boxes. Try whitespace first. Borders are the grouping tool of last resort. Continuity and alignment: the eye travels along lines. Every misalignment is a speed bump. A strict grid is invisible until it breaks, and then it is the only thing you can see.

Type does the heavy lifting. Use a deliberate scale: one ratio, five to seven sizes, from the system's tokens. And size is only one lever. Weight, color contrast, and spacing rank content with less noise than size alone. Secondary text should be quieter, not smaller. Tiny grey text fails hierarchy and accessibility at once. Line length around 45 to 75 characters.

Two tests. The squint test: blur the mock. What survives is the hierarchy. Is it the right thing? The one-bold-move rule: one unmistakable primary action per screen. Two primary buttons is a decision the design refused to make and exported to the user. Emphasis is a budget, and it is zero-sum.

Here is the case. Uber Eats grows overall, but weekday orders from 11:30am to 1:30pm run 30% below dinner. Call it the lunch gap. Look at the lunch browse screen at 11:45 and squint. What pops? An "Add" button on every card, all in brand orange, plus "Start group order," plus "Schedule," all primary. Meanwhile the one thing a person with a 12:30 meeting needs, whether this food can be at their desk by 12:00, is set in the same 14-point grey as the cuisine tag and the rating. The screen is shouting the things that do not decide anything and whispering the thing that does. Fix: one primary action, the rest become quiet outlines; the arrival time moves to the top of each card and gets weight, not size; the list groups by "arrives by 12:00" and "arrives after 12:15" with spacing instead of eleven dividers. Nothing new was added. The budget was spent differently, and now the screen is about the clock, which is what lunch is about.

The most common mistake is primary buttons everywhere, the "everything is important" tell. Why a PM cares: you will be asked to "make the pre-order option more visible," and the honest answer is often that the screen already spent its boldness. Knowing that lets you ask for a real trade instead of a louder button.

Accessibility Audit

TLDR: A practical sweep of a design against WCAG 2.2, ordered by how much harm each failure does: keyboard, contrast, color, targets, semantics, motion, cognition. Reach for it in critique, before handoff, when reviewing a design system component, or the moment someone says accessibility can be "phase 2."

The full idea

Accessibility has a reputation as a compliance chore. That reputation is wrong. The grounding is WCAG 2.2, the web accessibility standard, with level AA as the floor. The second source is Microsoft's Inclusive Design work, which gives the idea that makes this click: disability is a mismatch between a person and a design, and it is situational. One arm, an injured arm, or an arm holding a phone to your ear while you walk back to your desk at 11:50: same need. Accessibility findings are usability findings with higher stakes, and fixing them almost always helps everyone.

The method is a sweep in a fixed order, by harm. First, keyboard. Every interactive element must be reachable and usable by keyboard, in an order that follows the visual logic, with focus visible at all times and never hidden behind a sticky header. If the designer cannot Tab through the flow in their head, you found your first blocker. Second, contrast: 4.5 to 1 for body text, 3 to 1 for large text and UI components. Light grey on white is not a brand choice. It is an exclusion.

Third, never color alone. Every state needs a second channel: an icon, text, weight, or pattern. The test: imagine the screen in grayscale. Does the information survive? Fourth, targets and gestures: 24 by 24 pixel minimum, every swipe has a tap alternative, nothing depends on hover because touch exists. Fifth, semantics: real headings, labels tied to inputs, buttons that are buttons and not clickable divs, alt text that says what the image does. Sixth, motion and time: respect reduced motion, nothing flashes more than three times a second, no timeout without warning. Seventh, cognitive load: plain labels, controls in the same place on every page, errors that say what to do, no retyping what was just entered.

Take Uber Eats at lunch. Overall growth is strong, but weekday orders between 11:30am and 1:30pm run 30% below dinner. Call that the lunch gap. Now sweep the lunch experience. The 12:00 delivery promise is shown by turning the slot green when it is still available and grey when it is gone. Color alone, a major finding. The "Add for the table" plus button on the group order screen is 18 pixels wide, and half the office is tapping it on a phone at a standing desk. The office address field on the pre-order flow uses placeholder text as its only label. The delivery time picker is a swipe-only wheel with no tap alternative, so a person with a tremor cannot land on 12:00. And a keyboard user on a work laptop never reached checkout because the sticky lunch cart bar hides the focus ring on the address field. That one is the blocker, and it lands on exactly the users you need in the 11:30 to 1:30 window.

The most common mistake is treating accessibility as a final-sprint checklist. The skill is blunt about this: audit the design system once at the component level and inherit the fix everywhere. If you are auditing every screen separately, the system is leaking. Also, "it passes automated checks" means little: tools catch about 30 percent.

Why does a PM care? Because you set the definition of done, and "most users have a mouse" is the accessibility version of "users will figure it out." A blocker for keyboard users is a blocker, full stop. Severity uses the same scale as heuristic evaluation: blocker, major, minor, polish. You will be the person who decides whether it ships.

Design Metrics

TLDR: Measuring design with Google's HEART framework and the Goals, Signals, Metrics method, then hanging those numbers on the product's metric tree. Reach for it when a design team cannot show impact, when choosing metrics for a redesign, or when "the design is better" needs a number.

The full idea

This skill comes from Google's HEART framework, published by Kerry Rodden, Hilary Hutchinson, and Xin Fu, together with the Goals, Signals, Metrics method that makes it usable in practice. Design has a chronic credibility problem: it measures inputs, like screens shipped and components built, while the organization measures outcomes. HEART is the translation layer between the two.

HEART is five rows. Happiness: attitude, measured as satisfaction or perceived ease at the moment of use. Annual NPS is weather, not feedback. Engagement: voluntary depth and frequency of use. Only meaningful where more use means more value. A support portal that optimizes engagement is optimizing failure. Adoption: new users or accounts taking up the feature. Retention: do they come back. This is the metric most redesigns quietly damage. Task success: effectiveness, efficiency, and error rate. Completion percent, time on task, error recovery. This is the most design-attributable row in the whole framework.

The rule is to pick two or three rows that match the design's intent. A redesign meant to reduce support load is Task success plus Happiness, not Engagement. Choosing all five is choosing none.

Then the discipline that stops metric-grabbing: Goals, Signals, Metrics. State the goal in experience terms. Choose the signals that would show it. Then define the metric precisely. Run it in reverse to audit a dashboard: any metric you cannot trace back to a goal is dashboard lint.

Here is the case. Uber Eats grows overall, but weekday orders between 11:30am and 1:30pm run 30% below dinner. Call it the lunch gap. The team is redesigning the lunch browse experience at 11:45, because an office worker has about four minutes to decide and the current browse asks them to scroll through the same dinner-shaped list. The intent is that a hungry person with a 12:30 meeting picks food fast and trusts it will arrive by 12:00. So the rows are Task success and Happiness. Goal: an office worker opening the app at 11:45 places an order in under two minutes with confidence in the arrival time. Signals: fewer restaurant pages opened before ordering, fewer sessions in the window that end without an order, fewer changes to the delivery slot after it is chosen. Metrics: median time from app open to order placed between 11:30 and 1:30; percent of lunch-window sessions that end in an order; a one-question "did you get what you needed in time?" right after the 12:00 delivery. Before the redesign, 31 percent of lunch-window sessions ended in an order. After, 44. That second number means nothing alone. Against the baseline it is a career.

The most important rule: connect to the tree or float forever. Every design metric should hang off the product's metric tree. Lunch browse task success feeds lunch-window order conversion, which feeds weekday orders in the 11:30 to 1:30 window, which feeds the north star. A design team whose metrics live in a separate universe will lose every prioritization argument to a team whose metrics are the tree.

The most common mistake is shipping a redesign with no baseline captured. The before is now unmeasurable and the debate is unwinnable. The second is choosing Engagement because it is the one that always goes up. Watch that one here: more time browsing at lunch is a failure, not a win. Why a PM cares: you are the person who decides what goes on the dashboard, and you will be asked "did the redesign work?" The only honest answer is a before-and-after on the same task, tied to a metric the business already cares about.

Design System Ops

TLDR: Running a design system as a product: deciding what earns a component, designing component APIs, choosing a team model, and measuring adoption. Reach for it when building or governing a system, deciding whether something becomes a component, or when the system exists but teams route around it.

The full idea

The grounding for this skill is Nathan Curtis, who wrote the standard work on design system team models and component lifecycle, and Brad Frost, whose atomic design gives us a vocabulary of atoms, molecules, and organisms. The central claim: a design system is a product whose customers are product teams. And it fails the way products fail: built without discovery, shipped without adoption, maintained without a roadmap.

First question: what earns componentization? Not everything used twice. The bar is three parts. Used, or credibly about to be used, by three or more teams. A stable job, meaning the pattern's purpose will not churn monthly. And inconsistency costs something: user confusion, accessibility risk, or rebuild waste. Below that bar, publish it as a pattern, a documented recipe with no code contract. Promoting one team's habit to a system component freezes their local decision into everyone's constraint.

Second, component API design. A component's props are its contract, and the contract encodes policy. Expose intent, like variant="destructive", not styling escape hatches like color="#D33", or the system becomes a longer way to write CSS. Every component ships with all five states designed, accessibility audited once at the component, and guidance that includes when not to use it.

Third, the team model, from Curtis. Solitary: one team owns it, others consume. Fast, then a bottleneck, then a resentment. Centralized: a dedicated system team, sustainable if funded like a product team with a roadmap and research on its users. Federated: contributors from product teams with central stewardship. Best adoption, but it needs real governance or it becomes a junk drawer with a logo. Most orgs should run centralized with federated contribution. Most actually run solitary by accident. Contribution needs a paved road from "my team needs a variant" to "it's in the system," with SLAs. When contributing is slower than forking, teams fork, rationally. Every detached instance is a vote about your process, not their discipline.

Fourth, adoption is the metric. Percent of new screens on system components. Detach rate per component: high detach means the component's API is wrong, not the teams. Version lag across consumers. Mandates create malicious compliance. And deprecation is part of ops: announced, with a migration path and a removal date.

Design Canvases

TLDR: One-page tools that turn confidence into testable hypotheses before anything gets built: the Lean UX Canvas, the Empathy Map, the Opportunity Canvas, and the Test Card. Reach for them when kicking off a design initiative, converting a feature request into hypotheses, aligning a team before pixels, or when work is starting from a solution instead of a problem.

The full idea

Four tools, four authors. Jeff Gothelf's Lean UX Canvas, version 2, from Lean UX. Dave Gray's Empathy Map from XPLANE. Jeff Patton's Opportunity Canvas. And Strategyzer's Test Card. Business canvases model the business. These model the work about to be designed. Their shared job: turn confidence into hypotheses before the hypotheses turn into shipped code.

The engine is the Lean UX Canvas. Eight boxes, filled in order. One, the business problem, in outcome terms, without the solution baked in: "weekday lunch orders run 30% below dinner," not "we need a pre-order button." Two, business outcomes: the metric that moves. Three, users, specifically. Proto-personas are fine, labeled as guesses. Four, user outcomes and benefits: what the user is trying to achieve and feel. Five, solutions. Now ideas are allowed, plural, sketched cheaply. Six, hypotheses: "We believe [business outcome] will be achieved if [user] attains [user outcome] with [solution]." Missing any part and it is a hope. Seven, the most important thing to learn first: the riskiest assumption inside the strongest hypothesis. Eight, the least work to learn it: a test, this week, sized in days. The canvas is not done until something is scheduled. The ethic: boxes one through four before box five. A team that starts at box five is decorating a decision.

Run it on the case. Uber Eats grows overall, but weekday orders between 11:30am and 1:30pm are 30% below dinner. Call that the lunch gap. Business problem, the lunch gap itself, stated as a number and a window, not as a missing feature. Business outcome, weekday orders in that window. Users, desk-bound office workers with a fixed break and a meeting on either side of it. User outcome, food on the desk by 12:00 without spending the 11:45 to 12:00 stretch worrying about it. Solution idea, a pre-order flow that locks a 12:00 delivery slot in the morning. Hypothesis: we believe weekday 11:30 to 1:30 orders will rise if office workers get a guaranteed 12:00 arrival by ordering before 10am. Riskiest assumption: that they will decide what to eat hours before they are hungry. Least work to learn it: ask twenty office workers what they ate last Tuesday and when they decided. One day, no code.

The Empathy Map sits before personas. Six zones around a specific user in a specific situation: says, thinks, does, feels, pains, gains. Says must be verbatims. Where does contradicts says, behavior wins. Run it cold and mark every sticky that is a guess. The guess density is the finding. An empathy map built from no user contact is a séance.

The Opportunity Canvas is Patton's middle altitude: bigger than a story, smaller than a business model. Nine boxes around one feature, including the solution today, the workaround, which is the real competitor. For the lunch gap the workaround is the sandwich place downstairs, and it is a very good competitor: it is fast, it is certain, and it needs no app. Its spine: user value and business value must both be nameable. Use it to triage which of five candidate lunch features deserves a PRD at all.

The Test Card is the hypothesis's receipt. Four lines: we believe that, to verify we will, and measure, we are right if. That threshold is set in advance. Pair it with a Learning Card afterward and log both.

The most common mistake is the canvas workshop that produces beautiful walls and zero scheduled tests. Why a PM cares: you will receive feature requests as solutions every week. These are the one-page tools for walking them back to a problem.

Crit Facilitation

TLDR: Running design critique sessions that make the work better while it is still cheap to change: framing, feedback discipline, and decision capture. Reach for it when setting up or fixing a crit ritual, prepping to present work, or when crits have turned into either bloodsport or applause.

The full idea

Three sources ground this skill. Ed Catmull's Braintrust rules from Creativity, Inc., the book about how Pixar reviews its films. Lara Hogan's feedback equation. And the Feldman critique structure, the describe, analyze, interpret, judge sequence from art education. A crit exists to make the work better while it is still cheap to change. Not to approve it, not to display it, and not to perform seniority. The two failure modes are the same failure: feedback aimed at people, which is bloodsport, or at nobody, which is applause.

Start with the Braintrust rules, enforced. One: the work gets notes, the person does not need defending. Say it out loud every session until it is culture. Two: no authority in the room. The Braintrust cannot mandate. The designer owns what to do with every note. The moment notes become orders, presenters start bringing safe work, and the crit is dead a quarter before anyone notices. Three: problems, not prescriptions. "I lost track of whether my order would arrive by 12:00" is a note. "Make the delivery time sticky" is a solution wearing a note's clothes. Solutions are welcome as illustrations of the problem, never as the requirement.

Structure beats vibes. The presenter frames first, two minutes, written in advance: the problem, the stage, and what feedback is needed. Stage matters because feedback calibrated to the wrong stage is noise. Visual polish notes on a concept sketch waste the room. Then silent looking time before anyone speaks, because first-reaction theater rewards the fastest talker, not the best eye. Then clarifying questions, then critique. Half of most crit arguments are two people describing different understandings of the design. The facilitator is traffic, not judge: pulls in the quiet, parks the rabbit holes. Close with capture: what the designer heard, what they will explore, what is parked, logged so the same debate does not rerun next week.

Giving the note uses Hogan's equation. Observation, plus impact, plus a question or request. Here is the case. Uber Eats grows overall, but weekday orders from 11:30am to 1:30pm run 30% below dinner. Call it the lunch gap, and say the room is looking at the pre-order screen meant to close it. A note: "The 12:00 delivery promise sits below the fold on a standard phone," observation. "I'd expect an office worker with a 12:30 meeting to scroll past it and not trust the timing at all," impact. "What led to putting the tip selector above it?" question. That last part is load-bearing. It presumes intent. Half the time there was a reason, like a legal requirement on tip disclosure. A constraint you did not know beats an opinion you did.

Compare the bad version: "I don't love the pre-order screen, the time thing feels buried, just move it up." A feeling, no impact, and an order. The designer now either obeys or resists. Neither makes the work better.

The most common mistake is the most senior voice speaking first. The anchor is set, dissent is priced out. Why a PM cares: you are often that senior voice, and you will run these rooms. Your job is traffic, not verdict. Bring your prescription as a question.

Stakeholder Comms

TLDR: how to write to a specific named person: status updates, escalations, asks, and bad news. Reach for it whenever you draft anything one real person will read, in email, Slack, a doc comment, or an exec update.

The full idea

A lot of a PM's job is writing to people who can say yes or no. This skill pulls from three sources. Chris Voss, the former FBI negotiator, taught tactical empathy: the person who feels heard is the person who concedes most. Robert Cialdini wrote about pre-suasion: the frame you set before the ask matters more than the ask. And Kim Scott's radical candor says being direct and caring at the same time is the respectful combination.

Before you draft anything, load stakeholders.md for the recipient. If the person is not in it, ask two questions: what do they care about, and how do they like to be told things. Then add the answer to memory so next time you already know.

The method has five moves. One, their frame first. Open with the thing they care about, not the thing you want. One sentence that proves you know their world before you enter it. Two, BLUF, bottom line up front. The point lands in the first two lines, whether it is status, an ask, or bad news. Three, the bad news protocol: state it plainly with no cushioning adjectives, give the cause in one sentence, give the plan in two, and give the date they will hear from you next. Kim Scott's rule applies: softening the message is for your comfort, not theirs. Four, the ask is singular and answerable. "Can you approve the noon courier surge budget by Friday" works. "Thoughts?" does not. Five, match their channel and length from memory. A CFO who reads bullets gets bullets.

Here is the case. Uber Eats grows overall, but weekday orders from 11:30am to 1:30pm run 30% below dinner. Call it the lunch gap. Your pre-order flow, the one that promises a 12:00 arrival, slipped two weeks. Your stakeholder is Dana, the head of operations, and memory says she cares about courier utilization in the noon peak and reads Slack, not email, and hates long messages. The draft opens with her frame: "Dana, this affects how many couriers you need standing by at noon." Then the bad news, plain: "The 12:00 pre-order slot slips from Sept 2 to Sept 16." Cause in one sentence: "Kitchens cannot hold a hard noon slot, so we are switching to a 15-minute arrival window." Plan in two: "We are shipping the window version first so you can start staffing against real noon demand this month. The hard slot comes back only if the data says people need it." Next touch: "I will update you Thursday." One ask: "Can you tell me which three neighbourhoods you want the noon window turned on in first?" Five lines, in Slack.

The most common mistake is adjective inflation. "Great progress on lunch" tells Dana nothing. "Lunch-window orders up from 31 to 36 percent of sessions, target is 45" tells her everything. Passive voice like "it was decided" hides the person, and readers notice.

Why it matters: a PM's output is mostly decisions other people make. Writing that gets a clear yes or no fast, and keeps trust when the news is bad, is the skill that keeps you in the room.

Calibration

TLDR: record every prediction your product work makes (risk ratings, bet hypotheses, go/no-go calls, appetite estimates), score it on schedule, and build a bias profile so future judgments self-correct. Reach for it whenever a workflow produces a rating, forecast, or verdict, and whenever one comes due for scoring.

The full idea

This skill comes from Philip Tetlock's book Superforecasting. His finding: forecasting skill is trainable, but only with a feedback loop that almost nobody closes. You have to record the prediction precisely, score it on schedule, and study your misses by type. Product teams predict constantly: every risk rating, every bet, every "six weeks". We score almost none of them. So the same optimism bias ships the same surprises forever.

Rule one: predictions get recorded at birth. The moment a workflow produces a judgment, it writes one scoreable line to calibration.md. Hindsight launders everything. A scoreable line has four parts: the date, the source artifact, the claim stated so it can be proven wrong with a probability or rating, and the date it gets scored. Vague claims get sharpened or rejected at write time. "Lunch pre-orders should do well" is not scoreable. "At least 40 percent of weekday lunch-window sessions end in an order within 14 days of launch" is. Writing the sharp version improves the judgment by itself.

Rule two: scoring is scheduled, not remembered. Every prediction carries its score date, and /brief-me lists the due ones alongside your due work, whether or not you feel like grading yourself. Scoring is one line: right, wrong, or partial, plus a one-sentence cause.

Rule three: the bias profile is the payoff. Quarterly, or when you run /calibrate report, you compute from the ledger, by prediction type: the hit rate per type, the direction of the miss (optimistic or pessimistic, and by how much), and the expensive class, meaning which kind of miss cost the most. The profile goes at the top of calibration.md, and every judgment-producing skill reads it first. If the profile says your feasibility-LOW ratings fail 40 percent of the time, the next time four-risks is about to rate something feasibility LOW it says so and rates it MEDIUM unless there is specific evidence.

Here is the case. Uber Eats grows overall, but weekday orders from 11:30am to 1:30pm run 30% below dinner. Call it the lunch gap. In March the team runs four-risks on the 12:00 pre-order slot and rates feasibility LOW, meaning "this will not slip the schedule by more than two weeks." That line goes in the ledger with a June score date. In June, /brief-me flags it. The slot slipped five weeks because kitchens would not commit to holding a hard noon time on a weekday. Score: wrong, optimistic, cause: assumed kitchen capacity we never checked. Three more like it over the year, and the profile says "feasibility ratings on anything that needs a restaurant to change its own operations run optimistic." The next lunch spec that leans on kitchen behaviour gets a warning before anyone writes a date.

The most common mistake is recording predictions after the outcome is known. That is a diary, not a ledger. The second is only scoring the wins, which turns the ledger into a trophy case. Misses are the training data.

Why it matters: skills are copyable. Anyone can rebuild a framework library in a weekend. A year of scored predictions about how your specific org is wrong cannot be bought, copied, or cold-started. The skill calls this a cornered resource, in Hamilton Helmer's sense.

Memory Protocol

TLDR: the rules for how every Product OS workflow reads and writes the flat markdown files in .product-os/memory/. Reach for it before you ask the user anything a previous session already answered.

The full idea

Most AI tools have amnesia. You explain your company, get a decent answer, close the window, and tomorrow you explain your company again. The memory protocol is the part of Product OS that ends that. It is a house rule written into the system itself: all durable state lives in .product-os/memory/ as plain markdown files a human can open and edit. If you cannot grep it, the system failed.

The protocol has six rules. Rule one is the big one: read before asking. Every workflow loads profile.md and product-context.md first, always. If the answer to a question could be in memory, you check memory. The skill calls asking what memory already answers the one unforgivable failure. Rule two: load narrowly. Pull only the extra files the task needs. Never dump the whole directory into context. Rule three: missing is not blank slate. If a file you need is empty, say which one and route the user to /onboarding for core files or to the owning module's setup. Never quietly produce generic output where personal output was promised.

Rule four is write discipline. Each file has one owner. Core writes profile, product context, stakeholders, and working style. PM writes roadmap, bets, and metrics. Design writes the design system, the principles, and the critique log. The only shared file is lessons.md, which anyone may append to but nobody rewrites. One dated line per decision or finding. Rule five: live beats stored. If a connector like Linear, Jira, Notion, Figma, or Slack can answer with live data, prefer it, and if it disagrees with memory, say so. Stale memory is a finding, not a nuisance. Rule six: update on the way out. A workflow that changed reality appends to lessons and updates the owning file before it finishes.

Picture the case. Uber Eats grows overall, but weekday orders from 11:30am to 1:30pm run 30% below dinner. Call it the lunch gap. A PM runs /write-prd for a pre-order flow that locks a 12:00 delivery slot. The workflow opens product-context.md and learns the lunch gap is the standing bet this quarter, that the window under attack is 11:30 to 1:30, and that there is an open question about whether kitchens can hold a noon slot on a Tuesday. It does not ask her what the product is or what the lunch gap means. When the PRD is done, it writes one line to lessons.md: "2026-08-23, write-prd: 12:00 pre-order slot spec drafted, linked to the lunch gap bet, kitchen capacity still open." Next week, /brief-me reads that line and puts kitchen capacity in front of her before she spends another day on screens.

The most common mistake is treating memory as something only onboarding writes. Onboarding gives you a snapshot. If no workflow ever updates it, the snapshot is stale in a week and every brief gets a little more generic until the system looks like decoration.

Why does a PM care? Because the value of this system compounds only if the context compounds. The skills do not get smarter with use. The memory does. Protect it and every other skill in this guide gets sharper for free.

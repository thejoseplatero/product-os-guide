How it fits together

The shape of Product OS

TLDR: Product OS is memory plus skills plus commands, packed into five modules you install as a plugin. You need only two verbs each day: /brief-me to open the day and /start to begin any piece of work.

The full idea

Before you go skill by skill, here is the whole thing in one picture. Product OS is not a chatbot. It is an installable system that lives inside Claude Code as a plugin marketplace. It has four kinds of parts: skills, commands, agents, and bridges. Underneath all of them is memory.

A skill is a unit of know-how grounded in a named framework. Jobs to be done from Moesta and Christensen, strategy kernel from Rumelt, heuristics from Nielsen. A skill is a markdown file that says what good work looks like, what it needs before it can run, and what artifact it produces. Skills do not run on their own. A command is the verb you type, like /write-prd or /ship. Commands read memory, call the right skills, and produce the artifact. An agent is a worker a command hands a job to when that job is big and separate: deep research, a hostile code review, writing tests before code exists. A bridge is a special command that reads across two functions and reports where they disagree. /handoff-audit reads the PRD and the design files and catches "the PRD requires an empty state, the design has no empty state screen." Neither side could find that alone.

Memory is what makes any of this personal. It lives in your project at .product-os/memory/ as flat markdown files: your profile, your product context, your stakeholders, your roadmap, your bets, your metrics, your design system, your lessons, your calibration ledger. Every command reads memory before it opines, and the ones that change reality write one dated line back. The skills never get smarter. The memory does.

Now the modules. Core is always installed: the memory schema, onboarding, the daily brief, the router, and three shared skills, which are memory protocol, stakeholder comms, and calibration. PM holds twenty skills for discovery, strategy, PRDs, and go-to-market. Design holds twelve for critique, systems, accessibility, and handoff. Eng is the build module: it turns stories with acceptance criteria into tested software, and it needs PM installed. Leader holds the bridges and needs both PM and Design. You buy bundles, not checkboxes: PM, Design, Leader, or Builder, which is everything.

With the Builder bundle, the system runs a full pipeline from idea to working software. Say you want to add scheduled orders to a food delivery app. A problem brief asks whether it deserves discovery time. An opportunity assessment asks whether it deserves build time. /write-prd writes the spec. Story mapping picks the first slice. Story writing turns the slice into stories with Gherkin acceptance criteria. /build-setup picks the stack once. /build-story turns each criterion into a test first, then code, and the tests gate done. /build-slice builds the walking skeleton. /ac-audit and /ui-conformance check the seams on the build. /ship deploys. The one joint you never shortcut is acceptance criteria as tests.

Day to day you use two verbs. In the morning, /brief-me: one screen with the single thing that deserves your attention, what moved, what is at risk, who needs a touch, and which predictions are due for scoring. If nothing moved, it says so in two sentences. For any piece of work, /start and the outcome you want in plain words: "/start tighten the empty state copy on the courier screen." The router picks a lane. Express for a small clear ask: it names one skill and runs it. Guided for net-new or high-stakes work: it shows the whole chain, skips what memory already covers, and after every step asks go, skip, swap, or stop. Explore when you state no outcome: you get a menu grouped by what you are trying to do.

One rule sits above all of it. You keep the judgment gates. The system drafts, structures, audits, and remembers. Appetite calls, ship decisions, and kill decisions stay with the human. The rest of this guide is about making those decisions with better evidence.

The commands

  • /onboarding asks about ten questions about your product, org, and working style and writes the first version of every memory file. Core.
  • /brief-me produces the one-screen start-of-day briefing across roadmap, bets, risks, stakeholders, open questions, and due scorings. Core.
  • /start is the router: say the outcome you want and it picks the express, guided, or explore lane through the right skills. Core.
  • /calibrate scores the predictions that are due and, with report, rebuilds the org's bias profile. Core.
  • /write-prd turns a feature idea into a full PRD with JTBD framing, opportunity mapping, spec, risks, and GTM notes. PM.
  • /roadmap reviews, pressure-tests, or updates the Now/Next/Later roadmap with kill criteria, reconciling against any live tool. PM.
  • /design-critique runs a structured critique of a design against your own principles first and generic heuristics second. Design.
  • /design-system defines, builds, or connects a design system so tokens and components have one source of truth every other workflow reads. Design.
  • /build-setup scaffolds the build once per product: stack choice, repo structure, test harness, deploy target. Eng.
  • /build-story implements one story and verifies it against its acceptance criteria, tests first, the pipeline's workhorse. Eng.
  • /build-slice builds a whole release slice story by story in story-map order, walking skeleton first. Eng.
  • /ac-audit is a PM-to-eng bridge that cross-references the built software against the PRD and acceptance criteria. Eng.
  • /ui-conformance is a design-to-eng bridge that checks the rendered app against the design system and states matrix, not the mock. Eng.
  • /ship deploys what is built, writes the demo notes, and closes the loop in memory, only when the suite is green and the audit is clean. Eng.
  • /handoff-audit is a bridge that cross-references a PRD against the design artifacts and reports every seam defect before it ships. Leader.
  • /pm-design-sync is a bridge that preps a PM and Design sync by finding where the two functions' stated realities disagree. Leader.
  • /team-health-check is the widest bridge: it reads the whole memory system for signs that the product org itself, not the product, is drifting. Leader.

The agents

  • discovery-researcher runs market scans, competitor teardowns, and evidence gathering for or against a bet, starting from what memory already believes. PM.
  • design-critic does the deep design review: heuristic evaluation, states audit, and design-system conformance on one flow, judged by the org's own principles first. Design.
  • test-writer converts acceptance criteria into tests before any code exists, adversarially, and is kept separate from the implementer so nobody grades their own homework. Eng.
  • implementer writes the smallest clean production code that turns the already-written failing tests green, and never edits the tests. Eng.
  • code-reviewer reads one story's diff as a hostile senior engineer, checking correctness, test honesty, convention drift, and scope smuggling before ship. Eng.

Memory Protocol

TLDR: the rules for how every Product OS workflow reads and writes the flat markdown files in .product-os/memory/. Reach for it before you ask the user anything a previous session already answered.

The full idea

Most AI tools have amnesia. You explain your company, get a decent answer, close the window, and tomorrow you explain your company again. The memory protocol is the part of Product OS that ends that. It is a house rule written into the system itself: all durable state lives in .product-os/memory/ as plain markdown files a human can open and edit. If you cannot grep it, the system failed.

The protocol has six rules. Rule one is the big one: read before asking. Every workflow loads profile.md and product-context.md first, always. If the answer to a question could be in memory, you check memory. The skill calls asking what memory already answers the one unforgivable failure. Rule two: load narrowly. Pull only the extra files the task needs. Never dump the whole directory into context. Rule three: missing is not blank slate. If a file you need is empty, say which one and route the user to /onboarding for core files or to the owning module's setup. Never quietly produce generic output where personal output was promised.

Rule four is write discipline. Each file has one owner. Core writes profile, product context, stakeholders, and working style. PM writes roadmap, bets, and metrics. Design writes the design system, the principles, and the critique log. The only shared file is lessons.md, which anyone may append to but nobody rewrites. One dated line per decision or finding. Rule five: live beats stored. If a connector like Linear, Jira, Notion, Figma, or Slack can answer with live data, prefer it, and if it disagrees with memory, say so. Stale memory is a finding, not a nuisance. Rule six: update on the way out. A workflow that changed reality appends to lessons and updates the owning file before it finishes.

Picture a PM on a food delivery app. She runs /write-prd for a feature that lets customers tip the courier after delivery. The workflow opens product-context.md and learns the app is in four cities, the top priority this quarter is courier retention, and there is an open question about whether tipping is legal in one market. It does not ask her what the product is. When the PRD is done, it writes one line to lessons.md: "2026-08-23, write-prd: post-delivery tipping spec drafted, linked to courier retention bet." Next week, /brief-me reads that line.

The most common mistake is treating memory as something only onboarding writes. Onboarding gives you a snapshot. If no workflow ever updates it, the snapshot is stale in a week and every brief gets a little more generic until the system looks like decoration.

Why does a PM care? Because the value of this system compounds only if the context compounds. The skills do not get smarter with use. The memory does. Protect it and every other skill in this guide gets sharper for free.

Stakeholder Comms

TLDR: how to write to a specific named person: status updates, escalations, asks, and bad news. Reach for it whenever you draft anything one real person will read, in email, Slack, a doc comment, or an exec update.

The full idea

A lot of a PM's job is writing to people who can say yes or no. This skill pulls from three sources. Chris Voss, the former FBI negotiator, taught tactical empathy: the person who feels heard is the person who concedes most. Robert Cialdini wrote about pre-suasion: the frame you set before the ask matters more than the ask. And Kim Scott's radical candor says being direct and caring at the same time is the respectful combination.

Before you draft anything, load stakeholders.md for the recipient. If the person is not in it, ask two questions: what do they care about, and how do they like to be told things. Then add the answer to memory so next time you already know.

The method has five moves. One, their frame first. Open with the thing they care about, not the thing you want. One sentence that proves you know their world before you enter it. Two, BLUF, bottom line up front. The point lands in the first two lines, whether it is status, an ask, or bad news. Three, the bad news protocol: state it plainly with no cushioning adjectives, give the cause in one sentence, give the plan in two, and give the date they will hear from you next. Kim Scott's rule applies: softening the message is for your comfort, not theirs. Four, the ask is singular and answerable. "Can you approve the courier bonus budget by Friday" works. "Thoughts?" does not. Five, match their channel and length from memory. A CFO who reads bullets gets bullets.

Here is the food delivery version. Your restaurant onboarding tool slipped two weeks. Your stakeholder is Dana, the head of sales, and memory says she cares about the Q3 restaurant sign-up target and reads Slack, not email, and hates long messages. The draft opens with her frame: "Dana, this affects the Q3 sign-up number." Then the bad news, plain: "Onboarding slips from Sept 2 to Sept 16." Cause in one sentence: "The menu import broke on restaurants with more than 200 items." Plan in two: "We are shipping a manual import path this week so your team can keep signing restaurants. The full fix lands the 16th." Next touch: "I will update you Thursday." One ask: "Can you tell me which five restaurants need the manual path first?" Five lines, in Slack.

The most common mistake is adjective inflation. "Great progress on onboarding" tells Dana nothing. "Twelve restaurants onboarded this week, target is twenty" tells her everything. Passive voice like "it was decided" hides the person, and readers notice.

Why it matters: a PM's output is mostly decisions other people make. Writing that gets a clear yes or no fast, and keeps trust when the news is bad, is the skill that keeps you in the room.

Calibration

TLDR: record every prediction your product work makes (risk ratings, bet hypotheses, go/no-go calls, appetite estimates), score it on schedule, and build a bias profile so future judgments self-correct. Reach for it whenever a workflow produces a rating, forecast, or verdict, and whenever one comes due for scoring.

The full idea

This skill comes from Philip Tetlock's book Superforecasting. His finding: forecasting skill is trainable, but only with a feedback loop that almost nobody closes. You have to record the prediction precisely, score it on schedule, and study your misses by type. Product teams predict constantly: every risk rating, every bet, every "six weeks". We score almost none of them. So the same optimism bias ships the same surprises forever.

Rule one: predictions get recorded at birth. The moment a workflow produces a judgment, it writes one scoreable line to calibration.md. Hindsight launders everything. A scoreable line has four parts: the date, the source artifact, the claim stated so it can be proven wrong with a probability or rating, and the date it gets scored. Vague claims get sharpened or rejected at write time. "This should do well" is not scoreable. "At least 40 percent of new customers place a second order within 14 days" is. Writing the sharp version improves the judgment by itself.

Rule two: scoring is scheduled, not remembered. Every prediction carries its score date, and /brief-me lists the due ones alongside your due work, whether or not you feel like grading yourself. Scoring is one line: right, wrong, or partial, plus a one-sentence cause.

Rule three: the bias profile is the payoff. Quarterly, or when you run /calibrate report, you compute from the ledger, by prediction type: the hit rate per type, the direction of the miss (optimistic or pessimistic, and by how much), and the expensive class, meaning which kind of miss cost the most. The profile goes at the top of calibration.md, and every judgment-producing skill reads it first. If the profile says your feasibility-LOW ratings fail 40 percent of the time, the next time four-risks is about to rate something feasibility LOW it says so and rates it MEDIUM unless there is specific evidence.

Food delivery example. In March the team runs four-risks on scheduled orders and rates feasibility LOW, meaning "this will not slip the schedule by more than two weeks." That line goes in the ledger with a June score date. In June, /brief-me flags it. The feature slipped five weeks because the restaurant POS integration was harder than planned. Score: wrong, optimistic, cause: integration effort. Three more like it over the year, and the profile says "feasibility ratings on anything touching restaurant systems run optimistic." The next PRD touching a POS gets a warning before anyone writes a date.

The most common mistake is recording predictions after the outcome is known. That is a diary, not a ledger. The second is only scoring the wins, which turns the ledger into a trophy case. Misses are the training data.

Why it matters: skills are copyable. Anyone can rebuild a framework library in a weekend. A year of scored predictions about how your specific org is wrong cannot be bought, copied, or cold-started. The skill calls this a cornered resource, in Hamilton Helmer's sense.

JTBD Framing

TLDR: Jobs-to-be-done turns a feature request or a vague idea into the real job a customer is trying to get done, the moment they struggle, and what they compare you against. Reach for it when you evaluate a feature idea, write a problem statement, or need to challenge someone's pet feature.

The full idea

This idea comes from Bob Moesta and Clayton Christensen. Their claim is simple: people do not buy products, they hire them. They hire a product to make progress in a specific situation. So the thing we study is not the persona and not the feature. It is the struggling moment: the exact situation where someone is stuck and wants to move forward.

The method has four steps. First, find the struggling moment. Write it as "When [specific situation], I struggle to [the progress I want]." If you cannot picture the situation clearly, you do not have a job yet. You have a category. Second, write the job statement: "When [situation], I want to [motivation], so I can [expected outcome]." Here is the test: delete your product name. Does the sentence still make sense? If the statement mentions your feature, it is circular and you need to start over.

Third, map the four forces. There is the push of the current situation, meaning what hurts right now. There is the pull of the new solution, meaning what looks attractive. Then there is anxiety about the new thing, and habit, which is everything that keeps people where they are. Most teams only work on pull. But a feature that adds pull and ignores anxiety and habit loses to "do nothing," and "do nothing" is the most hired competitor in every market.

Fourth, name the real competition. What do people hire today for this job? Often it is a spreadsheet, a phone call, or simply ignoring the problem. That is the bar you have to beat, not the big company in your category.

Take our food delivery app. A stakeholder says "we need a group ordering feature." That is a feature wearing a trench coat. Ask for the struggling moment: "When I order lunch for my team of six on a Friday, I struggle to collect everyone's choices without ten messages back and forth." Now the job is clear. The push is the chaos of the group chat. The pull is one link, everyone picks. The anxiety is "what if someone's order goes missing and I get blamed." The habit is the group chat, which already works, badly, for free. The real competitor is the group chat, not the other delivery app.

The most common mistake is letting personas do the work that circumstances should do. "Millennials want convenience" tells you nothing. The same person hires a different product at 9am on a work day and at 9pm on a Sunday. Circumstance, not demographics. This matters to a PM because every roadmap decision is a bet on a job. If nobody is struggling, nothing gets hired, no matter how good the demo looks.

Continuous Discovery

TLDR: Continuous discovery is a weekly habit of talking to customers and organizing what you learn into an opportunity solution tree, so every solution is compared against other solutions and tied to an outcome. Reach for it when planning discovery, deciding what to build next, or when someone jumps from problem to solution in one step.

The full idea

This comes from Teresa Torres and her book Continuous Discovery Habits. Her big point is in the title: discovery is a habit, not a phase. A "discovery phase" with an end date means you stop learning on a Friday and build for six months on what you knew then. The core sin she names is comparing a solution against nothing. A team falls in love with one idea, and the only question left is "how do we build it." Good teams compare solutions against other solutions, map them to opportunities, and map those to an outcome.

The tool for this is the opportunity solution tree. You build it top-down and prune it bottom-up. At the root is one outcome: the single metric the team is chartered to move. If the root is a feature or a theme, stop and go get the outcome first. Under the outcome sit opportunities: needs, pains, and desires you have heard from customers, in their words. The test is simple. An opportunity is something a customer could confirm: "yes, that is annoying." A solution is something only you could confirm. Under each opportunity you target, list at least three solutions. Always three. One solution under an opportunity means you are already committed, not deciding. Under each solution go assumption tests: the riskiest things that must be true, and the cheapest test for each.

Assumption mapping: for a candidate solution, list assumptions across five types: desirability, viability, feasibility, usability, and ethical. Plot each on importance against evidence. Test the top-right corner first, important and no evidence. Testing the comfortable ones is theater. Tests should be the smallest thing that produces evidence: a fake door, a one-question survey, a prototype walkthrough, a concierge run. Days, not sprints.

Our food delivery app. The outcome is "increase repeat orders in the first 30 days." Opportunities we heard: "I never know if my order is actually on its way," "the delivery fee surprises me at checkout," "I order the same thing but have to search for it every time." Pick the first one. Three solutions: a live map, a plain text status line with minutes, and a notification when the driver picks up. Under the live map, a big assumption is "customers will open the app to check rather than wait for a text." Cheap test: a fake "track on map" button for a week. Count the taps.

The weekly habit is the part people skip. One customer conversation a week, recruited from people who used the product, keeps the tree current. Interview for stories, not opinions.

The most common mistake is opportunities that are secretly solutions wearing need language: "users need a dashboard." No customer ever said that. Why does this matter to a PM? Because your job is to make good decisions under uncertainty, and a tree with one branch is not a decision, it is a wish with a deadline.

Customer Interviews

TLDR: Customer interviews done right produce evidence instead of politeness: questions about the past, a commitment test at the end, and synthesis within a day. Reach for it when writing an interview script, debriefing a call, or checking whether "validation" was real.

The full idea

Two sources here. Rob Fitzpatrick wrote The Mom Test, and Bob Moesta gave us the switch interview. Fitzpatrick's rule is the one to remember: even your mom cannot lie to you if you never mention your idea. People are polite about the future and honest about the past. So you ask about the past.

The Mom Test has three rules. One, talk about their life, not your idea. The moment the idea enters the room, the data leaves. Two, ask about specifics in the past, not opinions about the future. "Would you use X?" is worthless. "When did this last happen? Walk me through it" is gold. Three, talk less, listen more. You are mining for facts, workarounds, and money already spent. You are not pitching.

Some questions that work. "Tell me about the last time you had this problem." "What did you do about it?" The workaround is the real competitor and the real budget. "What have you already tried or paid for?" Spend is evidence, adjectives are not. "Who else struggles with this?" And the sharp one: "What happens if you just do not solve it?" If the answer is "nothing really," the pain does not clear the bar.

Let us run it on the food delivery app. Bad version: "We are thinking of adding group ordering. Would you use it?" Everyone says yes. Good version: "Tell me about the last time you ordered food for more than three people." Now you hear: "Friday, I screenshotted the menu into the team chat, waited twenty minutes, two people never replied, I guessed, one of them was annoyed." That is a struggling moment, a workaround, and the cost of the workaround, all in one answer. Then: "What did you try?" "I tried a shared note once. Nobody used it." Now you know a feature that needs everyone to participate has already failed once.

Then comes the commitment test. Compliments are fool's gold. End every promising conversation with an ask that costs them something: their time (a follow-up session with their real order history), their reputation (an intro to a colleague who has the same problem), or their money (a deposit or a pilot fee). If they advance, that is real signal. "Sounds great, keep me posted" is a polite no. Log it as a no.

Moesta's switch interview is for real purchases. Find people who recently switched to or from a product and walk the timeline backwards: first thought, passive looking, active looking, the event that forced the decision.

Synthesis discipline: within 24 hours, write exact quotes, facts, and commitments, tagged to opportunities. Three interviews with the same unprompted complaint is a pattern worth a bet. One enthusiastic interview is an anecdote. The most common mistake is the word "would" anywhere in the script. This matters to a PM because you will be asked "did you validate it?" and the only honest answer is a list of things people did, not things they said they might do.

Four Risks

TLDR: Every product idea carries four risks: value, usability, feasibility, and viability. Reach for this when evaluating an idea, planning discovery, reviewing a PRD's risk section, or when a team is about to build something untested.

The full idea

This comes from Marty Cagan, in Inspired and Empowered. His observation is that most product failure is not building the thing wrong. It is building the wrong thing, confidently. Every idea carries four risks, and discovery's job is to knock down the biggest one before engineering scales it.

The four. Value risk: will they buy it, or choose to use it? This is the riskiest and the most skipped. Proxy signals of real interest, like clicks on a fake door, deposits, or signed letters of intent, beat stated intent every time. Usability risk: can they figure out how to use it? You can test this with a prototype and five users before anyone writes production code. Feasibility risk: can we build it with the time, skills, and tech we have? Engineers answer this, but only if you ask them during discovery, not after you hand them a spec. Viability risk: does it work for the business? Legal, compliance, sales channel, support load, brand, unit economics. This is the risk the PM is uniquely accountable for, and the one that kills products after they launch.

The method. For the idea in front of you, write each risk as a sentence that could be proven false. Rate it high, medium, or low, with one line of evidence, or admit "no evidence." Then design the cheapest test for the highest risk only. Do not test all four at once. Knock down the biggest, re-rank, repeat. A week of discovery on the right risk saves a quarter of building.

Prototypes are the currency: a feasibility spike, a user prototype in Figma, a live-data prototype, a concierge test. Match the prototype to the risk. A beautiful Figma flow tells you nothing about value.

Take the food delivery app and the idea "a monthly subscription with free delivery." Value risk: "Customers who order four or more times a month will pay 9.99 for free delivery." Evidence: none yet, so high. Usability: "Customers can find and understand the plan in checkout." Probably medium, easy to test with a prototype. Feasibility: ask engineering, likely low. Viability: "Subscribers do not order so often that we lose money on every delivery." That is the scary one, and it is math, not opinion. So the cheapest first test is a fake door: show the plan at checkout, count who taps "join," collect emails. Not a single line of billing code yet.

One more check from Cagan. If the idea arrived as a solution to build rather than a problem to solve, say so. You can still assess the four risks, but the team is operating as a feature factory and the value risk is probably unexamined. The most common mistake is a risk section that says "risks: timeline." That is a plan risk, not a product risk. This matters to a PM because your credibility comes from being the person who asked "what kills this?" before it was expensive to find out.

Strategy Kernel

TLDR: A strategy has three parts: a diagnosis, a guiding policy, and coherent actions. Anything missing one of them is a wish, a slogan, or a budget. Reach for it when drafting or reviewing a strategy, or when a "strategy" is really a list of goals.

The full idea

This is Richard Rumelt, from Good Strategy Bad Strategy. His claim is that a strategy is a kernel with three parts, and if one is missing you do not have a strategy. You have a wish, a slogan, or a budget.

Part one is the diagnosis: what is actually going on, named plainly. A good diagnosis simplifies the overwhelming mess down to the critical aspects. "We lose enterprise deals at security review" beats "the market is competitive." The diagnosis is falsifiable and often uncomfortable. If everyone nods instantly, it is probably not a diagnosis.

Part two is the guiding policy: the overall approach you chose to deal with the diagnosis. The key word is chose, because a real policy excludes other approaches. A policy that forbids nothing guides nothing. That exclusion is the strategy.

Part three is coherent actions: resource commitments that reinforce each other and follow from the policy. The coherence test: if a stranger read only the list of actions, could they guess the policy? If the actions could belong to any strategy, they belong to none.

Let us do the food delivery app. Bad strategy: "Become the most loved delivery platform by delighting customers and growing 40%." No diagnosis, no exclusion, a goal dressed as a plan. Good kernel. Diagnosis: "Customers in our mid-sized cities churn after their second order because delivery takes over 45 minutes, and we cannot fix speed without restaurant density we do not have." Guiding policy: "Win mid-sized cities by being the fastest option for a short list of popular restaurants, not the biggest menu." That excludes the "sign every restaurant" play. Coherent actions: sign the top 20 restaurants per city with exclusive prep-time agreements, put couriers in zones near those restaurants, show a 30-minute promise only for that list, and stop marketing the size of the menu. A stranger reading those four actions could guess the policy. That is coherence.

Rumelt also names four hallmarks of bad strategy, and you should call them out by name in any review. Fluff: inflated language that restates the obvious, like "customer-centric platform excellence." Failure to face the challenge: a strategy that never mentions what is hard. Mistaking goals for strategy: "grow 40%" is an ambition, not a how. Bad objectives: a long list of everything everyone wants, or objectives as impossible as the challenge they avoid.

The last idea is leverage. Strategy works by concentrating force where it matters: finding the pivot point where focused effort produces a disproportionate result. A strategy that spreads resources evenly across ten priorities has chosen not to have a pivot point. The most common mistake is the word "and" doing heavy lifting in the guiding policy, trying to keep every option open. This matters to a PM because your roadmap is only defensible if someone can trace every line of it back to a diagnosis and a policy that said no to something.

Positioning

TLDR: Positioning is choosing the market frame so buyers compare you to the right thing, expect the right thing, and pay the right price. Reach for it when writing positioning, messaging, a launch narrative, or when a product is being described by its features instead of its value.

The full idea

This is April Dunford, from Obviously Awesome. Positioning is context-setting. The market frame you choose decides what buyers compare you to, what they expect, and what they will pay. And here is her sharpest point: weak positioning is almost never a product problem. It is a default frame nobody chose.

There are five components, and the order matters because each one feeds the next. First, competitive alternatives: what would customers do if you did not exist? Include "spreadsheet," "intern," and "nothing." The alternative sets the bar. Positioning against a rival nobody uses only flatters the rival. Second, unique attributes: capabilities you have that the alternatives do not. Features, yes, but also your delivery model, your expertise, your integrations, your business model. Third, value: what those attributes enable for the customer, stated as outcomes. Take each attribute and ask "so what?" and keep asking until you hit something a buyer would pay for. Fourth, best-fit segment: who cares a lot about that value? Specific enough to target. Positioning for everyone is positioning for no one. Fifth, market category: the frame that makes your value obvious to that segment. Category is a lever, not a fact. Slack calling itself "email for teams" instead of "chat" changed what it was compared against.

Now the food delivery app. Say we are small and we are in one university town. Alternatives: the two big delivery apps, calling the restaurant, walking, and cooking. Unique attributes: we only list restaurants within ten minutes of campus, we allow split payment across up to eight people, and we have no service fee on orders over four people. So what? Groups of students can feed a study session in under 30 minutes without one person fronting the money. Who cares a lot? Student groups ordering late at night. Category: not "food delivery app," that puts us next to giants. Try "group food for campus." Now a student compares us to the group chat and the big apps' fees, and we look obviously better at our one thing.

Dunford gives three plays for choosing the frame. Head-to-head: own the existing category, only if you can actually win it. Big fish, small pond: subsegment the category where you win, like "CRM for investment banks." Create the game: a new category, expensive, needs missionary selling, usually the wrong answer for a small player. Our campus example is a big fish, small pond play.

The output is a positioning statement per audience, not a tagline: For [segment] who [struggle or context], [product] is a [category frame] that [value]. Unlike [top alternative], it [key differentiator]. Messaging comes from this, never the other way around.

The most common mistake is "our differentiator is quality, simplicity, or AI." Every competitor claims those too. This matters to a PM because the product you ship is only half the job. The frame it lands in decides whether anyone understands why it exists.

Moats

TLDR: A moat is a condition that gives you lasting better returns: a benefit plus a barrier that stops competitors from copying it. Reach for it when asking "what stops a competitor from copying this," or when a strategy doc claims differentiation.

The full idea

This is Hamilton Helmer, from 7 Powers. He calls a moat a "power": a condition that creates persistent differential returns. The key is that a power needs two things at once, a benefit and a barrier. A benefit without a barrier is a feature head start: temporary, and copied by anyone it hurts.

The seven powers. Scale economies: unit cost falls with volume, and the barrier is the loss a challenger must eat to match your scale. Network economies: value rises with users, and the barrier is that a small copy of a network is worthless. Counter-positioning: a new model the incumbent will not copy because it would cannibalize their core. The most available power for a small player. Switching costs: leaving hurts because of data, integrations, workflow, retraining. Earned over usage, invisible at purchase. Branding: habitual trust that commands a premium. Cornered resource: exclusive access to a patent, a dataset, a team, a supply deal. Process power: an embedded way of working that rivals can see but not copy on any useful timeline.

Apply two tests to any claimed moat. Benefit: does it materially improve cash flow or customer value? Barrier: what specifically prevents a competent, funded competitor from copying it within the payback window? "We move faster" and "our UX is better" fail the second test. That is operating excellence, which Helmer rules out as power: necessary, insufficient, and imitable.

Stage matters too. Counter-positioning and cornered resource are available at the start. Network and switching costs compound during takeoff. Scale, brand, and process power arrive at maturity. The right question is "which power is this bet positioned to earn, and does the roadmap feed it?"

Food delivery app. A founder says "our moat is the best app experience." Test two fails. Let us look for a real power. The app operates in small towns with one or two restaurants per cuisine. A bet: exclusive delivery deals with the top five restaurants in each town, in exchange for zero commission in year one. That is a cornered resource. Benefit: customers get the restaurants they actually want. Barrier: the big apps cannot offer zero commission without breaking their own pricing model everywhere else. The barrier becomes real when the top five restaurants in a town are all locked in. What does a rational competitor do in the meantime? Probably pay restaurants to break the deal. So the roadmap must feed the power: make the restaurant tools so good the restaurant would not leave even for money.

For any bet, name one intended power, not a menu, with the benefit and barrier in one sentence each. If no power is nameable, the bet may still be right, but it is a race, and you should price and pace it like one. The most common mistake is "our moat is AI." A supplier's product is nobody's cornered resource. This matters to a PM because "defensible" is the word that separates a feature from a business.

Briefs and Cases

TLDR: There is a ladder of documents below the PRD, from a half-page problem brief up to a business case, and each one is priced by the decision it serves. The full idea

This skill draws on Marty Cagan's opportunity assessment, Ryan Singer's Shape Up pitch with its idea of appetite, and the Amazon working-backwards discipline, whose PR/FAQ sits at the top of this ladder. The principle: documents are decision instruments, priced by the decision they serve. A two-week experiment documented like a capital request is theater. A quarter-long bet approved on a Slack message is gambling.

The ladder, bottom to top. Rung one, the problem brief, half a page. Decision: is this worth anyone's discovery time? Four parts: the struggling moment with quoted evidence, who has it and how often, what they do today, and why now. No solution content at all. Output: pursue or park.

Rung two, Cagan's opportunity assessment, one page. Decision: should a team spend discovery on this? Answer plainly: what problem, for whom, how big (one honest multiplication), what alternatives exist, why are we suited to win, why now, how will we measure success, what factors are critical, and a go or no-go. If three of eight answers are "we do not know," the output is a discovery plan, not a verdict. Say so instead of decorating the unknowns.

Rung three, the product brief or one-pager. Decision: alignment before detail. The PRD's trailer: problem, target user, the bet in one sentence, success as a number, what is out, open questions with owners. Its job is to get people disagreeing now, at one page, not at page nine of the PRD.

Rung four, the Shape Up pitch. Decision: should a team get a fixed appetite of time? Five parts: the problem with its raw story, the appetite ("worth six weeks, no more" instead of "how long will it take?"), a fat-marker solution, rabbit holes, and no-gos. Appetite is the strongest scope-control device on this ladder.

Rung five, the business case, two to three pages, only when real money moves. It needs a do-nothing baseline with its cost made explicit, build and run costs, benefits traced to an owned metric, risks, sensitivity, and kill criteria with a review date.

Pre-mortem

TLDR: A pre-mortem assumes the project already failed, asks everyone to write why, then sorts the causes and assigns owners to the real threats. Reach for it before a launch, a big bet, a hire, a migration, or any decision that is expensive to reverse.

The full idea

This comes from Gary Klein's research on prospective hindsight, and it is practiced today by Shreyas Doshi. Klein found that imagining an outcome as already certain improves how well people identify its causes, by about 30%. The trick is grammatical. Not "what could go wrong?" That question invites optimism and politeness. Instead: "It is six months later and this failed. What happened?" That question invites the truth everyone was sitting on.

The method has five steps. One, set the scene. "It is [a date after launch]. [Project] failed, clearly and publicly. Write the story of what happened." Everyone writes silently and independently first. The whole value is harvesting private doubts before the room converges on one opinion.

Two, collect the causes and sort them into three buckets, which is Doshi's taxonomy. Tigers: real threats that will hurt you if you do not address them. Paper tigers: things that look scary but are actually fine, and you consciously set them aside. Elephants: the thing in the room nobody is saying. The pre-mortem exists to give elephants a speaking slot.

Three, score the tigers by likelihood times damage, and take the top three to five. Four, assign de-risking actions. Each tiger gets an owner and a dated action that either prevents it or detects it early: a canary metric, a checkpoint, a kill criterion. An unowned tiger is a decision to accept the damage. Five, log it. Causes and mitigations go into memory, so that if a post-mortem ever happens it can be compared against the pre-mortem. That comparison is how a team's risk instincts get better over time.

Food delivery app. We are about to launch group ordering in three cities. Set the scene: "It is February. Group ordering launched in November and is being quietly removed from the app. What happened?" Silent writing produces: "Restaurants could not handle 20-item orders and cancelled them." "Split payments died when one card declined." "Nobody believed office managers would leave the group chat, but the sponsor had already announced it." Sort them. The first two are tigers. A competitor's similar announcement is a paper tiger. The last one is an elephant, and it only appeared because people wrote privately. Prioritization

TLDR: Three ways to rank a backlog (RICE, Kano, cost of delay) plus a final check on your own motivation. Reach for it when everything is marked P0, when you need to defend a call, or when you need to decide what not to do.

The full idea

Every backlog tells lies. Not on purpose. The lies come from gut feel, from the loudest voice in the room, and from the fact that nobody ever deletes anything. Prioritization is the set of tools that catches those lies. This skill uses three of them: RICE from Intercom, the Kano model from Noriaki Kano, and cost of delay from Don Reinertsen. The key point is this: no framework decides for you. Each one catches a different lie. You pick the one that targets the lie you suspect.

RICE is for when gut feel is running the roadmap. You score each item. Reach is how many people it affects per quarter, and it must be a real number. Impact is a scale per person: 0.25, 0.5, 1, 2, or 3. Confidence is 100, 80, or 50 percent, and if you are below 50 percent, stop scoring and go do discovery. Then divide by Effort in person-months. The score is not the decision. It is the start of the argument. The useful moment is when the score contradicts the favorite idea in the room, and the room has to explain why.

Kano is for when the team cannot tell table stakes from wow. You put each candidate in one of three buckets. Basic features make people angry when missing but nobody notices when present. Performance features are "more is better," and you compete here on purpose. Delighters are unexpected and earn love far beyond their cost. Two traps: delighters decay into basics over time, and teams over-invest in performance features because they are easiest to justify on a slide.

Cost of delay is for when everything is "high priority." For each item, ask: what does one month of not having this cost us, in revenue, risk, or learning? Divide by duration to sequence. This is the only framework that handles urgency and importance together, and it exposes fake P0s instantly. A P0 with zero cost of delay is somebody's pet.

Picture our food delivery app. The backlog has a live order map, a loyalty program, and a fix for a checkout bug that drops 4 percent of orders. Under RICE, the bug fix wins on reach and confidence. Under Kano, the map is a delighter and the bug fix is basic. Under cost of delay, the bug costs real revenue every month it sits there. Three tools, one answer, and now you can explain it.

The last pass is the hyper-focus trap check. Label which top item is interesting but unimportant and which is boring but load-bearing. Your brain will pick the interesting one on its own, so the ranking has to name the trade. And ship the list with a kill list: what you are explicitly not doing and why. A priority list without a kill list is a mood board. The most common mistake is setting confidence to 100 percent on items with no discovery behind them. That is not confidence, that is hope with a number.

Metrics Trees

TLDR: Pick one north star metric, break it into input metrics teams can actually move, and pair every metric with a counter-metric. Reach for it when defining success for a product, auditing a dashboard, choosing key results, or when a team is staring at a number it cannot move.

The full idea

Here is the idea in one sentence: a metric you cannot break down is a metric you cannot move. You can only watch it. Three sources. Amplitude's North Star framework gives us the top of the tree. John Doerr's Measure What Matters gives us the link to goals. And Andy Grove gives us the habit of pairing indicators so nobody games a number.

Start with the north star. It is the single metric that best captures the value customers receive, and revenue follows it with a lag. There are four tests. It measures customer value delivered, not what the company extracts. So, songs listened, not subscriptions sold. Second, moving it is a leading indicator of the business result. Third, every team can see how their work touches it. Fourth, it is a rate or ratio over a stated period, never a cumulative total. Registered users only ever goes up, so it tells you nothing.

Then build the tree. Break the north star into three to five input metrics. These are the levers teams actually pull: breadth, more users doing the core action; depth, doing more of it; frequency, doing it more often; efficiency, doing it faster or with less friction. Each input breaks down again until you reach a metric one team owns end to end. The tree is the org chart of accountability. The north star belongs to product leadership, inputs belong to teams, sub-inputs belong to squads. A team given a metric three levels above its control is chartered on hope.

Take our food delivery app. A good north star is completed orders per active customer per week. Breadth: customers who placed at least one order this week. Depth: items per order. Frequency: orders per customer per week. Efficiency: minutes from open app to order placed. Now the checkout squad owns "minutes to order placed," and they can actually move it. Give that squad "revenue" instead and they can only stare at it.

Now the Grove part. Every metric optimized alone will be gamed, by users, by teams, or by dashboards. So pair each target with the counter-metric that catches the failure mode. Delivery speed paired with order accuracy. Activation paired with week-four retention. Engagement paired with whether it is the good kind, because session length is a cost to the user, not a value. No key result ships without its counter-metric named.

One more discipline: leading versus lagging. Lagging metrics like revenue, churn, and NPS tell you the score after the game. Leading metrics like activation rate and time to value are playable during the game. Dashboards should be mostly leading. Reviews can be mostly lagging. A team reviewing lagging metrics every week is performing accountability, not exercising it. The most common mistake is a north star that is a revenue number. That is the board's metric, not the product's. It matters to you as a PM because the tree is how you turn "make the number go up" into work a team can start on Monday.

OKRs

TLDR: Objectives and Key Results are a focusing device: one inspiring direction, two to four numbers that prove you arrived. Reach for it when drafting quarterly goals, converting output goals to outcome goals, or when OKRs have become a task list with percentages.

The full idea

OKRs come from Andy Grove at Intel, written up in High Output Management. John Doerr carried them to Google and wrote Measure What Matters. Christina Wodtke added the weekly rhythm in Radical Focus. Here is the core idea. An OKR is a focusing device. The objective is the inspiring direction. The key results are how you will know you arrived. And its real power is what it makes you not do.

Writing the objective: it is qualitative, memorable, time-bound, and slightly uncomfortable. One line a team member could recite cold. If it could be any team's objective, like "delight our customers," it is fluff. Go back to your strategy first. Writing the key results: two to four per objective, and each one is an outcome with a number, never an activity. "Ship the new onboarding flow" is an output. You can ship it while making everything worse. "New-user week-one retention from 22 percent to 35 percent" is an outcome. It is the reason the flow exists.

The conversion test is simple. For any activity-shaped key result, ask "so that what?" until you hit a number in the world. Then write that number. Also attach the counter-metric from your metrics tree, or the key result is gameable by definition.

Let us try it on the food delivery app. Objective: "Make the second order feel automatic." Key results: customers placing a second order within 14 days goes from 31 percent to 45 percent. Reorder time from open app to order placed drops under 60 seconds. Counter-metric: refund rate on reorders stays at or below today's level. Notice there is no feature in there. The team can build a "reorder" button, or fix the saved-address bug, or do something nobody thought of yet.

Now the cascade. Company OKRs set what matters. Teams draft their own OKRs answering "how does our lever move that," and roughly half should be proposed bottom-up. This is Grove's point: people commit to goals they authored. Leadership's review job is coherence checking. Do these team key results plausibly add up to the company one? It is not assignment. OKRs handed down whole become compliance theater by week three.

Grading and cadence. Aspirational key results target around 70 percent attainment, so a straight-A quarter means the targets were sandbagged, and you should say so, gently. Committed key results, like contracts, compliance, or dates promised outside the company, target 100 percent and get labeled differently. Mixing the two silently is how "stretch goal" becomes an excuse. Set quarterly. Check confidence weekly: Wodtke's Monday ritual, per key result, is confidence up or down from last week and why. Grade at quarter end in one honest hour. A key result rolled over twice without examination is a strategy question wearing a metrics costume. The most common mistake is the roadmap with percent signs. If your key results list features, you have a plan, not a goal. As a PM, OKRs are how you say no to a hundred good ideas and mean it.

Experiment Design

TLDR: An experiment is a decision procedure, not a ritual: write the hypothesis first, check you have enough traffic to detect the effect, set guardrails, and fix the window before you start. Reach for it when planning an A/B test, reading results, or when someone says "let's just test it" on something that cannot be tested.

The full idea

The grounding for this skill is Ronny Kohavi's book Trustworthy Online Controlled Experiments. The one idea to keep: an experiment is a decision procedure. If no decision changes based on the result, the experiment is theater. Skip it and ship.

So the hypothesis comes first, written before anything else. The template is: we believe this change will cause this effect for this population because of this mechanism. We will know if this metric moves by this minimum size within this window. If it does not, we will do this specific thing: kill, iterate, or ship anyway and why. The "because" clause carries the weight. A hypothesis without a mechanism is a slot machine pull, and a win without a mechanism cannot be built on.

Here is one for our food delivery app. We believe showing the estimated delivery time on the restaurant list, not only at checkout, will raise order completion for first-time customers because uncertainty about wait time is why they leave. We will know if first-order completion rises by at least 3 points within two weeks. If it does not, we kill the change and interview ten drop-offs instead.

Next, power, honestly. Before running, ask: what is the minimum detectable effect at our traffic? Small products routinely run tests that can only detect a 20 percent lift, then read a flat result as "no effect." Compute it first. If the effect worth acting on is smaller than what you can detect, do not run the test. Use a different instrument: interviews, before-and-after with a holdout, or a painted door.

Then guardrails and the ratio check. Every test carries guardrail metrics that must not degrade: latency, error rate, support contacts, and the counter-metric from your metrics tree. And always run the sample ratio mismatch check. A 50/50 split that arrives as 52/48 means assignment is broken and every number downstream is fiction.

Reading results has four rules. Do not peek early and stop on significance; fix the window in advance. Segment only after the topline result, and only to generate new hypotheses, because twenty segments guarantee one fake "significant" one. A significant result you cannot explain by mechanism gets replicated before it gets celebrated. And losses teach more than wins. A killed idea is discovery working, so log it.

Finally, know when not to A/B test. Too little traffic for the effect you care about. Changes with network effects or long feedback loops. Strategic bets where the option value is bigger than the local metric; no A/B test approves a platform migration. And anything you would ship regardless. In each case, say which instrument replaces the test. "We cannot test this" never means "we cannot know anything." The most common mistake is the success metric switched after the fact to whichever one moved. As a PM, this skill is what keeps you from shipping noise with a confidence interval around it.

Pricing

TLDR: Price is the exchange rate on the value you create: pick the value metric first, research willingness to pay properly, anchor on the outcome, then design three tiers. Reach for it when setting or changing a price, designing plans, deciding if a feature should be paid, or when the price was copied from a competitor.

The full idea

Three people stand behind this. Patrick Campbell from ProfitWell, for value metrics and willingness-to-pay research. Madhavan Ramanujam, author of Monetizing Innovation, whose rule is price before you build. And Alex Hormozi, whose value equation is the anchor. The big idea: price is the exchange rate on the value you create. It is a product decision, not a finance afterthought, and the lever most products never test.

Start with the value metric. That is what you charge along: per seat, per thousand events, per project, or flat. A good value metric scales with the value received, so a heavy user pays more and is happy to. It is predictable by the buyer, because surprise bills churn accounts. And it aligns your growth with theirs, so your invoice reads like a receipt for their success. Per-seat is the default, not the answer. It taxes collaboration in products where value comes from more people seeing it.

Take our food delivery app, on the restaurant side. A flat monthly fee punishes the small cafe and undercharges the busy chain. Charging a percent per completed order scales with their value, is predictable, and means we only grow when they grow. That is the value metric doing its job.

Next, willingness to pay, asked properly. Never ask "would you pay X?" People are polite about the future, so the answer is worthless. Use Van Westendorp's four questions: at what price is this too expensive, at what price is it expensive but worth considering, at what price is it a bargain, and at what price is it so cheap you would doubt it? Run it on fifteen or more real prospects and the band falls out. For features, "how disappointed would you be if this went away" is a better must-have detector than "how much do you like it."

Now the anchor. Hormozi's value equation: perceived value equals dream outcome times likelihood it works, divided by time to result times effort required. Price against the outcome, not your costs and not your hours. For a restaurant, our app competes with the cost of staying as they are: empty tables on a Tuesday. Raising likelihood, with proof and guarantees, and cutting time to value moves willingness to pay more than discounts ever will.

Then packaging. Three tiers, each an identity, not a random pile of features. The entry tier answers "can I start cheaply." The middle tier is where you want most buyers, so design it first. The top tier anchors the price and catches the whales. Fence tiers along the value metric plus one or two capability gates, not twenty checkmarks nobody reads. And leave money on the table at the top: a plan ten times the middle price with human service costs one paragraph to offer.

The most common mistake is copying the nearest competitor's price. That outsources your strategy to someone with different costs and different customers. As a PM, pricing is the one decision that changes who your customer is.

GTM and Launch

TLDR: Tier the launch, write messaging from positioning, pick the one or two channels your product shape earns, and plan the day and the week after. Reach for it when planning a feature or product launch, or when "launch" currently means merge and tweet.

The full idea

Three sources. April Dunford: positioning feeds messaging, never the reverse. Brian Balfour: channels are not chosen, they are earned by the shape of the product. And the working-backwards press release, which, if you have one, is the launch narrative's source of truth.

Step one: tier the launch. Not every ship is a launch. Deciding the tier up front stops you under-marketing the big thing and exhausting your audience on small ones. Tier 1 is a new product or market claim: full apparatus, narrative, customers as proof, channel plan, sales enablement, support ready. Tier 2 is a meaningful capability: announcement, docs, an in-product moment, and one channel push. Tier 3 is an improvement: changelog, an in-product note if it is discoverable, and no external push. The tier is set by customer impact and story value, not by engineering effort. A two-week feature that unlocks a new buyer is Tier 1. A two-quarter migration is Tier 3.

For our food delivery app, say we ship group ordering, where an office can build one order together and split the bill. Three weeks of work, but it opens a new buyer: the office lunch organizer. Tier 1. The four-month courier routing rewrite that customers never notice? Tier 3.

Step two: messaging comes from positioning. If positioning is stale, run that skill first; messaging without it is adjectives. Then, per audience (buyer, user, press if Tier 1): lead with the pain of the alternative, name the change in their words, prove it with one thing, a number, a customer, or a demo, and give one call to action. If a press release from working backwards exists, it is the master narrative. Every asset is a resize of it.

Step three: channel-product fit. Channels reward product shapes. Virality needs the product to be seen in use. Content and SEO need searchable pain. Sales needs deal sizes that pay for humans. Paid needs lifetime value that pays for acquisition cost, with proof. Pick the one or two channels the product actually supports, and write down what you are not doing. A launch plan listing seven channels is a hope plan. Group ordering is seen by every coworker who joins the order, so virality is earned. Paid ads are not.

Step four: launch day and the week after. Before: support briefed with the FAQ, rollback path named, launch metrics instrumented and checked in staging. Most launches ship with broken analytics. During: one owner watching guardrails, one thread for triage. After, and this is the part that is actually go-to-market: a day-seven review against the launch hypothesis. Adoption, activation quality, support themes. A launch without a day-seven review is a party, not a strategy.

The most common mistake is drafting messaging before positioning exists, the "we will figure out the story in the blog post" move. For a PM, this skill matters because shipping is not the same as arriving. The launch is where the product meets the people it was built for.

Roadmapping

TLDR: A roadmap is a strategic communication device, not a delivery schedule, and each format answers a different question: Now/Next/Later, the GO roadmap, Three Horizons, and the Product Vision Board. Reach for it when creating or overhauling a roadmap, when a dated feature Gantt is causing pain, or when execs, sales, and the team each need a different view.

The full idea

Three sources. Roman Pichler gives us the GO Product Roadmap and the Product Vision Board. Janna Bastow gives us Now/Next/Later. Baghai, Coley, and White, via McKinsey, give us Three Horizons. The idea that holds them together: a roadmap is a strategic communication device, not a delivery schedule. The moment it becomes features with dates, it stops steering and starts promising. Each framework answers a different question.

Now/Next/Later is the working default. It answers: what are we doing, in what order of certainty? The time buckets are fuzzy on purpose. Now is committed and detailed, at most about three items, because more means nothing is now. Next is shaped but can be reordered. Later is directional and cheap to change. The fuzziness is the feature: it matches how certainty really decays. Each item is a problem or an outcome, with a metric and an owner. The weakness: it says nothing about why. Pair it with your strategy kernel or it turns into a prettier backlog.

The GO roadmap answers: why does each chunk of work exist? Five rows per slice: date or timeframe, name, goal, features, metrics. The rule that gives it its name: the goal row leads and the features row serves it. Features are trimmable examples of how the goal might be met; the goal is the commitment. One goal per slice, three to five per horizon, every goal traceable to strategy, metrics chosen before features. If a negotiation is about a feature, redirect it to the goal.

Three Horizons answers: are we investing in futures at all? H1 extends and defends the core, most of the effort. H2 is emerging opportunities being scaled. H3 is cheap probes on possible futures. It is a portfolio lens, not a delivery plan. Horizons are about business maturity, not time: an H3 probe can ship next month.

Our food delivery app: Now: fix the checkout drop-off. Next: group ordering for offices. Later: grocery delivery. As Three Horizons: checkout is H1, group ordering is H2, grocery is H3. And the GO slice for group ordering reads: goal, win the office lunch buyer; metric, 200 offices ordering weekly within one month of release; features, shared cart, split bill, invite link. If sales asks for the bill-splitting date, we point at the goal.

Upstream sits Pichler's Product Vision Board: one page with vision, target group, needs, product, and business goals. Every roadmap goal should trace back to it. The formats stack: Three Horizons balances the portfolio, strategy kernel picks the fights, GO states the goals, Now/Next/Later is the living view, metrics trees wire each item to a number. Build audience views from one source. The team sees problems and confidence, execs see goals and metrics, sales sees only what is committed in Now. Never let the sales view become the master, because whichever view is master is the roadmap you actually have. The most common mistake is features with quarter-precision dates twelve months out. That is fiction with a grid.

GO Product Roadmap

TLDR: Build Roman Pichler's five-row goal-oriented roadmap end to end, with his official checklist applied as hard gates before anything counts as done. Reach for it when actually constructing or reviewing a GO roadmap, making an internal versus public version, or converting a feature-date roadmap into a goal-led one.

The full idea

The source is Roman Pichler's GO Product Roadmap template and checklist, version 01 from 2023, at romanpichler.com. Roadmapping picks a format. This skill builds one. It applies Pichler's checklist as build gates, not as an afterwards review.

One column per slice, a release or a period. Five rows per slice. Date: when the goal should be met, a timeframe, not a promise. Name: memorable and fitting. Goal: the outcome or benefit, exactly one per slice. Features: three to five high-level capabilities needed to meet the goal. Metrics: how you will know, precise and time-bound. The defining rule: the goal is the commitment, the features are trimmable examples. If a negotiation is about a feature, redirect it to the goal.

The builder has three modes. Build, from a strategy input. Review, which lists gate failures on an existing roadmap, most damaging first, with fixes. And Bootstrap, when you have only an idea. Bootstrap runs a seven-question interview to produce a minimal Lean Canvas: who, what problem, why now, solution as a hypothesis, what is different, how you will know, how it makes money. Then one vision line: in five years, what is different in the world?

Build order is the heart of it, and it is never features first. Goals first: three to five per horizon, each traceable to a need, sequenced by dependency and cost of delay. Metrics second: how will you measure it and when, like "one week after release." Features last, three to five, only what is crucial. Name and date once the slice has substance. Features first with goals captioned on afterwards is a feature Gantt in disguise. Rebuild it, do not relabel it.

Every goal must pass five gates. Outcome-based: it states value created, never an activity. Specific: enough detail to tell what must be done. Measurable: a target you can verify. Prioritised: placed with dependencies and cost of delay in mind. Single: one goal per slice. The whole roadmap must be Connected, Adaptive with a quarterly review, Shared, and Actionable with no speculative slices.

Here is a slice for our food delivery app. Date: Q4. Name: Lunch Together. Goal: win the office lunch buyer so that 200 offices place a group order weekly. Metrics: 200 offices with at least one group order per week, measured four weeks after release. Features: shared cart, invite link, split bill. Now watch a weak version fail. "Launch group ordering" is an activity, so it fails Outcome-based. "Improve engagement" measured by "engagement improves" fails Measurable; the metric restates the goal. Placeholder numbers like "[N] percent" fail on purpose. Commit to a number and a date.

One last rule: internal versions may carry dates like "Q1." Public versions get coarse timeframes like "first half of 2027," or drop the date row entirely. Never let the external version become the master. For a PM, the gates matter because a roadmap with open failures is a draft, and a draft shown as a roadmap is a promise you did not mean to make.

Story Mapping

TLDR: Lay the work out along the user's real journey, then slice releases as thin end-to-end cuts, starting with the walking skeleton. Reach for it when breaking a big initiative into releases, when a flat backlog has lost the plot, or when planning what an MVP actually includes.

The full idea

This comes from Jeff Patton's book User Story Mapping. His picture: a flat backlog is a bag of parts with the picture on the box thrown away. Prioritized, but story-less. The map puts the picture back. It arranges work along the user's journey, so scope decisions become visible cuts through a story instead of fights over a ranked list.

Building the map has three moves. First, the backbone. Across the top, the user's activities in narrative order, told out loud: she realizes she is hungry, finds a restaurant, builds an order, pays, waits, eats, comes back. Activity level, user language, left to right in time. If you cannot narrate the backbone as a person's day, it is a feature list lying down. Second, steps. Under each activity, the tasks that accomplish it, then variations descending by necessity. Depth shows how well that activity is supported. Third, walk it with real people; the map builds shared understanding before it plans anything. Walking an engineer along the backbone reveals missing steps, like "wait, what happens when the restaurant rejects the order?" Those gaps are the cheapest bugs you ever fix.

Now the point of it all: slicing releases. Draw horizontal lines through the map. Each slice must span the entire backbone: a thin end-to-end journey, not a thick fragment. The user completes the whole story badly rather than half of it well. The first slice is the walking skeleton: the minimum path where a real user gets the real outcome once, with duct tape everywhere you cannot see. Later slices deepen activities by priority.

For our food delivery app, the walking skeleton is one city, a fixed restaurant list, card payment only, and a text when the food is on its way. No search, no ratings, no map. But a hungry person gets fed. Slice two adds search and live status. Name every slice by what the user can newly do, not by what the team builds.

Here is the anti-slice check. If a release covers three of seven activities completely and four not at all, you built a beautiful third of a product, which is a whole product to nobody. A "phase 1" of restaurant onboarding and a courier app, with no way to order, is exactly this. Patton's rule: you are slicing outcomes, not features.

Keep the map alive. When scope pressure comes, and it comes, cuts happen on the map where everyone sees which part of the journey got thinner, not silently in the backlog. In this skill the wall is required, not an appendix. Every run produces the written map and an HTML sticky wall you can drag, edit, and walk. A map that exists only as prose has already lost, because you cannot point at a paragraph in a room. The wall is a starting position, never a finding, so the notes must move. For a PM, this is the skill that turns "what is the MVP?" from an opinion fight into a line you draw together.

Story Writing

TLDR: Epics, user stories, and acceptance criteria that hold up: the three C's, INVEST, SPIDR splitting, and real Gherkin. Reach for it when breaking a PRD or story-map slice into buildable work, reviewing backlog quality, or when stories have become task tickets with "As a user" stapled on.

The full idea

The sources: Mike Cohn's User Stories Applied, Bill Wake's INVEST, Ron Jeffries' three C's (Card, Conversation, Confirmation), and job stories from Klement and Intercom. The story is not the ticket text. It is a placeholder for a conversation plus a confirmation of done. Forget the three C's and you get a backlog of tiny contracts nobody discussed.

Keep the hierarchy honest. An epic is a story too big for a sprint or two, tied to one outcome. It answers four things: the problem, the outcome metric, what is out, and "done when," a metric threshold held for a period or an explicit kill decision. A story is a thin vertical slice of user-visible value: as a specific role, I want a capability, so that an outcome. The "so that" carries the weight. A task is an implementation step inside a story, no user framing needed. The cardinal sin is dressing a task as a story. "As a user, I want the database migrated" is a lie with a persona.

For our food delivery app: epic, "Customers can reorder in under a minute," done when 45 percent of second orders use reorder for four straight weeks, or killed at quarter end. Story: "As a repeat customer, I want to reorder my last meal with one tap, so that I do not rebuild my cart on a busy night." Task: add a reorder endpoint. When personas mislead, use a job story: when it is 7pm and I am tired, I want to repeat last Friday's order, so I can eat without thinking.

INVEST is the review checklist. Independent, schedulable in any order. Negotiable, details left for the conversation. Valuable to the user, vertical not horizontal. Estimable, or it needs a spike, not more words. Small, days not weeks. Testable; a story you cannot demo is a philosophy.

When a story is too big, split with SPIDR: Spike, Path, Interface, Data, Rules. Never split by layer. A front-end story and a back-end story demo nothing. Watch the Rules trap: a story bundling a matching rule, a ranking rule, and a fallback rule is three stories wearing one badge. Ship matching alone first.

Acceptance criteria are the confirmation. Three to seven, each observable and binary. Use Gherkin when precision pays, as separate lines: Given, And, When, Then. Never folded into one sentence, which hides a second condition inside one bloated Given. Cover the unhappy paths: empty, error, and permission states. And a criterion that hedges is not a criterion. "(decided later)" is a placeholder pretending to be a check. Decide now or cut it into a spike.

The most common mistake is "As a user" on every story. Nobody is "a user." Name the role. And audit your own rewrite: after fixing a story, run the whole INVEST and smells checklist again on the new text. Author mode grades kindly. For a PM, stories are where the strategy finally touches a sprint, so this is where it either survives or quietly dies.

Heuristic Evaluation

TLDR: A structured walk through a flow using Nielsen's ten heuristics and Norman's two gulfs to find where users will stumble. Reach for it in critique, design QA, before handoff, or when you want to judge a competitor's UX without running a study.

The full idea

A heuristic evaluation is the cheapest usability method there is. You do not need users in the room. You need a flow, a checklist, and the discipline to look at the flow the way a distracted first-timer would, not the way the designer who built it does. The method comes from Jakob Nielsen, who published ten usability heuristics in the 1990s, and from Don Norman, who described the seven stages of action in The Design of Everyday Things. The posture underneath both is the same: an error is a design failure, not a user failure. Every place a user could stumble is the artifact's fault until proven otherwise.

Here is how you run it. Walk the real flow step by step. Not the happy-path demo, the actual flow. At each step ask Norman's two questions. First, the gulf of execution: can the user figure out what to do here? Are the options visible and labeled in the user's own words? Second, the gulf of evaluation: after they act, can they tell what happened? Is feedback immediate? Did the state visibly change?

Then sweep the ten heuristics and report only the ones that fire. Visibility of system status. Match with the real world. User control. Consistency. Error prevention. Recognition over recall. Flexibility for experts. Minimalism. Error recovery in plain language. And help, findable when needed. You look for violations, not essays.

Take our food delivery app. You tap "Place order" and the button goes grey for four seconds with no spinner and no message. That is a gulf of evaluation failure and a visibility of system status violation. The failure scenario in one sentence: a hungry user taps Place order, sees nothing happen, taps again, and gets charged twice. That is a blocker. Compare that to the restaurant list using the word "merchant" in one screen and "restaurant" in another. That is a consistency issue, and it is minor. Both are findings. They are not the same weight.

That brings us to the most common mistake: the inventory. Teams produce forty undifferentiated findings and hand it over as a list. Nobody can act on that. The skill says rate every finding as blocker, major, minor, or polish. Blocker means users will fail the task. Major means many will struggle. Minor is friction. Polish is nice to have. A report that names three blockers is worth more than one that lists forty items with no ranking.

Why does this matter to a PM? Because you will review designs every week, and you need a vocabulary that is not "I don't love it." Per finding you state the heuristic violated, the specific element, the failure scenario in one concrete sentence, the severity, and one suggested fix. Then you close with the three you would fix first and why. That is a review an engineer can act on and a designer can argue with. It turns taste into evidence.

Accessibility Audit

TLDR: A practical sweep of a design against WCAG 2.2, ordered by how much harm each failure does: keyboard, contrast, color, targets, semantics, motion, cognition. Reach for it in critique, before handoff, when reviewing a design system component, or the moment someone says accessibility can be "phase 2."

The full idea

Accessibility has a reputation as a compliance chore. That reputation is wrong. The grounding is WCAG 2.2, the web accessibility standard, with level AA as the floor. The second source is Microsoft's Inclusive Design work, which gives the idea that makes this click: disability is a mismatch between a person and a design, and it is situational. One arm, an injured arm, or an arm holding a baby while ordering dinner: same need. Accessibility findings are usability findings with higher stakes, and fixing them almost always helps everyone.

The method is a sweep in a fixed order, by harm. First, keyboard. Every interactive element must be reachable and usable by keyboard, in an order that follows the visual logic, with focus visible at all times and never hidden behind a sticky header. If the designer cannot Tab through the flow in their head, you found your first blocker. Second, contrast: 4.5 to 1 for body text, 3 to 1 for large text and UI components. Light grey on white is not a brand choice. It is an exclusion.

Third, never color alone. Every state needs a second channel: an icon, text, weight, or pattern. The test: imagine the screen in grayscale. Does the information survive? Fourth, targets and gestures: 24 by 24 pixel minimum, every swipe has a tap alternative, nothing depends on hover because touch exists. Fifth, semantics: real headings, labels tied to inputs, buttons that are buttons and not clickable divs, alt text that says what the image does. Sixth, motion and time: respect reduced motion, nothing flashes more than three times a second, no timeout without warning. Seventh, cognitive load: plain labels, controls in the same place on every page, errors that say what to do, no retyping what was just entered.

On our food delivery app: the cart marks an out-of-stock item by turning its name red. Color alone, a major finding. The "Add to cart" plus button is 18 pixels wide. The promo code field uses placeholder text as its only label. The delivery time picker is a swipe-only wheel with no tap alternative. And a keyboard user never reached checkout because the sticky cart bar hides the focus ring on the address field. That one is the blocker.

The most common mistake is treating accessibility as a final-sprint checklist. The skill is blunt about this: audit the design system once at the component level and inherit the fix everywhere. If you are auditing every screen separately, the system is leaking. Also, "it passes automated checks" means little: tools catch about 30 percent.

Why does a PM care? Because you set the definition of done, and "most users have a mouse" is the accessibility version of "users will figure it out." A blocker for keyboard users is a blocker, full stop. Severity uses the same scale as heuristic evaluation: blocker, major, minor, polish. You will be the person who decides whether it ships.

States and Edges

TLDR: Every screen is really five screens: empty, loading, partial, error, and ideal, plus the transitions between them. Reach for it when specing or reviewing any screen, preparing handoff, or whenever only the ideal state has been designed, which is always until you check.

The full idea

This skill comes from Scott Hurff's book Designing Products People Love, where he describes what he calls the UI Stack. The idea changes how you read every mockup: every screen is five screens. The pretty one in the deck is the ideal state. Users spend most of their early relationship with your product in the other four, and those four are where trust is won or lost.

Let me name them. One, the empty state, which is first contact. It has three flavors: first use, where the empty state is the onboarding and should invite the first action; user-cleared, where an empty inbox is a win and should feel like one; and no results, where the screen should repeat what was searched and offer a correction. An empty state that only says "No items" is a dead end dressed up as minimalism. Two, loading. Perceived speed is design's job. Skeletons that match the real layout beat spinners. Optimistic UI beats both when the action is safe to assume. Decide what is interactive during the load, because a frozen screen is an error state with better PR. Three, partial: some data, not enough to be useful. This is the state that makes new accounts look broken. Design the bridge from one item to the fifty-item mockup. Four, error, per class: user-fixable errors say what to do and keep the input. System-down errors apologize and say what is safe to retry. Permission-denied errors say who can help. Five, ideal. Already in the deck. It was never the risk.

Then the transitions. How does empty become partial? How does loading become error? Unhandled transitions are where the flashes, the jumps, and the lost form input live.

Our food delivery app makes this concrete. A new user opens the Orders tab. The mockup shows six past orders with photos. The real first-use screen is empty. Does it say "No orders yet" or "Hungry? Browse restaurants near you" with a button? A user searches for "ramen" at 2 a.m. and nothing is open. Does the screen say "No results," or "No ramen places are open right now, here is what is" and show them? The card is declined at checkout. Does the app wipe the cart and the address? Wiping a form is a hostile act.

The method for catching all this is the matrix habit. Screens down the rows, five states across the columns. Every cell either has a design, is marked N/A with a reason, or is a finding. This matrix is exactly what the PRD's spec section checks against at handoff. The matrix closes the seam between the PRD and the mocks.

The most common mistake is reviewing the happy path only and saying "we'll design errors during build." Build designs them as browser defaults. As a PM, you own the requirement. If your spec says "handle errors" and the design has one generic error screen, you did not spec it. Ask for the matrix before the handoff, not after the bug reports.

UX Writing

TLDR: Writing the words a user reads in the product: labels, buttons, errors, empty states, confirmations, onboarding. Reach for it when drafting or reviewing any in-product copy, or the moment the interface says "An error occurred."

The full idea

This skill is grounded in Torrey Podmajersky's book Strategic Writing for UX. Her starting point is worth writing down: words are the interface's cheapest, most-shipped, least-reviewed component. Every string does a job. It helps the user, and it carries the brand's voice, in that order.

Six rules do most of the work. One, buttons say what happens. "Place order," "Remove 2 items," "Send to driver." Never "OK / Cancel" on a destructive confirm. "Delete / Keep" makes the choice clear without reading the paragraph above, which nobody read. Two, write from the user's side of the screen. They manage notifications, not webhook config. Three, front-load. The first two words carry the meaning because users scan the left edge. "Payment failed: card expired," not "There was a problem processing your payment because the card on file appears to have expired." Four, errors say what happened, why, and what to do. No apologizing paragraphs, no blame, no error code as the only content, and preserve the user's work. Five, one idea per string. If a tooltip needs three sentences, the design needs a change. Six, consistency is comprehension. One name per concept everywhere. If it is "cart" in the nav, "basket" on the button, and "order" in the email, the user has three things to reconcile. Keep a terms list and enforce it in critique.

Then voice. Onboarding can be warm. Errors are calm and plain. A cute 404 page is fine. A cute "your payment failed" is contempt. Destructive confirmations are sober. Success states can celebrate briefly. A voice that does not change with the stakes is not a voice, it is a font.

The restaurant list says "merchants" because that is the database table name. Nobody ordering pad thai says "merchant." And the empty cart says "Your cart is empty." That describes the emptiness. "Add something from the menu to get started" describes the way out.

The method for checking all of this is the read-aloud test. Read the flow's strings out loud in sequence as a conversation. Screen says X, user does Y, screen says Z. Anywhere you wince, cut. The most common mistake is "An error occurred," which is the string equivalent of a shrug. Why does a PM care? Because copy ships without review more than any other part of the product, and the error state is where you earn or lose trust at the highest exchange rate. You will write half these strings yourself in tickets. Write them well.

Usability Testing

TLDR: Watching a handful of real people try to complete real tasks on your design, then fixing the top three problems and testing again. Reach for it before build, to settle a design argument with evidence, or when the team is debating what users will do instead of watching five of them.

The full idea

Two names anchor this skill. Steve Krug, whose book Rocket Surgery Made Easy argues for small, frequent tests with fixes made the same morning. And Jakob Nielsen, whose research found that five users find about 85 percent of the problems in a given design. The lesson from Nielsen is not "five is enough forever." It is: test five, fix, test five again. That beats twenty users on one version every time.

One boundary before we start. A usability test answers can they use it. It does not answer do they want it. For want, you run customer interviews. Mixing the two questions ruins both answers.

Tests are won or lost in task design. Tasks are scenarios with a goal, not instructions. "You want to order lunch for yourself and a vegetarian coworker, arriving by 12:30. Do that." Not "Tap the group order button." The moment your task names a UI element, you are testing reading comprehension. Use their reality where you can: their address, their real hunger. Four to six tasks, riskiest flow first because attention fades. Include one task that tests whether they can find the feature before you test whether they can use it. Define success per task in advance: unaided, with struggle, failed. Otherwise grading becomes vibes.

Moderating is a discipline of silence. Ask them to think aloud. Answer questions with questions: "what would you expect that to do?" Never rescue before the failure has taught you something: "what would you do if I weren't here?" Never explain the design, because you will not ship yourself alongside it. Watch the hands and hesitations over the words. Behavior is the finding. The polite person who says "this is nice" while failing the task three times gave you a blocker, not a compliment.

Food delivery example. Five participants. Task one: find a restaurant open now that delivers to your address. Task two: change the delivery address after adding items. Task three: tip the driver after delivery. Three of five could not find where to change the address because it was hidden under the map. Two said "oh, that's fine" while scrolling past it twice. That is your first fix. Not the small font on the receipt that one person mentioned.

Synthesis follows Krug's rule. Same day, each observer lists the three worst problems they saw. Dedupe. Fix the top three only before the next round. A forty-item findings report is where usability data goes to die. Small test, top-three fix, retest beats the big quarterly study by an order of magnitude. Log findings and fixes so the same problem found twice shows up as a pattern.

Unmoderated tools are for benchmarking known flows with completion rate and time on task. They cannot probe, so do not use them to explore a design you are still shaping. Why a PM cares: you will sit in arguments about what users will do. The cheapest way to end the argument is to watch five of them.

Information Architecture

TLDR: Structuring navigation, labels, and content so users can find things: card sorting to learn their mental model, tree testing to check the structure. Reach for it when designing or reorganizing navigation, naming sections, deciding where a feature lives, or when users keep "not finding" things that exist.

The full idea

Information architecture, or IA, comes from Rosenfeld and Morville's book Information Architecture, known as the polar bear book because of its cover, and from Donna Spencer's practical work on card sorting. Here is the definition I want you to keep: IA is the argument the product makes about how the user's world is organized. When users cannot find things, the taxonomy is wrong. Not the users, and usually not the visual design either.

The core diagnosis is one question: whose model is it? Most broken IA is the org chart or the database schema leaking into the navigation. Sections named for the teams that built them. Splits where the backend splits. The user's mental model groups by their task and their vocabulary. So every IA job starts here: is this structure organized by how we build it or by how they use it?

Now the methods, matched to the question. Open card sort: users group your content their way and name the groups. Use it to discover the mental model before you design a structure. The group names users invent are label gold. Closed card sort: your categories, their sorting. Use it to validate a proposed structure or place new items into it. Tree test: users find X in a text-only hierarchy with no visual design to help. A failure is unambiguous: the label or the location is wrong. Run it before UI exists and again after big changes. Under about 70 percent first-click success, the argument is not landing. And first-click testing on mocks, from Bob Bailey's research: get the first click right and task success roughly doubles.

Labels are the IA's interface. User vocabulary over internal. What users type into search is their label. One concept, one name. Scent over cleverness: a label must predict what is behind it. "Workspace Hub" predicts nothing.

Here is our food delivery app. The bottom nav says Home, Marketplace, Activity, Wallet, More. An open card sort with ten users produces groups they called Order Food, My Orders, Saved Places, and Payment. Nobody said Marketplace or Activity. "Reorder my last meal," the most common task, lived under More. A tree test on the new structure got 82 percent first-click on "find your last order." The old one got 41. That is a finding you can ship.

Structure heuristics. Breadth beats depth at equal scent, because each extra level sheds users. But forty items at one level is a search problem pretending to be navigation. Things can live in two places when tasks arrive from two directions. And search is IA too: the no-results page, synonyms, and top-query tuning are part of the architecture.

The most common mistake is redesigning the visual nav to fix what a tree test would show is a taxonomy problem. New icons, same wrong labels. Why a PM cares: "where does this feature live" is a decision you will make monthly, and the honest answer comes from a card sort, not a naming meeting.

Visual Hierarchy

TLDR: Directing attention with layout, type, spacing, and contrast so the user knows what to look at first and what to ignore. Reach for it when a screen feels cluttered or flat, when everything looks equally important, or when reviewing visual quality in critique.

The full idea

Visual hierarchy is the design answering a question before the user asks it: "what should I look at first, and what can I ignore?" The grounding here is the Gestalt principles from Max Wertheimer, typographic scale practice from Robert Bringhurst as passed down through every good design system, and the working heuristics made popular by Refactoring UI by Adam Wathan and Steve Schoger. The one-line summary: a screen where everything is emphasized has no emphasis.

Four Gestalt principles carry most of the load. Proximity: things close together read as related. This is the most violated principle in practice. A label equidistant from two fields belongs to neither. Padding inside a card larger than the gap between cards dissolves the cards. Space is meaning, so spend it on purpose. Similarity: same style implies same behavior. If blue text is sometimes a link and sometimes just emphasis, both uses are broken. Common region: enclosure groups things. Which is why the fix for clutter is rarely more boxes. Try whitespace first. Borders are the grouping tool of last resort. Continuity and alignment: the eye travels along lines. Every misalignment is a speed bump. A strict grid is invisible until it breaks, and then it is the only thing you can see.

Type does the heavy lifting. Use a deliberate scale: one ratio, five to seven sizes, from the system's tokens. And size is only one lever. Weight, color contrast, and spacing rank content with less noise than size alone. Secondary text should be quieter, not smaller. Tiny grey text fails hierarchy and accessibility at once. Line length around 45 to 75 characters.

Two tests. The squint test: blur the mock. What survives is the hierarchy. Is it the right thing? The one-bold-move rule: one unmistakable primary action per screen. Two primary buttons is a decision the design refused to make and exported to the user. Emphasis is a budget, and it is zero-sum.

Take the food delivery app's restaurant page. Squint at it. What pops? The "Add to cart" button on every item, all in brand orange, plus "Start group order," plus "Schedule," all primary. The restaurant name, delivery time, and minimum order are the same 14-point grey. The thing the user most needs, "delivers in 25 min, $2.99 fee," is invisible. Fix: one primary action, the rest become quiet outlines; the delivery line moves up and gets weight, not size; the menu sections get grouped by spacing instead of eleven dividers. Nothing new was added. The budget was spent differently.

The most common mistake is primary buttons everywhere, the "everything is important" tell. Why a PM cares: you will be asked to "make the new feature more visible," and the honest answer is often that the screen already spent its boldness. Knowing that lets you ask for a real trade instead of a louder button.

Design System Ops

TLDR: Running a design system as a product: deciding what earns a component, designing component APIs, choosing a team model, and measuring adoption. Reach for it when building or governing a system, deciding whether something becomes a component, or when the system exists but teams route around it.

The full idea

The grounding for this skill is Nathan Curtis, who wrote the standard work on design system team models and component lifecycle, and Brad Frost, whose atomic design gives us a vocabulary of atoms, molecules, and organisms. The central claim: a design system is a product whose customers are product teams. And it fails the way products fail: built without discovery, shipped without adoption, maintained without a roadmap.

First question: what earns componentization? Not everything used twice. The bar is three parts. Used, or credibly about to be used, by three or more teams. A stable job, meaning the pattern's purpose will not churn monthly. And inconsistency costs something: user confusion, accessibility risk, or rebuild waste. Below that bar, publish it as a pattern, a documented recipe with no code contract. Promoting one team's habit to a system component freezes their local decision into everyone's constraint.

Second, component API design. A component's props are its contract, and the contract encodes policy. Expose intent, like variant="destructive", not styling escape hatches like color="#D33", or the system becomes a longer way to write CSS. Every component ships with all five states designed, accessibility audited once at the component, and guidance that includes when not to use it.

Third, the team model, from Curtis. Solitary: one team owns it, others consume. Fast, then a bottleneck, then a resentment. Centralized: a dedicated system team, sustainable if funded like a product team with a roadmap and research on its users. Federated: contributors from product teams with central stewardship. Best adoption, but it needs real governance or it becomes a junk drawer with a logo. Most orgs should run centralized with federated contribution. Most actually run solitary by accident. Contribution needs a paved road from "my team needs a variant" to "it's in the system," with SLAs. When contributing is slower than forking, teams fork, rationally. Every detached instance is a vote about your process, not their discipline.

Fourth, adoption is the metric. Percent of new screens on system components. Detach rate per component: high detach means the component's API is wrong, not the teams. Version lag across consumers. Mandates create malicious compliance. And deprecation is part of ops: announced, with a migration path and a removal date.

Our food delivery app has a restaurant card. The consumer app, the merchant dashboard, and the courier app all show restaurants. Three teams, stable job, inconsistency confuses support. That earns a component. The surge pricing badge used by one team on one screen does not. It becomes a pattern. When the courier team detaches the card forty times to add an ETA slot, that is not a discipline problem. The card's API is missing a prop.

The most common mistake is counting components as the success metric. A vanity total. Why a PM cares: someone will ask you to fund or defund the system team. The answer comes from adoption and detach rate, not from how many components exist.

Journey Mapping

TLDR: Mapping one person's end-to-end experience to find where it hurts, then using a service blueprint to find why it hurts backstage. Reach for it when problems span screens, channels, or teams, when onboarding or retention sags for unclear reasons, or before redesigning any multi-step flow.

The full idea

Three sources ground this skill. G. Lynn Shostack invented service blueprinting in the 1980s. Kerry Bodine and the Forrester lineage shaped modern journey mapping practice. And Daniel Kahneman's peak-end rule tells us how to read the emotional line. Hold onto this sentence: a journey map is a diagnostic instrument, not a poster. If it does not change a decision, it is wall art.

Scope it like a diagnostician. One persona, one goal, end to end, including the stages outside your product. The journey starts at the struggling moment, not at your login screen. "Maya, from realizing she has no dinner plan at 7 p.m. to having eaten" beats "the user experience of our app." The seams between channels, app to SMS to phone call to app again, are where journeys die, and no single team owns a seam by default. That is why the map has to.

Build the layers from evidence. Rows against a timeline of stages: doing, the observed actions; thinking and feeling, verbatims from research, not invented emotions; touchpoints per channel; and the emotional line. A map without research inputs is persona fan fiction. Read the line with peak-end in mind: the worst moment and the final moment dominate how people remember the whole thing. A mediocre middle matters less than one terrible peak or a limp ending. That reorders your fix list against intuition. Then mark the moments of truth: the two or three points where the relationship is decided. First value delivered, first failure handled, the loyalty ask.

When the cause is backstage, blueprint. The journey map shows where it hurts. The service blueprint shows why. Below the customer's actions you add frontstage, what they see; backstage, the staff and system actions they do not see; support processes; and the line of visibility. Most journey pain traces to something below that line.

Here is Maya in our food delivery app. Her order is accepted at 7:10. The tracker says "Preparing" for forty minutes. She calls the restaurant. They never received it. Her verbatim: "I felt stupid for trusting the little progress bar." The peak is that phone call. The ending is a refund email two days later. Above the line, the tracker screen looks fine. Below the line, the restaurant's tablet went to sleep and the system marks an order "Preparing" on send, not on acknowledgment. Redesigning the tracker would be repainting a door that is nailed shut. The fix is a backstage acknowledgment timeout and an honest "restaurant hasn't confirmed yet" state.

Output discipline: each mapped pain gets evidence, a stage, a severity, a suspected backstage cause, and an owner. Feed the top items into the roadmap. A map dated last year describes a product that no longer exists.

The most common mistake is building the map in a workshop from what the team assumes users feel. Why a PM cares: retention problems rarely live on one screen. The map is how you find the seam nobody owns, and then own it.

Design Metrics

TLDR: Measuring design with Google's HEART framework and the Goals, Signals, Metrics method, then hanging those numbers on the product's metric tree. Reach for it when a design team cannot show impact, when choosing metrics for a redesign, or when "the design is better" needs a number.

The full idea

This skill comes from Google's HEART framework, published by Kerry Rodden, Hilary Hutchinson, and Xin Fu, together with the Goals, Signals, Metrics method that makes it usable in practice. Design has a chronic credibility problem: it measures inputs, like screens shipped and components built, while the organization measures outcomes. HEART is the translation layer between the two.

HEART is five rows. Happiness: attitude, measured as satisfaction or perceived ease at the moment of use. Annual NPS is weather, not feedback. Engagement: voluntary depth and frequency of use. Only meaningful where more use means more value. A support portal that optimizes engagement is optimizing failure. Adoption: new users or accounts taking up the feature. Retention: do they come back. This is the metric most redesigns quietly damage. Task success: effectiveness, efficiency, and error rate. Completion percent, time on task, error recovery. This is the most design-attributable row in the whole framework.

The rule is to pick two or three rows that match the design's intent. A redesign meant to reduce support load is Task success plus Happiness, not Engagement. Choosing all five is choosing none.

Then the discipline that stops metric-grabbing: Goals, Signals, Metrics. State the goal in experience terms. Choose the signals that would show it. Then define the metric precisely. Run it in reverse to audit a dashboard: any metric you cannot trace back to a goal is dashboard lint.

Here is the food delivery app. The team redesigned checkout because too many people abandoned at the address step. The intent is that people finish ordering without friction. So the rows are Task success and Happiness. Goal: a first-time user completes checkout without help or a retry. Signals: fewer address edits after the first entry, fewer support chats during checkout, fewer back-button presses on the payment screen. Metrics: percent of first orders completed without an address edit; median time from cart to order placed; a one-question "how easy was that?" right after the confirmation. Before the redesign, 48 percent of first-timers completed without an edit. After, 71. That second number means nothing alone. Against the baseline it is a career.

The most important rule: connect to the tree or float forever. Every design metric should hang off the product's metric tree. Task success on checkout feeds first-order conversion, which feeds weekly orders, which feeds the north star. A design team whose metrics live in a separate universe will lose every prioritization argument to a team whose metrics are the tree.

The most common mistake is shipping a redesign with no baseline captured. The before is now unmeasurable and the debate is unwinnable. The second is choosing Engagement because it is the one that always goes up. Why a PM cares: you are the person who decides what goes on the dashboard, and you will be asked "did the redesign work?" The only honest answer is a before-and-after on the same task, tied to a metric the business already cares about.

TLDR: Running design critique sessions that make the work better while it is still cheap to change: framing, feedback discipline, and decision capture. Reach for it when setting up or fixing a crit ritual, prepping to present work, or when crits have turned into either bloodsport or applause.

The full idea

Three sources ground this skill. Ed Catmull's Braintrust rules from Creativity, Inc., the book about how Pixar reviews its films. Lara Hogan's feedback equation. And the Feldman critique structure, the describe, analyze, interpret, judge sequence from art education. A crit exists to make the work better while it is still cheap to change. Not to approve it, not to display it, and not to perform seniority. The two failure modes are the same failure: feedback aimed at people, which is bloodsport, or at nobody, which is applause.

Start with the Braintrust rules, enforced. One: the work gets notes, the person does not need defending. Say it out loud every session until it is culture. Two: no authority in the room. The Braintrust cannot mandate. The designer owns what to do with every note. The moment notes become orders, presenters start bringing safe work, and the crit is dead a quarter before anyone notices. Three: problems, not prescriptions. "I lost where I was in the flow at step three" is a note. "Make the stepper sticky" is a solution wearing a note's clothes. Solutions are welcome as illustrations of the problem, never as the requirement.

Structure beats vibes. The presenter frames first, two minutes, written in advance: the problem, the stage, and what feedback is needed. Stage matters because feedback calibrated to the wrong stage is noise. Visual polish notes on a concept sketch waste the room. Then silent looking time before anyone speaks, because first-reaction theater rewards the fastest talker, not the best eye. Then clarifying questions, then critique. Half of most crit arguments are two people describing different understandings of the design. The facilitator is traffic, not judge: pulls in the quiet, parks the rabbit holes. Close with capture: what the designer heard, what they will explore, what is parked, logged so the same debate does not rerun next week.

Giving the note uses Hogan's equation. Observation, plus impact, plus a question or request. On our food delivery app: "The 'Place order' button is below the fold on a standard phone," observation. "I'd expect many first-time users to scroll past it or think the cart is the last step," impact. "What led to putting the tip selector above it?" question. That last part is load-bearing. It presumes intent. Half the time there was a reason, like a legal requirement on tip disclosure. A constraint you did not know beats an opinion you did.

Compare the bad version: "I don't love the checkout, the button feels buried, just move it up." A feeling, no impact, and an order. The designer now either obeys or resists. Neither makes the work better.

The most common mistake is the most senior voice speaking first. The anchor is set, dissent is priced out. Why a PM cares: you are often that senior voice, and you will run these rooms. Your job is traffic, not verdict. Bring your prescription as a question.

Design Canvases

TLDR: One-page tools that turn confidence into testable hypotheses before anything gets built: the Lean UX Canvas, the Empathy Map, the Opportunity Canvas, and the Test Card. Reach for them when kicking off a design initiative, converting a feature request into hypotheses, aligning a team before pixels, or when work is starting from a solution instead of a problem.

The full idea

Four tools, four authors. Jeff Gothelf's Lean UX Canvas, version 2, from Lean UX. Dave Gray's Empathy Map from XPLANE. Jeff Patton's Opportunity Canvas. And Strategyzer's Test Card. Business canvases model the business. These model the work about to be designed. Their shared job: turn confidence into hypotheses before the hypotheses turn into shipped code.

The engine is the Lean UX Canvas. Eight boxes, filled in order. One, the business problem, in outcome terms, without the solution baked in: "declining first-week reorders," not "we need a loyalty program." Two, business outcomes: the metric that moves. Three, users, specifically. Proto-personas are fine, labeled as guesses. Four, user outcomes and benefits: what the user is trying to achieve and feel. Five, solutions. Now ideas are allowed, plural, sketched cheaply. Six, hypotheses: "We believe [business outcome] will be achieved if [user] attains [user outcome] with [solution]." Missing any part and it is a hope. Seven, the most important thing to learn first: the riskiest assumption inside the strongest hypothesis. Eight, the least work to learn it: a test, this week, sized in days. The canvas is not done until something is scheduled. The ethic: boxes one through four before box five. A team that starts at box five is decorating a decision.

For our food delivery app: business problem, first-week reorder rate fell from 38 to 29 percent. Users, first-time weeknight customers. User outcome, dinner sorted without thinking, again. Solution idea, a "reorder last meal" button on the home screen. Hypothesis: we believe first-week reorders will recover if first-time weeknight customers get dinner sorted in one tap with a reorder button. Riskiest assumption: that they want the same meal again. Least work to learn it: check the last 500 second orders and count how many repeated a restaurant. One day, no code.

The Empathy Map sits before personas. Six zones around a specific user in a specific situation: says, thinks, does, feels, pains, gains. Says must be verbatims. Where does contradicts says, behavior wins. Run it cold and mark every sticky that is a guess. The guess density is the finding. An empathy map built from no user contact is a séance.

The Opportunity Canvas is Patton's middle altitude: bigger than a story, smaller than a business model. Nine boxes around one feature, including the solution today, the workaround, which is the real competitor. Its spine: user value and business value must both be nameable. Use it to triage which of five candidate features deserves a PRD at all.

The Test Card is the hypothesis's receipt. Four lines: we believe that, to verify we will, and measure, we are right if. That threshold is set in advance. Pair it with a Learning Card afterward and log both.

The most common mistake is the canvas workshop that produces beautiful walls and zero scheduled tests. Why a PM cares: you will receive feature requests as solutions every week. These are the one-page tools for walking them back to a problem.
